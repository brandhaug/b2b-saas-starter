Researched live on 2026-11-01. Release window: 2026-05-01 through the time of retrieval on 2026-11-01, UTC. This is a feature-adoption audit of the current checkout, not an upgrade plan. No dependencies or application code were changed.

## Scope and method

- Read all 20 manifests: the root, `infra`, the three `apps/*` manifests, and the 15 `packages/*` manifests. These contain 214 direct external dependency declarations and 94 distinct external package names. Workspace packages are internal and excluded from the external count.
- Matched all 94 catalog entries in `pnpm-workspace.yaml` to direct declarations. There are **zero unused catalog entries by declaration**. That does not establish that every declaration is necessary at runtime. Peer-only packages and packages loaded by tools need different evidence from source imports.
- Parsed `pnpm-lock.yaml`: 1,193 package identities and 1,198 dependency snapshots. Direct resolutions match the catalog. The exceptions in notation are `vite`, an npm alias for `@voidzero-dev/vite-plus-core@1.4.0`, and `qrcode.react`, declared `^4.2.0` and resolved `4.2.0`.
- Retrieved npm metadata for all 94 direct packages, plus the pnpm pin, npm's Node wrapper, and the transitive parser override. Read the registry `time` map rather than inferring release dates from version strings. Registry metadata is available at `https://registry.npmjs.org/<package-name>`; for `vite`, query `@voidzero-dev/vite-plus-core` instead.
- The 94 packages have 4,646 package-version publications in the window, including prereleases, nightlies, and parallel release lines. Eleven have none. This count is not a claim that 4,646 release notes were individually read.
- Retrieved GitHub release histories for 67 repository identifiers discovered from package metadata. Pagination reached the start of the window or exhausted available releases for 66. Some exhausted repositories have no useful release notes. AI SDK hit GitHub's 10,000-result limit before reaching May. Package changelogs supplemented release lists, especially for Paraglide, inlang, Babel's Rolldown bridge, Vite React, js-yaml, and AI SDK.
- Used release indexes to triage families, then inspected release bodies and code for the recommendations below. For TanStack adapters whose notes only say “updated dependencies,” inspected the underlying core release notes too. This is complete dependency inventory coverage, with qualified release-history and feature coverage.
- Dates below refer to npm publication when explicitly labeled npm, otherwise GitHub release publication. Commit dates, tag dates, npm dates, and release-page dates can differ. Registry `latest` is not necessarily the newest prerelease or the right upgrade target.

The research scripts and raw responses were kept outside the repository under the session temporary directory, `dependency-evidence`. They are not a durable part of this report. The upstream URLs below are the durable citations. Existing context was checked against `docs/research/dependency-audit.md`, not treated as fresh upstream evidence.

Manifest coverage: `package.json`; `infra/package.json`; `apps/{api,background,web}/package.json`; and `packages/{ai,api,auth,authz,billing,capabilities,db,email-delivery,email,env,failure,i18n,logger,oxlint-plugin,rate-limit}/package.json`. The braces abbreviate individual paths, not additional glob matches. The sole lockfile found was `pnpm-lock.yaml`.

## Recommended adoptions

### 1. Cross-browser passkey tests

[Playwright 1.61.0, June 15](https://github.com/microsoft/playwright/releases/tag/v1.61.0) added `browserContext.credentials`, a virtual WebAuthn authenticator that works across browsers. [1.62.0, July 24](https://github.com/microsoft/playwright/releases/tag/v1.62.0) added credentials to storage state. [1.64.0, October 7](https://github.com/microsoft/playwright/releases/tag/v1.64.0) added signature-counter controls and reproducible `--shuffle` ordering.

The repository has `@playwright/test@1.64.1`, but `apps/web/e2e/authentication.ts` still uses `newCDPSession` and `WebAuthn.*` commands. Move the shared passkey helper to the Credentials API, preserve user-verification and resident-key behavior, and then run the existing registration, sign-in, and recovery scenarios across the configured browsers. Persist credentials only where the test intentionally reuses an identity. Signature-counter controls are useful for replay/cloned-authenticator scenarios if those checks are part of the auth contract.

This is test-only and does not change Workers or SSR code. The cost is fixture migration and checking behavioral parity, not a package upgrade. Use seeded shuffle on a separate diagnostic run to find shared-state assumptions. Do not replace every serial test with a lock merely because 1.64 supports test locks.

The authoritative API link is [Credentials](https://playwright.dev/docs/api/class-credentials). A guessed `class-webauthn` documentation URL returned 404 during research and was not used as evidence.

### 2. Make dynamic localization access fail at lint time

Paraglide **2.28.0**, npm **2026-10-14**, added the `@inlang/paraglide-js/eslint` plugin and `paraglide/no-dynamic-message-access`. See the [first-party changelog](https://github.com/opral/paraglide-js/blob/main/CHANGELOG.md) and [publication metadata](https://registry.npmjs.org/@inlang/paraglide-js). Installed **2.29.3** includes it.

`packages/i18n/scripts/compile.mjs` generates messages; `lint.config.ts` does not enable this rule. Configure its `messageModules` option for the shared package's actual message import aliases. The benefit is preventing dynamic indexing that defeats static message analysis and tree-shaking. First try the ESLint-compatible plugin through Vite+/Oxlint's JavaScript plugin support; verify that its required rule APIs are supported before making it a mandatory check.

Keep the existing unused-message check. The new rule answers a different question. Locale URL trailing-slash canonicalization is already in the custom compiler flow and is not a new adoption task. This is build-time work with no additional Worker service or client runtime.

### 3. Remove only the Fallow workarounds that diagnostics prove redundant

[Fallow 3.35.0, October 22](https://github.com/fallow-rs/fallow/releases/tag/v3.35.0) recognizes Vite+ configs, `vp` scripts, JavaScript lint plugins, and Vitest activation through `vite-plus`. [3.36.0, October 25](https://github.com/fallow-rs/fallow/releases/tag/v3.36.0) reports redundant entry patterns and dependency/ignore exceptions. Installed **3.37.0** already includes both.

`.fallowrc.json` still explains explicit test globs as a workaround for Vitest detection through Vite+, and ignores lint dependencies loaded through `lint.config.ts`. Capture `fallow dead-code --format json` and inspect `workspace_diagnostics`, especially `entry-pattern-redundant` and `ignore-dependencies-entry-redundant`. Remove one confirmed redundant exception at a time and compare findings with the current zero-issue regression baseline.

The config imports another file and contains custom Workers entry points, generated messages, and vendored UI. Upstream Vite+ support does not prove all of those are discoverable. Keep exceptions that still explain real dynamic loading. This is a low-cost cleanup with no production-runtime impact.

### 4. Align custom rule helpers with the bundled linter

[Vite+ 0.3.2, September 14](https://github.com/voidzero-dev/vite-plus/releases/tag/v0.3.2) exports `vite-plus/lint/plugins` and `vite-plus/lint/plugins-dev`. Installed **1.4.0** includes them. `packages/oxlint-plugin/src/index.ts` and its internal helpers still import direct **`@oxlint/plugins@1.80.0`**, while this Vite+ line bundles Oxlint **1.89.0**.

Evaluate replacing helper and test imports with the Vite+ exports. Check the AST/type APIs used by the custom rules and run their existing tests before dropping the direct dependency. This would reduce independent tool API drift. It is not proof of a current bug, and deleting the package before checking supported exports would be premature. Preserve Vite+'s pinned Node/pnpm setup and the current Vite alias.

### 5. Bring Effect lint policy forward deliberately

Installed **`oxlint-plugin-effect@0.11.0`**, npm August 22, predates the current Effect 4.1 application. [0.21.0, October 1](https://github.com/cevr/effect-oxlint/releases/tag/v0.21.0) explicitly targets Effect 4 stable. [0.29.0, October 16](https://github.com/cevr/effect-oxlint/releases/tag/v0.29.0) adds `noPointFreeLog`, opt-in `requireSpawnBudget`, and more accurate `noGlobals` handling. It also makes `noInterruptibleMemo` opt-in and corrects its explanation for Effect 4.0.1 and later.

`lint.config.ts` spells out the enabled rule names. An upgrade alone will not enable new names. First compare diagnostics from the current rules under the new plugin; then consider bounded process-test budgets and deterministic tooling rules in their appropriate paths. Keep browser/DOM exemptions and host-adapter exemptions. A blanket `noLocaleCompare` policy would be wrong for localized UI sorting even if it helps stable generated output.

This is the most worthwhile upgrade-based feature work, but it can produce many findings. Do not apply an entire recommended preset and fix the resulting churn without reviewing each rule's assumptions.

### 6. Localize toast accessibility labels

[Sonner 2.0.8, August 9](https://github.com/emilkowalski/sonner/releases/tag/v2.0.8) added custom aria-label support. The [tagged types](https://github.com/emilkowalski/sonner/blob/v2.0.8/src/types.ts) expose `customAriaLabel`, `containerAriaLabel`, and `toastOptions.closeButtonAriaLabel`.

The installed version is **2.0.8**. `apps/web/src/components/ui/sonner.tsx` does not supply localized labels. Pass translated labels from the application's localization boundary rather than making the vendored wrapper own locale state. Check announcement behavior, the close button, and direction in the supported locales. This is a small client-side accessibility improvement; it does not require an SSR or Effect redesign.

### 7. Use request-scoped MCP visibility for discovery

[Effect 4.1.0, October 29](https://github.com/Effect-TS/effect/releases/tag/effect%404.1.0) adds `McpServer.visibility` to hide tools, resources, and prompts based on request-provided services. The same release supplies `McpTest.makeClient` for in-memory tests through the JSON-RPC encoding.

`apps/api/src/mcp.ts` already uses the new request middleware/registration model, but does not use visibility. Filter lists to operations available to the caller's workspace, permissions, and scopes. Reuse authorization decisions from capabilities/authz. Visibility is discovery behavior, not permission enforcement; retain checks on execution and direct calls.

Keep actual Worker/OAuth tests as the authority. The in-memory client can simplify existing isolated registration tests where transport setup obscures the assertion. The new cache hints target protocol `v2026_07_28`, while the current code uses `v2025_11_25`. Do not add hints without a protocol and client-compatibility decision. Per-request visibility fits Workers; process-wide visibility state does not.

### 8. Consider standardized public HTTP errors

The same [Effect 4.1.0 release](https://github.com/Effect-TS/effect/releases/tag/effect%404.1.0) adds `HttpApiError.Problem`, `HttpApiSchema.asProblem`, and Problem Details middleware with `application/problem+json` rendering and decoding. Installed **4.1.0** has these APIs; no current adoption was found.

Evaluate this at `packages/api` and `apps/api/src/http.ts`, keeping business errors in capabilities and their existing failure mapping. The gain is a standard machine-readable contract for external API clients and generated documentation. The cost is changing endpoint error schemas, client decoders, and error-contract tests. Review whether validation details may expose internal fields before enabling detailed decoding errors.

There are no production compatibility obligations in this starter, but consistency still matters. Do not convert some public errors while leaving clients to guess the format. This is more expensive than the first seven items and should be a focused API decision.

### 9. Add maintainability diagnostics without confusing them with coverage

[Fallow 3.38.0, October 30](https://github.com/fallow-rs/fallow/releases/tag/v3.38.0) adds `health.maxFileLines`, off by default, with per-path overrides. Installed **3.37.0** requires an upgrade. Current scripts invoke only `dead-code`; they do not exercise health/audit reporting.

Use a non-blocking health report first, then decide thresholds for application modules versus generated files, test fixtures, and vendored UI. `lint.config.ts` is a concrete large-file candidate, but an explicit policy file should not be split merely to meet a count. Fallow's static test reachability is not measured test coverage. Its experimental tsrs backend also needs the backend-specific packages and version pin; the existing root `tsrs` declaration alone does not enable it.

### 10. Use the email preview tools already paid for

[React Email 6.2.0, May 21](https://github.com/resend/react-email/releases/tag/react-email%406.2.0) adds CSS-first `theme` and `utility` props to `<Tailwind>`. [6.5.0, May 27](https://github.com/resend/react-email/releases/tag/react-email%406.5.0) adds email-client filtering and accessibility defaults. [6.8.0, July 13](https://github.com/resend/react-email/releases/tag/react-email%406.8.0) adds live editing of preview props; 6.9 improves the editor layout.

Both `react-email` and `@react-email/ui` are **6.11.5**. Use `packages/email/src/previews` to exercise long names, empty optional fields, translated copy, and unusual amounts with the props editor. CSS-first theme reuse is worth a small experiment if templates duplicate the web palette. Keep preview/build tools on Node; preserve the existing Worker-safe rendering boundary. Do not narrow compatibility warnings to fewer email clients without an actual supported-client policy.

## Evidence limits and follow-up checks

1. **AI SDK history is incomplete.** npm reports 466 in-window publications, 388 stable. The retrieved package changelog matched 220 versions. GitHub pagination fetched 10,000 monorepo releases, then returned HTTP 422, “Only the first 10000 results are available,” before reaching May. Older release lines and prereleases need tag-specific retrieval for exhaustive coverage. The recommendation to retain Effect-owned inference is based on actual imports, not on a claim that the missing AI releases have no useful features.
2. **Registry publication is stronger than feature attribution for some packages.** Fontsource, DefinitelyTyped packages, and Standard Webhooks lack useful retrieved package-release narratives.
