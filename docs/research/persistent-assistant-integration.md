# Persistent assistant integration

Research for [Research: Assess persistent chat integration with Effect and workspace authority](https://github.com/brandhaug/b2b-saas-starter/issues/443). Checked 2026-09-15 against repository commit `40e586f189fecf0d844e802618209a2416dc816a`, installed package source, and current primary documentation/source. This report supplies evidence for an implementation-ready specification. It does not choose conversation visibility, retention periods, or approval policy for the user.

## Findings that change the starting assumption

The application already saves **Assistant Tasks**. A task records a delivery investigation, evidence, a possible replay proposal, approval/cancellation, and a replay identity. It is not a conversation. The chat transcript still exists only in React state, and the model sees one question at a time. A Durable Object would therefore add a conversation runtime alongside existing task behavior, not replace the task store. Sources: [chat component](../../apps/web/src/components/workspace-assistant-page.tsx), [task capability](../../packages/capabilities/src/developer-platform/webhook-investigation-tasks.ts), [D1 adapter](../../packages/capabilities/src/developer-platform/webhook-investigation-tasks.live.ts).

The current model adapters explicitly reject assistant-role history and streaming. Installing a chat package or saving the browser transcript cannot make them multi-turn. Workers AI currently receives a flattened prompt string; the OpenAI-compatible adapter sends a non-streaming `/chat/completions` request. Both report empty token-usage fields. Sources: [shared acceptance policy](../../packages/ai/src/text-model.ts), [Workers AI adapter](../../packages/ai/src/workers-ai.ts), [OpenAI-compatible adapter](../../packages/ai/src/openai.ts).

Three integration candidates remain credible: custom conversation storage/runtime with Effect, AIChatAgent with an Effect-to-UI-stream adapter, or AIChatAgent with AI SDK inference and Effect business capabilities. They differ mainly in who owns model execution, transport, and recovery. No candidate removes application authorization or lifecycle work.

## Current request and persistence boundaries

### Web

`WorkspaceAssistantPage` keeps `transcript` in `useState`, posts `{workspaceSlug, question, taskId?}`, and drops a completed answer after unmount. Its transcript is never submitted as model context. The route can reopen a task through `taskId`, but that does not restore chat. Sources: [page component](../../apps/web/src/components/workspace-assistant-page.tsx), [assistant route](../../apps/web/src/routes/workspaces.$workspaceSlug.assistant.tsx).

The server function resolves the current session, current Workspace membership and `assistant:read`. When a task is selected it also checks `webhook:list`, reloads the task, and constructs model evidence from diagnosis, source delivery ID, status, outcome, response status and bounded attempts. It excludes payloads, headers, response bodies and endpoint URLs. Unconfigured deployments show an unavailable assistant UI, although the underlying service has a deterministic mock. Provider errors become a safe unavailable response. Sources: [web assistant boundary](../../apps/web/src/lib/server/assistant.effects.ts), [session and permission guard](../../apps/web/src/lib/server/authorize.ts).

### REST

`POST /assistant/answer` is an independent bearer-token route. It uses the Effect HTTP contract, assistant rate bucket and `assistant:read`, then calls the same service. The web app never calls this worker. REST accepts `AssistantPrompt`, including an optional client-supplied evidence string. That string is caller input, not server-verified task evidence; the web's evidence builder is not reused here. The service currently cannot execute tools, so this does not authorize an action. A persistent conversation API must distinguish caller text from trusted capability evidence. Sources: [REST handler](../../apps/api/src/handlers.ts), [contract](../../packages/api/src/index.ts), [request guards](../../apps/api/src/request-guards.ts), [assistant service](../../packages/ai/src/index.ts).

The specification must decide whether REST remains a one-shot endpoint, gains conversation operations, or addresses the same conversation runtime as web. If it gains access, token scope/workspace confinement remains mandatory. A human session must never become an API token merely to reuse the route. Existing Assistant Task create/get/approve/cancel operations are web server functions, not entries in the external operation catalog. Sources: [task boundary](../../apps/web/src/lib/server/assistant-tasks.effects.ts), [operation catalog](../../apps/api/src/operations.ts), [API intent](../../apps/api/AGENTS.md).

### Assistant Tasks and replay evidence

D1 stores task records with a Workspace foreign key, status, timestamps, JSON evidence and replay ID. Workspace deletion cascades those records. A task has no conversation foreign key today. List returns the latest 30; direct lookup can load older tasks. Sources: [schema](../../packages/db/src/schema.ts), [task storage](../../packages/capabilities/src/developer-platform/webhook-investigation-tasks.live.ts).

An eligible proposal concerns one source delivery and its endpoint URL. Approval rechecks source state, URL and enabled status. A conditional D1 mutation chooses approval or cancellation and commits its audit evidence atomically. Approval reserves `replay_<taskId>` before enqueue, and retry reuses that identity. Outcome comes from the actual replay delivery, including `unavailable` when retained evidence is missing. Neither a model answer nor successful enqueue establishes delivery success. Sources: [shared task behavior](../../packages/capabilities/src/developer-platform/webhook-investigation-tasks.ts), [Live transition](../../packages/capabilities/src/developer-platform/webhook-investigation-tasks.live.ts), [contract cases](../../packages/capabilities/src/developer-platform/webhook-investigation-tasks.contract.ts).

Approval currently means an explicit action by a currently permitted Member against the exact proposal. It is not restricted to the Member who requested the task. Preserve that distinction when choosing shared conversations. Chat text, client tool results, and a model-generated `approved: true` must never substitute for the existing authenticated action. This follows the [task intent](../../packages/capabilities/src/developer-platform/webhook-investigation-tasks.AGENTS.md) and [approval handler](../../apps/web/src/lib/server/assistant-tasks.effects.ts).

## What Effect and Alchemy already provide

Effect's installed `LanguageModel.make` accepts separate `generateText` and `streamText` implementations, encoded response parts, typed `AiError`, tools and schema handling. The limitation belongs to our adapters, not Effect. `ManagedRuntime.runPromise` accepts an abort signal. Our OpenAI fetch already receives Effect's interruption signal; the current Workers AI binding port has no cancellation parameter. Sources: [LanguageModel rc.112](https://unpkg.com/effect@4.0.0-rc.112/src/unstable/ai/LanguageModel.ts), [ManagedRuntime rc.112](https://unpkg.com/effect@4.0.0-rc.112/src/ManagedRuntime.ts), [current provider ports](../../packages/ai/src/workers-ai.ts).

Effect `Chat` maintains Prompt history, serializes operations on a local semaphore and can load/save through `BackingPersistence`. Its streaming history is accumulated in memory and saved on finalization. Installed `Chat.makePersisted` uses `Effect.orDie` for automatic save failures. It does not implement a durable incremental stream log or application recovery ledger. The semaphore belongs to that Chat instance, so two independently loaded instances are not a cross-request concurrency guarantee. Source: [Chat rc.112](https://unpkg.com/effect@4.0.0-rc.112/src/unstable/ai/Chat.ts).

Alchemy includes `AI.layerChatDurableObject` and a Durable Object `BackingPersistence` adapter. The adapter namespaces keys but ignores TTL. This is useful for a history experiment; adopting it as-is would conflict with a requirement for typed persistence failures and enforced retention. Alchemy also supports plain Worker DO bindings whose `className` matches a named exported class. Sources: [AI chat persistence beta.77](https://unpkg.com/alchemy@2.0.0-beta.77/src/Cloudflare/AI/DurableObjectChatPersistence.ts), [DO persistence adapter](https://unpkg.com/alchemy@2.0.0-beta.77/src/Cloudflare/Workers/DurableObjectChatPersistence.ts), [DurableObject binding](https://unpkg.com/alchemy@2.0.0-beta.77/src/Cloudflare/Workers/DurableObject.ts).

## Compatibility matrix

The estimates below are engineering judgments from the contracts above and below, not implementation measurements.

| Concern                      | Workers/D1 + Effect                                                                                  | Custom DO + Effect                                     | AIChatAgent + Effect protocol bridge                                  | AIChatAgent + AI SDK inference                                          |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Saved conversation           | New capability/store, using D1                                                                       | New conversation capability and DO storage             | SDK transcript, D1 conversation directory and domain records          | Same                                                                    |
| Browser disconnect           | Persisted history alone does not finish detached work; needs an execution owner and replay transport | Application owns turn execution and durable stream log | SDK owns chat transport/replay; Effect supplies response              | SDK owns chat transport/replay and AI SDK supplies response             |
| Current adapters unchanged   | One-shot only                                                                                        | One-shot only                                          | One-shot only                                                         | Replaced for persistent chat                                            |
| Multi-turn and streaming     | Extend provider adapters and context assembly                                                        | Same                                                   | Same, plus format mapping                                             | Provider SDKs handle model wire format, subject to model support        |
| Authoritative message format | Application schema / Effect Prompt                                                                   | Application schema / Effect Prompt                     | AI SDK UIMessage for transcript, explicit conversion to Effect Prompt | AI SDK UIMessage, converted to provider messages                        |
| Model execution owner        | Effect                                                                                               | Effect                                                 | Effect; SDK handles conversation admission/recovery                   | AI SDK within an Effect adapter boundary                                |
| Tools                        | Effect tool handlers call capabilities                                                               | Same                                                   | One chosen tool loop; map IDs/results/approval states                 | AI SDK tools call authorized Effect capability adapters                 |
| Typed failures               | Existing approach extends                                                                            | Same, including storage/recovery                       | Translate Effect errors to safe stream parts and terminal records     | Translate SDK/provider errors into domain failures at the adapter       |
| Maintenance burden           | Execution/reconnect protocol and concurrency                                                         | Complete chat protocol/recovery plus provider adapters | Both changing schemas, but no provider-provider bridge                | New inference dependency and ADR revision; less bespoke model wire code |
| Deterministic local mode     | Extend existing mock                                                                                 | Extend mock plus local DO storage                      | Mock Effect stream through actual SDK transport                       | Deterministic SDK-compatible fake through actual SDK transport          |

D1 remains a legitimate history store. For the chosen disconnect outcome it must be paired with a deliberate executor and replay protocol. A DO is a candidate owner for that work; [persistent assistant runtime](persistent-assistant-runtime.md) assesses recovery guarantees and cost.

### AIChatAgent's useful boundary and its traps

Cloudflare documents SQLite message persistence, resumable streams, WebSocket synchronization and data/tool parts. It requires a SQLite DO migration. `onChatMessage` returns a `Response`; it does not require that the response originated from AI SDK inference. `maxPersistedMessages` limits stored history, while model context needs its own pruning. Sources: [chat-agent documentation](https://developers.cloudflare.com/agents/communication-channels/chat/chat-agents/).

Current upstream source wraps `onRequest` to serve `get-messages` and intercepts chat protocol frames before forwarding unhandled messages to the consumer's `onMessage`. It persists custom request body data for continuations. It uses Sessions, queues turns by default, and enables `chatRecovery` by default. These details mean a check only inside `onChatMessage`, an inherited `onRequest`, or an ordinary `onMessage` override is insufficient to prove authorization of every built-in operation. Source: [AIChatAgent source](https://raw.githubusercontent.com/cloudflare/agents/a7b29135acf127cdf4a44114652970d0a22300de/packages/ai-chat/src/index.ts).

For an Effect bridge, convert validated stored text history into `Prompt`, consume `Stream<Response.StreamPart>` and emit AI SDK UI stream chunks. A minimal supported mapping needs stable message/part IDs, start/text-delta/end, finish metadata, error and abort. Tools need stable tool-call IDs and explicit input/output/approval mappings. Unsupported message parts should fail visibly, not be flattened. The AI SDK's chunk schema defines those distinct variants. Source: [UI message chunk schema](https://raw.githubusercontent.com/vercel/ai/main/packages/ai/src/ui-message-stream/ui-message-chunks.ts).

`createUIMessageStream` accepts an execute callback with a writer, so it can package output from a non-AI-SDK producer. The adapter must supervise the Effect consumer, propagate explicit cancellation, and sanitize errors. Returning an Effect `Stream` directly is not the `Response` contract. Source: [UI stream writer](https://raw.githubusercontent.com/vercel/ai/main/packages/ai/src/ui-message-stream/create-ui-message-stream.ts).

The wire protocol uses SSE framing for UI data and requires its protocol header on a custom HTTP backend. Raw provider SSE is not automatically the UI protocol. The SDK's client integration uses the Agents connection; replacing the current server-function submit path therefore requires a real client transport decision. Sources: [AI SDK stream protocol](https://raw.githubusercontent.com/vercel/ai/main/content/docs/04-ai-sdk-ui/50-stream-protocol.mdx), [Cloudflare client SDK](https://developers.cloudflare.com/agents/communication-channels/chat/client-sdk/).

A lower-level Effect-to-AI-SDK model adapter is possible in principle, but unnecessary for the UI protocol bridge. AI SDK's model contract has provider/model identity, `doGenerate`, `doStream` and version-specific result shapes. Wrapping Effect tool execution inside an AI SDK model while also enabling AI SDK tool execution would create competing owners. Prefer the Response boundary unless an experiment establishes a concrete need for a provider adapter. Sources: [V3 model interface](https://raw.githubusercontent.com/vercel/ai/main/packages/provider/src/language-model/v3/language-model-v3.ts), [V4 model interface](https://raw.githubusercontent.com/vercel/ai/main/packages/provider/src/language-model/v4/language-model-v4.ts).

With AI SDK inference, use one bounded model/tool loop, explicitly set retry/time/token/step budgets, and execute business tools through named Effect adapters with fresh authority. AI SDK exposes stop conditions, abort, timeout, provider options and tool execution. These are mechanisms, not the application's spend or permission policy. Change [ADR 0008](../adr/0008-effect-ai-starter-assistant.md) if inference leaves Effect LanguageModel; keep Effect services, schemas, capabilities and public errors. Source: [AI SDK streamText implementation](https://raw.githubusercontent.com/vercel/ai/main/packages/ai/src/generate-text/stream-text.ts).

## Authorization and evidence form one lifecycle boundary

The following are specification requirements inferred from existing repository rules. The exact sharing and revocation policy still needs a human decision.

| Event                                                               | Existing guarantee to preserve                                                               | New work or decision                                                                                                                                                                                          |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Open/list/reconnect/history                                         | Current membership, permission and suspension checks; outsiders get non-disclosing not-found | Authorize before DO selection/history read. Use immutable Workspace ID plus conversation ID, with a server-owned directory. Slugs and arbitrary instance names cannot prove access                            |
| New message, stop, regenerate, clear, tool-result or approval frame | Server functions authenticate every call                                                     | Gate each operation, validate payload limits and provenance, and reject client-supplied system/assistant history as authority. Audit built-in SDK frame interception before adopting it                       |
| Existing socket loses access                                        | Product calls check current state                                                            | Decide the maximum revocation delay; invalidate/close subscriptions and prevent further sensitive broadcasts. Read-only mode does not remove read access                                                      |
| Task evidence enters history                                        | `webhook:list` checked before reading and prompting                                          | Preserve sensitivity on derived answers, summaries, citations and exports. `assistant:read` alone cannot grant access to explanations derived from withheld webhook evidence                                  |
| Background continuation/recovery                                    | Background consumers recheck suspension at execution                                         | Persist actor references and authorization context, then resolve current authority on each continuation/tool execution. Do not persist a session object, role snapshot, or browser body as enduring authority |
| Replay approval races                                               | Conditional D1 approval/cancel and stable replay identity                                    | SDK tool approval UI must route to the exact authenticated domain approval. Reconcile a committed action after interruption instead of executing a new action                                                 |
| Workspace suspension                                                | Stops product access and ordinary background work                                            | Suspend chat submissions, resumption and outputs under an explicit policy; reactivation must not replay suppressed actions automatically                                                                      |
| Workspace/account deletion                                          | D1 foreign keys and plugin lifecycle own existing deletion                                   | DO storage needs explicit cleanup and a deletion marker that blocks late writes/recreation. Decide ownership of shared transcripts when one Member leaves or deletes their account                            |
| Export and retention                                                | Capability-built archives and explicit approved retention rules                              | Add a conversation export/deletion contract. Existing workspace and personal archives contain no transcript; workspace snapshots also do not collect Assistant Tasks                                          |

Sources: [workspace context](../../packages/capabilities/src/workspace-context.ts), [web authorization](../../apps/web/src/lib/server/authorize.ts), [role grants](../../packages/authz/src/roles.ts), [suspension policy](../../packages/capabilities/src/governance/workspace-suspension.AGENTS.md), [workspace lifecycle](../../packages/capabilities/src/governance/workspace-lifecycle.AGENTS.md), [workspace export snapshot](../../packages/capabilities/src/governance/workspace-export-snapshot.ts), [personal archive](../../packages/capabilities/src/governance/personal-data-export-archive.ts), [retention intent](../../packages/capabilities/src/governance/retention.AGENTS.md).

A practical concern is a privileged Member explaining a failed webhook, then a less privileged Member reopening that conversation. Removing the raw evidence field does not remove its content from the generated answer. Credible policies include a conversation-wide required permission set, private conversations with explicit sharing checks, or separate restricted threads. These are alternatives for the product decision, not selected behavior.

Cloudflare supports custom routing with server-selected instances, so a same-origin authenticated web route can select a conversation after authorization. The SDK's read-only connection flag controls writes and survives hibernation; it does not establish who the user is or whether they may read the stream. Avoid copying documentation examples that trust query-string role/user IDs. Sources: [routing](https://developers.cloudflare.com/agents/runtime/communication/routing/), [readonly connections](https://developers.cloudflare.com/agents/runtime/communication/readonly-connections/).

WebSocket connections expose state, original URI and close/send methods; connection state can help remember a verified identity reference. It cannot replace the repository's current-state checks. An outer HTTP gate protects new connections, but an already-open socket bypasses that gate for subsequent frames. Source: [WebSocket lifecycle](https://developers.cloudflare.com/agents/runtime/communication/websockets/).

Abuse and spend belong to the same design. REST currently has an assistant bucket of 20 requests per 60 seconds, keyed through the request guard. Web rate-limit bindings cover authentication only, and the assistant server function has no explicit assistant limiter. Neither model adapter sets an output-token budget or records usage. Persistent sessions need limits for turn size, total context, queued turns, parallel conversations, generation duration, reconnect traffic and per-workspace/provider spend. A reconnect should not count as a fresh inference; a recovery attempt that calls the provider must count. Sources: [rate bindings](../../infra/bindings.ts), [REST limiter](../../apps/api/src/request-guards.ts), [web ask](../../apps/web/src/lib/server/assistant.effects.ts), [provider adapters](../../packages/ai/src/openai.ts).

Keep transcript retention, prompt context, and replay-buffer retention distinct. Store bounded evidence with provenance and observation time, then reauthorize before reuse. Summaries must preserve restrictions and mark stale observations. Record actual provider/model, finish reason, usage when supplied, attempt identity and terminal status. Do not invent zero tokens or delivery success when evidence is unavailable. The current service already guarantees honest selected provider/model identity; extend that invariant across recovery and model changes. Source: [assistant contract](../../packages/ai/src/index.ts).

The logger owns one canonical event per request/service and invocation-scoped exporters. A conversation can span many invocations, so it needs correlated turn/attempt events, not one exporter held open for the conversation. Keep IDs in events/spans, low-cardinality metrics, safe terminal errors, and prompt/evidence text out of routine telemetry. Sources: [logger intent](../../packages/logger/AGENTS.md), [web observability](../../apps/web/src/lib/observability.ts).

## Deployment, local behavior and verification

Alchemy and generated Wrangler configuration share [infra/bindings.ts](../../infra/bindings.ts) and [infra/write-wrangler.ts](../../infra/write-wrangler.ts). The stack currently provisions an AI binding for web and API, but no conversation DO binding. A DO option needs a named Worker class export, namespace binding, SQLite migration, typed env support, and equivalent local configuration. Changing only generated Wrangler JSON would leave Alchemy deployment inconsistent. The specification must choose the hosting worker and access boundary; a dedicated worker adds another deployment and binding boundary. Sources: [Alchemy stack](../../alchemy.run.ts), [web Wrangler](../../apps/web/wrangler.jsonc), [API Wrangler](../../apps/api/wrangler.jsonc).

Preserve provider-light development and fixture parity. The unconfigured mock should exercise accepted history, deterministic chunks, cancellation, terminal failure and reconnection through the selected real transport. The existing mock only produces one complete answer, so current tests cannot prove the chosen outcome. Seed task behavior and Live task behavior already share contract cases; a conversation capability needs equivalent observable behavior even if storage differs. Sources: [mock](../../packages/ai/src/mock.ts), [seed/live task contract](../../packages/capabilities/src/developer-platform/webhook-investigation-tasks.contract.ts), [fixture rules](../../AGENTS.md).

Existing evidence includes provider selection and rejection tests, server authorization tests, task race/idempotency tests, mounted chat/task UI tests, and an end-to-end test that reopens an approved task after an unavailable queue. These prove useful boundaries, not stream durability. No application tests were run by this research worker. Sources: [AI tests](../../packages/ai/src/index.test.ts), [web assistant tests](../../apps/web/src/lib/server/assistant.test.ts), [task Live tests](../../packages/capabilities/src/developer-platform/webhook-investigation-tasks.live.test.ts), [assistant investigation e2e](../../apps/web/e2e/assistant-investigation.spec.ts).

## Recommendation for the next decision

Keep **custom DO + Effect** and **AIChatAgent + AI SDK inference with Effect capabilities** as the main implementation candidates. The first preserves the current model architecture and gives direct control of transport policy. The second buys a maintained chat protocol and model integrations while requiring an explicit inference ADR change. An **AIChatAgent + Effect Response bridge** is credible when retaining Effect inference is a firm requirement; require a small protocol experiment before choosing it, because it preserves custom provider work while adding another changing message schema.

Do not run Effect Chat persistence and AIChatAgent transcript persistence as independent authorities. If AIChatAgent owns history, derive each Effect prompt from its authoritative history and authorized evidence. Likewise, define one owner for admission, model/tool looping, retry and recovery, with separately bounded responsibilities. A Workflows option should own a domain process only if the product requires that process; it should not silently become a second chat recovery loop.

### Bounded experiments still needed

1. **Transport and authorization conformance.** Pin the proposed package versions, run one named conversation in the local web Worker, and prove all built-in message/history/clear/regenerate/approval paths pass the intended gate. Include reconnect and a revoked Member with an open socket. Pass criterion: no protected state escapes or mutates through a built-in path.
2. **Effect bridge feasibility, only if retained as a candidate.** Feed a deterministic Effect stream with text, metadata, explicit abort and typed failure into AIChatAgent. Disconnect before the first token and mid-answer, then reopen. Include one non-mutating tool result if tools are in scope. Pass criterion: one correctly reconstructed message, no duplicate generation, accurate terminal status, and no swallowed persistence failure.
3. **Provider contract.** Exercise the selected Workers AI and OpenAI-compatible models with assistant history, streaming, usage, cancellation and bounded output. Pass criterion: measured provider behavior matches the declared capability set and the mock; unsupported features are refused. Do not infer frontier-model support from the currently hardcoded model defaults.
4. **Deployment and lifecycle.** Verify the chosen named export survives the TanStack/Alchemy build, bindings match local configuration, and deletion during generation cannot resurrect data. Exercise a real restart separately from network loss, coordinated with the runtime report's failure cases.

These are experiments that can settle architecture uncertainty. They are not a component implementation backlog. Remaining human decisions are conversation/task relationships, visibility and authorship, concurrent-message behavior, retention/export ownership, revocation timing, approval presentation, and which inference/recovery owner to accept.
