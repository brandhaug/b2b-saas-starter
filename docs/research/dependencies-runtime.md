# Runtime dependency audit

Audited 2026-09-07 against checked-in manifests, catalog and lockfile, relevant intent nodes, architecture, and ADRs 0002, 0039, 0050, 0062 and 0068. Versions below are repository pins, not claims about the latest registry release. This is a fit assessment, not a penetration test or a complete transitive vulnerability scan.

Keep the backend's main libraries. They support the explicit requirements with little duplication. Replacing Effect, Better Auth, Drizzle, or Alchemy would rewrite working contracts without an identified starter benefit. The worthwhile changes concern React Email package consolidation, integration and stale configuration.

## Concrete findings

### Remove the stale extract-zip audit exception

`pnpm-workspace.yaml` suppresses `GHSA-jmr9-qjv8-65gv` with a comment saying Alchemy brings in `extract-zip`. The current `pnpm-lock.yaml` contains no `extract-zip` entry. Remove the suppression and rerun the package audit. This restores reporting if a later dependency reintroduces it, without changing runtime code. The advisory itself remains real; absence from this lockfile is the reason for removal. [Advisory](https://github.com/advisories/GHSA-jmr9-qjv8-65gv)

### Schedule PostHog export after HTTP response work

`packages/logger/src/wide-event.ts` awaits `runWideEventSinks` in `Effect.onExit`. `providers.ts` awaits `captureImmediate` and then `shutdown`, with a 3000 ms request timeout. Therefore configured analytics adds vendor delivery time to the request's completion. This is a code-path inference, not a measured latency claim. PostHog's Workers guide uses request-owned `waitUntil` for capture and shutdown. [Workers guide](https://posthog.com/docs/libraries/cloudflare-workers)

Keep PostHog and give the HTTP integration a request-owned background scheduler. Pass the completed immutable event to that scheduler, while keeping console logging and Effect span completion where they are. Preserve awaited behavior for tests and queue/cron scopes unless their lifecycle explicitly supplies the same guarantee. Test that a held export promise does not hold the HTTP response, that the runtime owns the outstanding work, and that missing credentials send nothing. Medium cost, because the existing per-invocation lifetime must remain intact.

The server uses `traceId` as PostHog `distinctId`, so these events represent request telemetry rather than a user's product journey. Keep correlation identity separate from user identity when adding product analytics. Changing that policy needs an explicit identity decision.

### Keep the OAuth declaration patch until upstream types replace it

`patches/@better-auth__oauth-provider@1.7.2.patch` changes only `.d.mts` declarations, removing inferred optional properties whose type is `undefined`. It does not modify authentication runtime behavior. A future Better Auth upgrade should attempt removal and run typecheck plus auth/OAuth tests. Replacing the auth stack to avoid this patch has far higher cost than the patch itself. Do not assert the patch is obsolete without testing the replacement release.

### Review MCP revision support as an explicit feature decision

The API serves and tests session-based `2025-11-25`; a test offers `2026-07-28` and expects negotiation back to the served version. Auth independently uses CIMD profile `mcp-2026-07-28`. Better Auth's current guide describes the newer stateless protocol and an official SDK handler. These are separate transport and auth choices. A client that requires the newer transport will not gain support from updating the auth plugin alone. [MCP guide](https://better-auth.com/docs/plugins/mcp)

Prefer checking Effect's transport support and upgrading within the existing capability projection when newer-client compatibility becomes required. Adopting a second MCP SDK now would require rebuilding typed tools, resource projections, caller propagation and transport tests. High cost. The present evidence establishes a compatibility limit, not a reason to discard Effect.

The custom CIMD transport also deserves a focused contract review. Better Auth requires resolving once, rejecting special-use addresses, pinning the approved address and refusing redirects. `apps/web/src/lib/server/client-metadata-fetch.ts` rejects URL literals/suffixes and redirects but delegates DNS/connect behavior to Workers fetch. Its comment claims platform equivalence; this audit did not establish all four guarantees from Cloudflare documentation. Keep the plugin, but verify that transport claim before expanding arbitrary discovered clients. A Node-only replacement is unsuitable. [CIMD contract](https://better-auth.com/docs/plugins/cimd)

### Do not replace application OTLP export with native Workers export yet

Cloudflare can export logs and traces to OTLP destinations, making this a credible future simplification. Its current documentation explicitly excludes metrics export. The repository exports request counters and duration histograms through Effect, so a full replacement loses a promised signal. Cloudflare's PostHog destination also exports logs rather than the custom captured analytics events used here. Keep the current seam. Revisit when native export can preserve all three signals and their trace relationships. [Native export limitations](https://developers.cloudflare.com/workers/observability/exporting-opentelemetry-data/), [PostHog destination](https://developers.cloudflare.com/workers/observability/exporting-opentelemetry-data/posthog/)

### Preserve the D1 batch boundary

`packages/db/src/service.ts` uses Drizzle builders' `toSQL()` with `RawD1.batch` because the installed Effect driver lacks a batch API. Cloudflare documents transactional execution for D1 batches. This small local adapter preserves atomicity and does not justify replacing Drizzle. A future driver batch API is useful only if it preserves atomic commit/rollback behavior, parameter encoding and failure mapping. [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/)

### Restore TanStack's server-function CSRF middleware

E2E logs reported TanStack's missing-CSRF-middleware warning. Source inspection confirms an integration gap. Before this audit, `apps/web/src/start.ts` defined a custom `startInstance` with config, maintenance, observability and locale middleware, but no CSRF middleware. Installed `@tanstack/start-server-core` 1.169.31, in `createStartHandler.ts`, installs its default CSRF middleware only when there is no custom start instance. The warning detects the built-in middleware marker, so the warning alone would not exclude equivalent custom protection. No equivalent origin or Fetch Metadata validation was found in this application's request middleware or session gate.

Better Auth's `trustedOrigins` configuration protects its own auth handling; it does not establish a global guard for TanStack capability mutations. For example, the POST `createApiTokenServerFn` calls `requireRequestSession()` and then the capability with permission checks. The session helper reads `auth.api.getSession` using request headers, but does not validate the incoming request's origin. Authentication and permission checks remain present; the missing check concerns whether the browser request came from the application origin.

The migration registers TanStack Start's existing `createCsrfMiddleware({ filter: (ctx) => ctx.handlerType === 'serverFn' })` in `requestMiddleware`. The filter leaves auth callbacks and other server routes under their existing handling. TanStack explicitly requires this registration for custom `src/start.ts` files and documents same-origin verification using Fetch Metadata, Origin or Referer, rejecting requests without those checks by default. [Server-function protection](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions)

This is a confirmed missing defense, not a demonstrated exploit. Browser cookie behavior, request encoding and deployment policy affect exploitability. The fix adds no dependency. Five focused tests pass against the configured middleware: same-origin success, cross-origin POST and GET rejection, missing-metadata rejection, and router bypass. Web typechecking passes. See the main audit for production build and browser results. No exploit against a deployed environment was attempted.

## Validation limits

This assessment inspected manifests, the lockfile, source use sites, relevant tests and primary documentation. The React Email migration above reflects the resulting implementation. See the [main dependency audit](./dependency-audit.md#validation) for integrated validation results and their limits. Replacing the main backend frameworks is not justified by the evidence gathered here.
