# Starter security checklist

Use this checklist before customer use and after changes to data flows or security
controls. It covers ordinary B2B personal data and Workspace data under the
repository's security baseline.
Sensitive-sector and children's data require a separate assessment.

## How to record an assessment

Implementation means code or a procedure exists in this repository. Deployment
verification means an operator observed the behavior on a named deployment and
revision. Operator-owned work includes provider configuration, access reviews,
contracts, incident handling, and evidence custody. An implementation link or a
passing local test does not establish deployed behavior or operating effectiveness.

Keep a private, ordinary record for each applicable row: date, owner, deployment
and revision, result, evidence link, and remaining action. Leave untested rows
unverified; explain why a row is not applicable. Do not put credentials, customer
payloads, or unrestricted evidence links in this repository. No control registry,
evidence ingestion service, or automated evidence expiry is needed.

This checklist does not certify an organization or establish GDPR compliance.
Adopters own legal assessment, certification or assurance engagements, and proof
that controls operated effectively over the assessment period. For orientation,
use [AICPA's SOC resources](https://www.aicpa-cima.com/resources/landing/system-and-organization-controls-soc-suite-of-services)
for SOC 2, [ISO/IEC 27001:2022](https://www.iso.org/standard/27001) for an information
security management system, and the [European Commission's GDPR guidance for organizations](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations_en).
These sources do not turn the rows below into an exhaustive standards mapping.

## Provider and region register

Use this table as the deployment's provider worksheet. An unset optional provider
is inactive, remains marked inactive in the worksheet, and needs no configuration.
The operator must fill in the actual account, endpoint, region, retention setting,
legal role and transfer mechanism for every enabled row. These are operational
inputs, not legal conclusions. The served privacy notice is [`/privacy`](../apps/web/src/routes/privacy.tsx),
with its English template in [`packages/i18n/messages/public/en.json`](../packages/i18n/messages/public/en.json).
Adapt both to the enabled rows and the operator's legal decisions. The [optional-provider
guide](../apps/web/content/docs/getting-started/optional-providers.mdx),
[retention policy](retention.md), [backup runbook](backup-recovery.md), and
[monitoring runbook](monitoring.md) describe the implementation details. The
operator also supplies the legal entity and contact, purposes and lawful bases,
rights contact and handling process, retention periods, recipients, regions,
transfer safeguards and effective date for the final notice.

Cloudflare D1 chooses a primary location automatically unless the operator sets a
location hint or jurisdiction when creating the database. Workers code, secrets,
Queues, Cron and vendor telemetry can still be global, so a D1 location is not an
EU-only processing claim. Record the chosen Cloudflare settings and all outbound
endpoints here. See [Cloudflare data location](https://developers.cloudflare.com/d1/configuration/data-location/)
and [Workers data localization](https://developers.cloudflare.com/data-localization/how-to/workers/).

Review this register when a provider, endpoint, region, data category, retention
setting, contract or transfer mechanism changes. A provider row with unknown
operator inputs remains unverified until those values are recorded.

All three Workers share one D1 database. Workspace isolation is logical,
implemented through membership, permission and ownership checks; there is no
separate database or independent recovery boundary per Workspace. Privileged
infrastructure access crosses that logical boundary. Restoring D1 affects the
whole service and can resurrect deleted data or revoked credentials. Follow the
[service closure and reopening procedure](operations.md#choose-the-recovery-action),
including queues, independent security evidence and external-state reconciliation.
A SQL restore alone does not recover R2 artifacts, provider state or delivered mail.
