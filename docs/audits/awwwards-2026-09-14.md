# Web app review against the AWWWARDS design brief

Reviewed 14 September 2026. Method: independent design assessment by `/root/design_review`, independent detector/browser assessment by `/root/technical_review`, and a primary-agent workspace/account inspection. No UI code changed.

The implementation has a credible engineering identity and a good usability foundation. It does not meet the requested cinematic design brief. The strongest existing material is the actual workspace, architecture trace, runnable commands, and honest provider states. A redesign should make that material more compelling.

The two highest-priority findings are a broken copyable setup sequence and mobile hero headings exceeding the brief's line limit. The remaining findings concern composition, navigation density, discovery, and asset delivery.

## Coverage and limits

Current-checkout browser evidence used localhost:3187, with localhost:3188 configured for credential authentication. The service already on :3071 belonged to an obsolete worktree; its screenshots were discarded.

- Public homepage, pricing, docs index, quickstart article, and sign-in at 1440×1000 and 390×844.
- English and Norwegian homepage at 320px; Norwegian also at 390px. Narrow sign-in and reduced-motion checks.
- Workspace overview, members, API tokens, webhooks, audit, billing, settings, assistant, and notifications through the real preview components. Eight detail pages captured at both 1440px and 390px, all with document width equal to viewport width.
- Member invitation dialog inspected without submission. Local seeded member sign-in succeeded; account settings were inspected in the browser and source. Workspace route source inspected; privileged admin and enrolled-factor flows were not exercised.
- Source review across navigation, typography, tokens, motion, public layouts, authentication, workspace components, account, and admin composition.

This is a design and implementation review, not a complete accessibility certification, production performance benchmark, security audit, or exhaustive mutation-flow test. Preview screenshots represent fixtures, not live persisted behavior. No production Lighthouse numbers or full screen-reader journey are claimed.

## Prioritized findings

### P1: The final setup action copies an incomplete sequence

[ClosingSection](../../apps/web/src/components/landing/closing-section.tsx#L16) builds `git clone … && vp install …` without entering the cloned directory. Installation therefore runs in the caller's old directory. [SETUP_STEPS](../../apps/web/src/lib/toolchain.ts#L17) also omits environment preparation shown in the [quickstart](../../apps/web/content/docs/getting-started/quickstart.mdx#L14).

This breaks the repository's main conversion action. Include the directory change and documented environment preparation in the canonical sequence, then derive the displayed command count from it. Verify the copy result against a clean-directory walkthrough. Suggested follow-up: `impeccable harden`.

### P1 under the brief: Mobile hero wrapping violates the line limit

[HeroSection](../../apps/web/src/components/landing/hero-section.tsx#L41) uses 48px mobile display type with a 51.84px line height. At 320px the content width is only 288px. English becomes four lines. The longer [Norwegian headline](../../packages/i18n/messages/web/nb.json#L173) becomes four lines at 390px and five at 320px, pushing the CTAs toward the bottom of the first viewport.

Use fluid mobile type and deliberate headline lengths in both locales. Verify rendered lines at 320px, 390px, tablet, and desktop. A `max-w-5xl` class cannot guarantee this result on a narrow screen. Suggested follow-up: `impeccable typeset`, then `impeccable adapt`.

[Evidence: Norwegian mobile hero](awwwards-2026-09-14/hero-nb-mobile.png).

### P2: The public page lacks the composition and motion requested

The [hero grid](../../apps/web/src/components/landing/hero-section.tsx#L33) gives a large right-hand column to four bottom-aligned command lines, leaving its upper area empty. The [request trace](../../apps/web/src/components/landing/request-trace-section.tsx#L189) then repeats code panels beside a small schematic across a long scroll. On mobile the schematic precedes the trace instead of accompanying each stage. The sampled homepage was approximately 7,480px tall on desktop and 8,506px on mobile.

Use the real workspace and architecture as larger visual subjects. Condense repeated code behind explicit choices, vary section composition, and build the requested motion into a shorter narrative. The [preview image](../../apps/web/src/components/landing/demo-strip.tsx#L48) also needs a deliberate hover/focus response if adopting the brief. Preserve reduced-motion access using [GSAP matchMedia](https://gsap.com/docs/v3/GSAP/gsap.matchMedia%28%29/). Suggested follow-up: `impeccable layout`, `impeccable animate`.

Do not invent customer testimonials or partner adoption claims. The project has no production users. Generic seeded photography would satisfy an asset-source instruction but would offer weaker evidence than authored product imagery.

### P2: The docs index duplicates navigation and stretches sparse cards

The [docs index](../../apps/web/src/routes/_knowledge.docs.index.tsx#L37) repeats the article inventory already in the [sidebar](../../apps/web/src/routes/_knowledge.tsx#L107). Governance has nine articles while two adjacent categories have three, stretching their cards to leave large empty lower areas.

Use content-sized category lists and a prominent Quickstart entry. This is wasted space inside occupied cells; `grid-flow-dense` will not fix equal-height stretching. Suggested follow-up: `impeccable distill`, `impeccable layout`.

[Evidence: docs index](awwwards-2026-09-14/docs-desktop.png).

### P2: Mobile workspace controls delay the records

At 390px the preview banner, heading, action row, search, and wrapped field filters place the first API-token identity near y=600. The webhook record starts around y=660. The controls remain readable and contained, but a visitor spends most of the first screen getting past navigation and filters for a two-record fixture.

[DeveloperListToolbar](../../apps/web/src/components/developer-list-controls.tsx#L25) renders every field control. Keep search visible, group secondary filters behind a labeled control with an active count, and tighten the preview banner. Preserve direct access to selected filters and sorting. Suggested follow-up: `impeccable adapt`.

[Evidence: mobile API tokens](awwwards-2026-09-14/tokens-mobile.png).

### P2: Sign-in makes evaluation harder than necessary

[Sign-in](../../apps/web/src/components/auth/sign-in-page.tsx#L472) exposes password, passkey, email-link and email-code paths alongside recovery, demo credentials, and registration. On mobile these consume several rows. The [demo credential disclosure](../../apps/web/src/components/auth/demo-credentials-footer.tsx#L36) presents text that evaluators must transfer into the form.

Keep a clearly dominant sign-in path and group secondary methods. Add explicit owner/member fill actions inside the demo disclosure. Preserve the existing validation and password-manager affordances. Suggested follow-up: `impeccable onboard`.

### P2: The disabled assistant is a dead end in the preview

The preview assistant shows only "Not enabled" and "Chat is not enabled for this workspace." The [unavailable branch](../../apps/web/src/components/workspace-assistant-page.tsx#L230) supplies no explanatory next step. Most of the page remains empty, and visitors cannot inspect what the advertised assistant does.

Add a contextual setup/documentation link and clearly labeled example evidence or an explanation of the available investigation workflow. Keep provider availability honest. Suggested follow-up: `impeccable onboard`.

[Evidence: assistant preview](awwwards-2026-09-14/assistant-desktop.png).

### P2: A 405 KB logo is delivered for a 40px mark

The shared PNG is 1254×1254 and 405,358 bytes, rendered at 40×40 by [public navigation](../../apps/web/src/components/public-layout.tsx#L121) and the [auth shell](../../apps/web/src/components/auth/auth-shell.tsx#L23). This is unnecessary cold-load image payload across entry pages.

Use a faithful vector or appropriately sized raster assets with density variants. Keep the existing intrinsic dimensions to prevent layout shifts. Suggested follow-up: `impeccable optimize`.

The design is coherent and recognizably about this repository. Its real architecture, sample prices, and provider states support trust. Workspace navigation groups administration and developer tools clearly. Tables/code scroll within bounded regions. Main mobile controls are 44px tall and auth inputs use 16px type. In the sampled text there was no verified invisible CTA or contrast failure. Reduced-motion emulation produced zero homepage CSS animations, and shader source handles offscreen and hidden-document suspension.

The remaining mobile touch exceptions are FAQ triggers at about 42px, footer links at 40px, and the 40px logo. Bring them to the repo's 44px target during polish. These sizes alone do not establish an AA violation; [WCAG 2.2](https://www.w3.org/TR/WCAG22/) defines a 24px minimum with exceptions, while the repo sets a stronger local target.

A skeptical developer gets useful proof but hits the incomplete setup command at the decisive action. A first-time evaluator faces too many authentication choices. A mobile operator gets readable controls but sees too little record content in the first viewport. The homepage's strongest moment is the real workspace preview; the extended code trace is where momentum drops.

## Detector interpretation

The static detector scanned 247 markup files within `apps/web/src` and returned `[]`, exit 0. Runtime overlay checks ran on homepage, demo, pricing, and quickstart. Their candidate counts were 53, 8, 7, and 11 respectively. These are heuristic candidates, not accepted defects.

Verified false positives included intentionally screen-reader-only architecture text flagged as overflow, flex-centered controls flagged for missing padding, approved source-path microtype, semantic mauve syntax highlighting, notification list borders classified as nested cards, hidden details-menu descendants flagged as occluded, and gradients/shapes from development tools. No missing bento corner was verified. No production bundle or performance claim follows from the detector.

Recommended order: correct setup instructions and hero wrapping; improve public composition and mobile record density; simplify docs/auth discovery; improve the assistant unavailable state and logo delivery; finish with `impeccable polish`.
