# Client-only vendor graphs stay out of the web Worker's server bundle

The web Worker's deploy bundle is the Vite SSR environment's output uploaded verbatim: `Cloudflare.Website.Vite` runs the build (alchemy injects the Cloudflare Vite plugin), collects every emitted `dist/server` chunk, and uploads them as the Worker's modules. In that deploy build the Cloudflare plugin sets `resolve.noExternal: true` for the server environment — workerd cannot resolve bare module specifiers at runtime, so every node_module the server graph can reach is bundled into the upload. A `pnpm -C apps/web build` run does not show this: the standalone build externalizes node_modules, so its `dist/server` (~2.9 MB) is not what deploys; the deploy-shaped output was ~10.5 MB, past the 10 MiB Workers upload limit (the same build first hit the free tier's smaller limit, which is why `vite.config.ts` sets `build: { minify: true }` for every environment).

Minification was never the whole story: the bundle was already minified, and ~2.5 MB of it was better-auth's server stack (SAML, passkeys, webauthn crypto) that the product genuinely executes. The dead weight was **client-only code the server could reach but never runs**. `MdxMermaid` renders an empty `<figure>` on the server and renders mermaid in a `useEffect`; `ClientTelemetry` renders nothing and initializes browser SDKs in a `useEffect`. Both sat behind dynamic imports (`await import('mermaid')`, `await import('posthog-js')`, `await import('@sentry/react')`), so their vendor graphs were emitted as lazy chunks into `dist/server` — mermaid with cytoscape, katex, and its posthog-js telemetry dependency (~2.7 MB) — uploaded to the Worker, never executed there, and re-downloaded by browsers from the client bundle they were already in. The decision: **a dynamic import of a browser-only package that is reachable from the server graph must sit behind TanStack Start's `createClientOnlyFn(loader)`, whose compile-time transform replaces the whole call — loader argument included — with a stub in the server environment** — the import never enters the server module graph, so its chunks are never emitted. The helper is identity-typed (`<TFn>(fn: TFn) => TFn`), so callers keep the real module types with no absence guards, and untransformed contexts (Vitest, Storybook) run its identity runtime stub. The server stub throws if called, which is the honest failure: these loaders run only inside `useEffect`, which never executes during SSR, and a future call site that did run server-side should fail loudly, not return `undefined`. This is how `mdx-mermaid.tsx` and `client-telemetry.tsx` load mermaid, `posthog-js`, and `@sentry/react` today, and it took the deploy-shaped bundle from ~10.5 MB to ~6.5 MB — well under the limit with the auth stack intact.

The alternatives: post-build minification of `dist/server` between `vite build` and `alchemy deploy` (shrinks bytes but ships the same dead modules, and alchemy's `Website.Vite` runs the build itself, so the step needs a custom hook in the deploy path); keeping the imports and asking Cloudflare's bundler to tree-shake (dynamic imports are live by definition); or guarding the imports with `import.meta.env.SSR` (a define swap inside a nested function — rolldown still bundles the import). Stubbing mermaid out of SSR entirely was unnecessary: the SSR figure was always empty, so behaviour is unchanged by construction.

**The rule going forward:** when a client-only package joins the app, its dynamic import goes behind `createClientOnlyFn` (the `react-doctor/prefer-dynamic-import` and `effect/noDynamicImports` lint rules keep the import bound to a named loader). The call must stay a literal `createClientOnlyFn(...)` in the component's module — the compiler detects the pattern lexically, so a shared `clientOnly()` wrapper would leave the wrapped import untransformed in the server graph and reintroduce the leak. The deploy bundle is checked by reading the `Uploading worker (X MB)` line in the deploy log — or locally by hashing `apps/web/dist/server` the way the build does. The `assert-client-boundary.mjs` check guards the mirror-image leak (server-only modules into `dist/client`); this decision covers the other direction, which no automated check catches yet.
