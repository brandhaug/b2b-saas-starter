# OAuth 2.1 for interactive MCP clients, beside API Tokens

MCP clients that a person operates — Claude, Cursor, and their kind — connect to the API worker's `POST /mcp` through OAuth 2.1, and scripts and CI keep connecting with a workspace API Token (ADR 0026). Both credentials open the same route and reach the same capability layer; neither replaces the other.

## Why both

An API Token is a workspace-owned machine credential: an owner or admin mints it, scopes it, and it outlives any one person's session. That is exactly right for a deploy pipeline and exactly wrong for a person sitting in Claude: pasting a long-lived admin-minted secret into a desktop app hands the workspace's security posture to whichever laptop the app runs on, and the audit trail then names a token, not a Member. The MCP specification (2026-07-28) expects the interactive case to be OAuth: the client discovers the authorization server from the resource's protected-resource metadata, identifies itself through a Client ID Metadata Document, and the person signs in and consents in a browser. Removing tokens in favour of OAuth would break the non-interactive case, where no browser exists to consent in.

## What the starter does

- **Authorization server: the web worker**, through `@better-auth/mcp` (the OAuth 2.1 provider configured for MCP) with the `jwt` plugin for signing keys (`/api/auth/jwks`) and `@better-auth/cimd` for client discovery. The provider's tables ride the shared D1 schema as plugin-owned tables (`packages/db`). The resource identifier every access token is audience-bound to is the API worker's `/mcp` URL, from `MCP_RESOURCE_URL`; locally it defaults to the API dev server.
- **Resource server: the API worker.** `POST /mcp` accepts a Bearer JWT beside an API Token, telling them apart by shape. A JWT is verified against the issuer's JWKS with jose (signature, `iss` = `MCP_OAUTH_ISSUER`, `aud` = `MCP_RESOURCE_URL`, expiry), then its starter claims are mapped onto the same `WorkspaceContext` the token path builds — with an actor this time, resolved from the membership table on every call. The worker serves the RFC 9728 protected-resource metadata and answers an unauthenticated `/mcp` with the `WWW-Authenticate` challenge that points at it. Both env vars unset means the OAuth path is inactive and `/mcp` takes API Tokens only, like every other optional provider. REST routes stay token-only: OAuth is for the interactive surface.
- **One workspace per consent.** The consent page at `/oauth/consent` makes the user pick exactly one Workspace and shows the requested scopes. The pick becomes the consent's reference id through the provider's post-login mechanism: the consent page is both the post-login and the consent hop, and the consent server function vouches for the pick with a header the provider's `shouldRedirect` requires, so a browser-initiated authorization can never skip the picker on the strength of a stale `session.activeOrganizationId`. This is the one place the starter reads that session field, and it reads it only as the plugin's own hand-off channel — the invariant that routes resolve the workspace from the URL slug stands.
- **Claims name the workspace; the role is re-resolved.** The access token carries `starter_workspace_id`, `starter_workspace_slug`, and `starter_workspace_role` (contract in `packages/authz/src/mcp-access-token.ts`), plus the OAuth `scope`, which must include `mcp:read`. The API worker authorizes each tool call as the Member's current role from the membership table, not as the role claim, so a removed member is refused and a role change applies on the next call. Role-derived API-token scopes were considered as the claim and rejected: the three token scopes do not map one-to-one onto the three workspace roles, and a session in the web app and a Claude session must reach the same `authorize()` decision.
- **Connections are a capability.** `McpClientConnections` (`packages/capabilities/src/developer-platform/`) lists a user's consents with their client and workspace, revokes one — deleting the consent and revoking the refresh and access tokens it minted, which the provider's own delete-consent endpoint does not — and records `mcp_client.consent_granted` / `mcp_client.consent_revoked` Audit Events. Seed and Live adapters, per ADR 0044. The account page lists connected clients with revoke.
- **DPoP is not implemented on the resource server.** Neither the resource nor any client requires it; a token carrying a `cnf` claim is refused rather than accepted as a bare bearer.

## Trade-offs accepted

- The Client ID Metadata Document transport on Workers cannot pin DNS answers; it refuses non-HTTPS, IP-literal and non-public hosts and never follows redirects, and leaves address resolution to the Workers runtime.
- The consent's audit row cannot join the provider's consent write in one batch (the write is an HTTP-shaped call) — the ADR 0051 trade, again. Revocation is one batch.
- `@better-auth/oauth-provider`'s type declarations are patched (`patches/`) to drop `?: undefined` members that the repository's `exactOptionalPropertyTypes` rejects; remove the patch when upstream fixes it.
