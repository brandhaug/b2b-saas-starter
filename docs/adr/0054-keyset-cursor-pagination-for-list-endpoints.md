# Keyset cursor pagination for list endpoints

Every REST list endpoint on the `StarterApi` contract (`members`, `notifications`, `api-tokens`, `webhooks`, `audit-events`) accepts optional `cursor` and `limit` query parameters and answers `{ items, nextCursor }`. `limit` defaults to 50 and is capped at 200; `nextCursor` is `null` on the last page. The MCP list tools take the same two inputs, because they are derived from the same operation table as the REST routes (`apps/api/src/operations.ts`), so the two Capability Interfaces cannot page differently.

The cursor is a keyset position, not an offset: the sort key of the last item on the page plus its id as the tie-break, base64-encoded as `"<key> <id>"`. A page request returns rows strictly after that position in the endpoint's documented order, so rows inserted between two page fetches never shift, duplicate, or hide rows the caller has not yet seen. Offset pagination was rejected for exactly that reason. Timestamped lists (notifications, API tokens, audit events) sort newest first on `(createdAt DESC, id DESC)`; lists whose wire shape carries no timestamp (members, webhook endpoints) sort on `id ASC`. The cursor is opaque to clients. It carries no signature, and decoding a malformed one yields an empty page rather than an error, because a cursor addresses a position and a nonsense position holds nothing.

The codec, the limit clamp, the `Page<T>` shape, and the page-building helper live in one module, `packages/capabilities/src/internal/keyset-cursor.ts`, exported as `@b2b-saas-starter/capabilities/internal/keyset-cursor`. The audit page in the web app used a private copy of this codec first; that copy was moved rather than duplicated so the capabilities, the web app, and the API worker share one encoding. Each list capability exposes a paged read (`listPage`, `listMembersPage`, or `list` with `cursor`/`limit` for the audit log) implemented by both the Seed and the Live adapter, and the contract tests walk pages against both adapters with an insert between fetches (ADR 0044's invariant 4). The unpaged reads stay for the web app's server functions, which render whole collections that are small by construction.
