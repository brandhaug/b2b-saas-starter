# Notification email over a queue, with a daily digest cron

A Notification reaches a user by email on one of three channels the user picks per Notification kind: `off`, `instant`, or `digest`. Security kinds (`api_token.created`, `api_token.revoked`, `workspace_member.role_changed`, `two_factor.changed`, `account.impersonated`) default to `instant`; every other kind defaults to `digest`. The defaults live in code (`defaultChannelFor` in `packages/capabilities/src/notifications/notification-kinds.ts`), and `notification_preferences` stores only what a user changed, so a new kind gets its default without a backfill. The kind itself is a stored column on `notifications` (`kind`, defaulting to `announcement` for rows written before it existed) — one vocabulary in `packages/db/src/enums.ts`, lifted into `Schema.Literals` for server-function inputs and queue messages.

**Instant emails ride a second Cloudflare Queue, `b2b-saas-starter-notification-emails`, not the webhook queue and not the request path.** `NotificationFeed.create` persists the row, resolves who can see it (the target user, or every member for a broadcast), and enqueues one `NotificationEmailQueueMessage` per recipient whose channel for the kind is `instant`. The message carries ids only — `notificationId`, `recipientUserId`, and the producer's `traceparent`. The background worker's consumer re-reads the Notification, the recipient's address, and the recipient's current preference at send time, so a preference changed between enqueue and delivery is honoured and no address or body sits in the queue. A Notification that was read in the meantime, or that the recipient can no longer see, is acked without an email. Rendering and sending go through `EmailDispatcher` from `packages/email` with one React Email template per kind over the shared layout; without an `EMAIL` binding the dispatcher logs, exactly as the invitation and account-lifecycle emails do. The queue is declared once in `infra/bindings.ts` beside the webhook queue, so alchemy and the generated `wrangler.jsonc` files agree on the name, the consumer settings, and which workers produce onto it (web, api, background) and which one consumes (background). It has no dead-letter queue on purpose: after three failed sends the message is dropped, and the recipient still has the Notification in the feed and, when they take the kind as digest, in the next digest.

The enqueue is best-effort, mirroring `WebhookPublisher`: without a `NOTIFICATION_EMAIL_QUEUE` binding nothing is enqueued and `create` still succeeds, and a queue rejection annotates the wide event instead of failing the producer. The Notification row is the durable record; email is a projection of it. This keeps local development provider-light (CLAUDE.md rule 3) and keeps a queue outage from turning a settled webhook delivery into a retry loop — the background worker is itself a producer, creating a `webhook.delivery_failed` broadcast when a delivery is rejected or dead-lettered.

**The digest is a Cloudflare cron trigger on the background worker, `0 8 * * *` (08:00 UTC), not a queue and not a Durable Object alarm.** One `scheduled` invocation per day reads `Clock`, cuts the window `[now − 24h, now)`, asks `NotificationFeed.listDigestCandidates` for every unread (Notification, recipient) pair inside it — a broadcast appears once per member — resolves each recipient's preferences once, keeps the pairs whose kind the recipient takes as `digest`, and sends one `NotificationDigestEmail` per recipient with at least one item. The grouping is a pure function (`buildDigests`) over the candidates and a channel resolver, so it is tested with fixed rows and a frozen `TestClock`. A failed send is counted on the `notification_digest` wide event and not retried inside the run: tomorrow's digest is the retry. Sends are counted, never fatal, so a run that fails its reads sent nothing — the scheduled entry retries the run twice with jitter before letting the invocation reject, and a final failure is recorded by the platform rather than swallowed. The schedule is the `notificationDigestCron` constant in `infra/bindings.ts`, read by alchemy (`crons`) and by the wrangler generator (`triggers.crons`). Unread is the digest's only inclusion rule — a Notification read in the app before 08:00 is not re-sent — and there is no per-recipient "last digest" watermark, because a fixed daily window over unread rows needs none.

Links in every notification email point at the web app. The background worker reads the origin from `BETTER_AUTH_URL`, which alchemy already holds for the web worker and now forwards to the background worker too, rather than introducing a second name for the same value; the generated `wrangler.jsonc` pins the dev-server origin for local runs. Every email carries an unsubscribe link to `/account/notifications?kind=<kind>`, a signed-in page with that kind's row highlighted. It is deliberately not a one-click endpoint: the link carries no token and no user id, so a forwarded or leaked email cannot change anybody's preference, and the same page is the preferences section of `/account`. A preference change records a `notification_preference.changed` Audit Event against the user.

The alternatives were sending instant emails inline from the request that created the Notification (couples a mutation's latency and failure mode to an email provider, and puts the fan-out on every surface separately), reusing the webhook queue with a discriminated message (two consumers with different retry ladders and different failure semantics on one queue), and a Durable Object alarm per user for the digest (ADR 0009 defers Durable Objects without a coordination need, and a daily window over unread rows has none).
