# Separate operator and merchant authentication realms

The Operations App authenticates System Operators with its own Better Auth session contract and host-only cookie, while sharing the platform's Better Auth persistence model. Operator Sessions never become Merchant App sessions through cookie or domain sharing. Impersonation instead uses an explicit, audited handoff that creates a temporary Merchant App session with the initiating System Operator recorded as provenance; this preserves the Merchant App's host-only credential boundary at the cost of a dedicated cross-application handoff. Only Merchant Members are eligible impersonation targets; System Operators and Customer Accounts remain outside this capability. Impersonation also requires a dedicated `merchant:impersonate` Operator Permission rather than following automatically from Operations App access or a broad Better Auth role. A non-empty Impersonation Reason is required before the handoff and is stored with the start event; an external support reference is optional and neither field grants authority. An Impersonated Merchant Session has a one-hour absolute lifetime, matching Better Auth's default duration but allowing no sliding refresh or extension; continuing afterward requires a new reason and fresh TOTP verification. Each System Operator and each target Merchant Member may participate in at most one active impersonation at a time; overlapping attempts are rejected. Every protected request authoritatively rechecks that the operator is enabled, remains 2FA-enrolled, and still holds `merchant:impersonate`, that the target is enabled and remains a member of the same Merchant, and that neither identity's security state has been revoked; failure immediately terminates impersonation. While it is active, every Merchant App screen displays a persistent, non-dismissible banner naming the target Merchant Member and Merchant, identifying that a System Operator is acting, showing remaining time, and providing a prominent stop action. Its authority is deliberately narrower than the target Merchant Member's: identity and security changes, MFA management, identity deletion, Merchant ownership changes, creation or rotation of long-lived credentials, monetary movements, changes to payout or billing destinations, destructive entity deletion, and bulk data wipes are always denied. Operators may inspect financial state, while consequential financial or destructive mutations use separately permissioned and audited Operations App workflows. Reversible Merchant operations such as service or schedule edits remain available and retain operator provenance. System Operators are provisioned only through controlled invitation or bootstrap paths; the Operations App has no public or self-service registration, and Merchant authority cannot grant operator access. The first System Operator is granted access by an idempotent Bun bootstrap script that targets an existing verified email, changes no Merchant membership, records a global audit event, and requires an explicit production flag for remote use. Operator identities are disjoint from Merchant Members and Customer Accounts: operator provisioning rejects existing product identities, and Merchant onboarding rejects operator identities, preventing self-impersonation and cross-surface credential confusion.
