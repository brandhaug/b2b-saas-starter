# Derived workspace onboarding checklist

The workspace dashboard shows an onboarding checklist whose steps are computed from live capability state on every read, never from stored per-step flags. The `workspaceProgress` projection in `packages/capabilities/src/workspace-projections.ts` asks the owning capability for each step — Workspace Membership for "invite a Member" (more than one member), API Token Registry for "create an API Token", Webhook Endpoints for "add a Webhook Endpoint", Billing for "choose a plan" (present only when `Billing.configured` is true, complete when the plan is not the free one) — and the small `workspace-onboarding` governance capability for the two facts nothing else serves: whether the acting user's account has two-factor enabled, and whether the workspace dismissed the checklist. A stored "done" flag would drift the moment the last token is revoked; a derived step reopens instead, and there is no second source of truth to migrate or backfill.

The one thing persisted is the dismissal, an additive nullable `workspaces.onboardingDismissedAt` column. It is starter-owned and read or written only by the capability, so it deliberately carries no `additionalFields` entry on the organization plugin: nothing returned through a plugin endpoint needs it. Dismissing is a workspace-level decision, so it is a permission (`onboarding:dismiss`, held by owner and admin, not member) enforced by `requireWorkspacePermission` in the web server function and recorded as a `workspace.onboarding_dismissed` Audit Event in the same D1 batch as the column update. Members see the checklist read-only.

The projection covers more than one permission, which the capabilities intent node otherwise forbids, so it takes the decision as an argument instead of making it: `workspaceProgress({ developerPlatform })`. The dashboard loader computes `developerPlatform` from the actor's `apiToken:list` and `webhook:list` permissions with the same pure `authorize()` behind `whenPermitted`; when it is `false` the token and endpoint reads never run and those two steps are absent from the payload, not hidden in the markup. A member's checklist therefore lists the steps their role may know about, and a Capability Interface that serves the projection later makes the same call at its own boundary.
