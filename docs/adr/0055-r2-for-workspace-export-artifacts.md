# R2 for workspace export artifacts

An owner can request a Workspace Export: a ZIP of the workspace's members, invitations, API Token metadata, Webhook Endpoints with their deliveries, Audit Events, Notifications, and the workspace record, with a `README.txt` describing every file. The request writes a `pending` row to `workspace_exports`, records `workspace.export_requested`, and enqueues a job on a dedicated Cloudflare Queue (`b2b-saas-starter-workspace-exports`). The background worker builds the archive through the same capability services the app renders from, so the export can never show a field the UI hides (signing secrets, token hashes, raw audit metadata), writes it to an R2 bucket, marks the row `ready`, records `workspace.export_completed`, and creates a Notification for the requester.

This is the starter's one carve-out from ADR 0028. The bucket holds export artifacts only: no user uploads, no general file storage, no public access. A lifecycle rule deletes every object seven days after it is written (`WORKSPACE_EXPORT_RETENTION_DAYS` in `infra/bindings.ts`), and the export row carries the same horizon as `expiresAt`, so the UI and the bucket agree on when a link stops working. Alchemy provisions the bucket, the queue, and their bindings on all three workers only when `WORKSPACE_EXPORT_BUCKET` is set at deploy time. Without it the `WorkspaceExports` capability reports unavailable and workspace settings explains why instead of offering a button; the Seed adapter builds the same archive in memory, so local development and tests need neither R2 nor a queue.

Downloads never expose the bucket. The API worker serves `GET /exports/:exportId/download?expires=…&signature=…`, a public route whose credential is an HMAC-SHA256 over `"<exportId>.<expires>"` with a per-export secret stored on the row. Both workers share only the D1 row, so no cross-worker signing secret exists and a leaked link is good for one artifact and at most fifteen minutes. Links are minted after the permission check — by the settings loader for the session surface, and by the bearer-gated `POST /workspaces/:slug/exports/:exportId/download-link` for machine clients — and every download records `workspace.export_downloaded`. The permission is the owner-only `workspaceExport` statement: an admin can rename the workspace but cannot walk away with every member's email and the full audit trail, the same line `organization:delete` draws.

The export is the access half of a GDPR data subject request; the erasure half is account deletion, owned separately. The governance documentation describes how the two are served together. Rejected alternatives: presigned S3 URLs (need account-level R2 API credentials in a worker, and the starter deploys with none), storing archives in D1 (a blob column in the shared database for a seven-day artifact), and streaming the ZIP from the request path (an owner would wait on a full table walk inside one HTTP request).
