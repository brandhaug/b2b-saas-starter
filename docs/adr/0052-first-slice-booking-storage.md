# D1-backed first-slice booking storage

The first Booking Vertical Slice uses the shared D1 database as the source of truth for all mutable product state, with Merchant—not the Starter's Workspace—as its ownership and authorization boundary. D1 persists Merchant configuration, Public Booking Pages, one-to-one Merchant Owner membership, Providers, Services and eligibility, recurring Schedule Rules, Booking Sessions with expiring Time Slot Holds and Booking Quotes, Appointments with immutable booking snapshots, Confirmation access metadata, and the transactional outbox. HMAC-derived Confirmation Access Tokens are never persisted. Booking Sessions and Appointments preserve the fixed `pay_in_person` Checkout Path, while Booking Readiness, Availability and Time Slots, the Customer Directory, and Confirmation are derived views. The first slice deliberately has no Workspace bridge, Brand or Shop rows, Checkout Policy, durable Customer profile, Sale Order, generic Payment ledger, generated slot rows, or Confirmation record.

Confirmation atomically consumes the held interval, creates the Appointment and snapshots, issues confirmation access, reduces the Booking Session to a 24-hour idempotency record, and appends the outbox item. During that window the consumed capability can replay only the identical confirmation command and return the existing Appointment. A ten-minute hold locks the accepted quote, an anonymous Booking Session expires after thirty minutes of inactivity or two hours absolutely, and a Confirmation Access Token expires thirty days after the Appointment ends. This favors durable server-owned booking state and stable history over browser-carried carts, live catalog joins for historical records, and copied Legacy Source entities.

One typed, explicitly clock-anchored Seed Booking Scenario is the only authored fixture. Local development, end-to-end tests, and screenshots populate D1 from it; unit tests may load the same graph into in-memory capability adapters, but runtime applications never fall back to fixture data. Reseeding replaces only the canonical seeded Merchant graph. This supersedes [ADR 0017](./0017-deterministic-seed-workspace.md) and replaces the runtime Seed-layer fallback described for the generic Starter in ADRs [0044](./0044-per-capability-effect-services-with-seed-and-live-adapters.md) and [0049](./0049-persisted-local-d1-in-dev-and-e2e.md); persistent local D1 and test-only in-memory adapters remain.
