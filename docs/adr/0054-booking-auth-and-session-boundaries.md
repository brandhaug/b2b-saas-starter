# Booking auth and session boundaries

The first Booking Vertical Slice deliberately uses four separate authorization mechanisms instead of porting the Legacy Source's user-kind and browser-JWT model. Merchant Owners authenticate only through verified Better Auth email-and-password sessions scoped to `app.<domain>`; first-slice ownership is one person to one Merchant, and current membership is resolved server-side on every protected request. Customers remain anonymous: a short-lived Booking Session uses a route ID plus a hashed browser-held capability, while confirmed Appointments use read-only, HMAC-derived Confirmation Access Tokens that the Booking and Background Workers can reproduce for asynchronous email without persisting bearer secrets. The server-to-server Platform API accepts only independently scoped, single-Merchant bearer tokens.

These boundaries keep Merchant credentials away from public booking traffic, prevent customer contact details from becoming an accidental identity registry, and stop one credential type from crossing Worker or tenant boundaries. Additional Merchant roles, customer accounts and OTP, OAuth, support impersonation, ownership transfer, and deletion are deferred; local-storage JWTs, browser API tokens, and authorization inferred from Provider status are intentionally rejected. Consumed Booking Sessions reject further use except for a 24-hour idempotent replay of the identical confirmation command, which returns the existing Appointment rather than risking a duplicate after a lost response.
