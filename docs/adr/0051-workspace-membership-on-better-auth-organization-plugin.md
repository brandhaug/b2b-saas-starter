# Workspace membership on Better Auth's organization plugin

Workspace membership runs on Better Auth's `organization` plugin rather than on hand-written Drizzle writes. Reads and writes split by direction. Reads go straight through Drizzle, because `workspace-projections.ts` joins member data into dashboard reads and an HTTP hop per read would wreck that. Writes — add, remove, change role, invite, cancel, accept — go through the plugin's endpoints, so its validation and its lifecycle hooks apply (`afterUpdateMemberRole`, `afterRemoveMember`, and roughly two dozen more) and the starter does not reimplement an invitation state machine. `teams` and `dynamicAccessControl` are switched off and stated rather than left to the default: teams add two tables and make `session.activeTeamId` required, and dynamic access control wants an `organizationRole` table. Static roles are enough for a starter.

The plugin's vocabulary stops at `packages/auth`. `modelName` points its `organization`, `member`, and `invitation` models at `workspaces`, `workspace_members`, and `workspace_invitations`, so the domain word stays **Workspace** (CONTEXT.md) and nothing above the auth package learns the word "organization". `modelName` is the drizzle schema _export key_, not the SQL table name. The plugin names the foreign key `organizationId`, so `member` and `invitation` each carry `fields: { organizationId: 'workspaceId' }`; every other field name already matches. `planId` and `updatedAt` are `additionalFields` on the organization model, not entries in `metadata`, because a column the plugin does not know about is stripped from every endpoint response — and `metadata` is plain `text` because the plugin JSON-stringifies it itself. The consequence is that Better Auth now owns the shape of those three tables: camelCase columns, epoch-integer dates, surrogate `id` primary keys. The old composite membership key became a unique index on `(workspaceId, userId)`, which keeps the one-membership-per-user invariant while giving the plugin the row id its `removeMember` and `updateMemberRole` endpoints address members by. `packages/capabilities` reaches the write path through structural ports it declares itself (`WorkspaceMemberBinding`, and the invitation equivalent) with the app supplying the adapter, so `capabilities` and `auth` stay siblings and neither imports the other.

Authorization is a separate package and one decision point. [`@b2b-saas-starter/authz`](../../packages/authz/AGENTS.md) owns the statement set, the static role table, the API-token scope mapping, and the `requirePermission` guard; it is built on `createAccessControl`, which is pure, so it sits _below_ both `auth` and `capabilities` and is usable before any capability layer exists. Enforcement happens at the route boundary, not inside a capability: `requireWorkspacePermission` for web server functions and `enforcePermission` for bearer-token API routes. An endpoint names the permission it needs (`{ apiToken: ['create'] }`), never a role and never a scope, because the role table is the only place that mapping lives. API-token scopes are synthetic roles over the same statements, so a browser session and a bearer token resolve through one `authorize()` call. A system admin (`user.role === 'admin'`) is a separate axis and is granted nothing inside a workspace.

What this cost. Membership writes and their audit rows can diverge: D1 rejects an explicit `BEGIN`, and a plugin write cannot be enlisted into the `batch()` the other mutating capabilities use, so the two-statement atomicity trick is unavailable for membership. It is recorded here as a trade so it is not rediscovered later as a bug. Adding a column to `workspaces` now means adding an `additionalFields` entry too, and schema changes on those three tables follow Better Auth's conventions rather than the starter's. The API worker cannot drive most of this surface: `removeMember` and `updateMemberRole` are `requireHeaders: true` and so is every invitation endpoint, `createInvitation` additionally demands a caller who is already a member, and a bearer token is no session. Only `addMember` runs headerless. The worker does not get a session, and that is now decided rather than deferred. Minting one for the API token's creating user would manufacture an identity nobody signed in as, would behave inconsistently once that user leaves the workspace, and would put the plugin's own permission check beside `authorize()` as a second authority — the opposite of the single decision point above. Writing around the plugin would mean a second write path and a reimplemented invitation state machine. So membership and invitation **writes** are a `apps/web` surface; the worker keeps the **reads**. `POST /workspaces/:slug/invitations` was removed from the contract with this decision: it emailed a link carrying no invitation id, so no recipient could accept it, and a published endpoint that cannot do what it claims is worse than no endpoint. The cost is that the REST surface cannot provision people at all, and that invitation events now have no outbound webhook producer, because `apps/web` publishes no webhooks. Migrations squashed to one baseline, so an existing local D1 must be reset (see [docs/setup.md](../setup.md#database)); nothing was live, so no data migration was needed.
