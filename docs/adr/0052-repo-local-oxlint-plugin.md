# Repo-local oxlint plugin for starter conventions

Lint runs in three layers. Oxlint's own rules come first, enabled by category. Third-party JS plugins come second: `oxlint-plugin-effect` for the Effect discipline, ultracite's `anti-slop` for the type-safety rules, `eslint-plugin-better-tailwindcss` for class names. `@b2b-saas-starter/oxlint-plugin` is the third layer, and it exists because some conventions here are not expressible with anyone else's rules. A convention that only this repo holds gets a rule in that package instead of a paragraph in a markdown file, because a paragraph does not fail CI. Nine rules live there today. Three are written for this repo: `no-interface-merge-outside-dts` and `no-mismatched-augmentation-context` make CLAUDE.md rule 7 executable, and `no-unknown-error-message` names the one duplicated idiom the codebase kept re-deriving. Six are ported, with attribution in each file, from two public MIT plugins that solve the same problem: [pingdotgg/t3code](https://github.com/pingdotgg/t3code/tree/main/oxlint-plugin-t3code) and [UsefulSoftwareCo/executor](https://github.com/UsefulSoftwareCo/executor/tree/main/scripts/oxlint-plugin-executor). Both were read in full first, and most of what they contain was rejected: about half of their rules duplicate something `effect/*` or `anti-slop/*` already reports, several hard-code the source repo's package names or directory layout, and a few encode a policy this repo has already settled the other way. `no-switch-statement` is the clearest of those. This repo deliberately enables four rules that make `switch` safer, so banning it would reverse a decision rather than enforce one.

Two of the local rules exist because their failure is silent. `consistent-type-definitions` is set to `"type"` repo-wide and is auto-fixable, and `oxlint --fix` runs in the pre-commit hook, so an `interface` written inside a `declare module` block in a `.ts` file gets rewritten to a type alias on commit and the augmentation quietly becomes a duplicate identifier. The hook already guards this by running `typecheck` afterwards, which catches the breakage one step downstream. `no-interface-merge-outside-dts` has no fixer, so it survives `--fix` and reports at the site with the reason. `no-mismatched-augmentation-context` covers the mirror trap: `declare module 'x'` augments the real module only from inside a module, while `declare global` and `declare namespace` reach the global scope only from a global script. Get the file's module-ness wrong in either direction and TypeScript still compiles. The augmented member is simply absent, and the symptom appears somewhere else as a missing property. `apps/web/src/worker-env.d.ts` documents having discovered this the hard way.

Three of oxlint's six categories are on: `correctness`, `suspicious`, and `perf`. Turning the last two on cost four adjustments, and in three of them an allow-list beat an off switch. `react-in-jsx-scope` is off outright, because the automatic JSX runtime makes it a relic and it accounted for 851 of the reports. `no-underscore-dangle` allows `_tag`, which is Effect's discriminant and the only dangling underscore the repo writes. `import/no-unassigned-import` allows `**/*.css`, because stylesheet and font imports are how TanStack Start and Tailwind are wired. `unicorn/consistent-function-scoping` is off in tests and config files only, where a row builder belongs next to the case it serves; its two hits in production code were genuine and were hoisted. `pedantic` stays off, and that is a judgement rather than a deferral: it is 87 `max-lines-per-function` reports on test bodies plus `max-dependencies`, and neither is a thing worth policing here. Four type-aware rules arrived with the new categories. Two were suppressed at the single site that trips them. Two are off repo-wide, and both because they fight a settled convention: `consistent-return` would demand an explicit `return undefined` on eleven validators whose contract is "return a message or fall through", and `no-unnecessary-type-arguments` would collapse `Effect.Effect<A, unknown, never>` to something a reader has to reconstruct.

`react/forbid-elements` forbids `button`, `input`, and `label` outside `apps/web/src/components/ui/`, which turns DESIGN.md's component contract from prose into a check. A hand-rolled `<button>` loses the focus ring, the disabled treatment, and the size scale that `buttonVariants` encodes, and it had happened three times. The rule also forced one gap closed: replacing the raw radio inputs in the invitation form needed a `RadioGroup` primitive, which did not exist. `table` is deliberately not on the list. `ui/table.tsx` encodes workspace data-table styling with fixed cell padding and an overflow wrapper, and the schematic module table on the landing page overrides nearly all of it, so pointing that page at the primitive would mean fighting it cell by cell.

What this cost. Oxlint has no in-process rule tester for JS plugins, so a rule only runs inside the real linter, and `packages/oxlint-plugin/test/harness.ts` spawns the actual `oxlint` binary over fixtures in a temp directory. That means the plugin package needs Node builtins and a `spawnSync`, which the Effect rules forbid, so it carries a scoped override in `.oxlintrc.json` alongside the two vitest rules that cannot see through the harness's generic `it()` wrapper. The harness decodes oxlint's `--format=json` output through an Effect `Schema` so nothing past the subprocess boundary needs a cast, and it collects every case in a `describe` body and lints them in one invocation, because a process per assertion does not scale. Rules are syntax-only: neither upstream plugin touches type information and neither does this one, so anything needing the type checker still belongs in a tsgolint rule. The plugin's version is pinned to the linter's, and `@oxlint/plugins` was added to the `oxc` group in `.catalog-updaterc.json` so the two move together.
