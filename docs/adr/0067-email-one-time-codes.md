# Email one-time codes on the email-otp plugin

Email one-time codes are a Better Auth plugin (`emailOTP`), not hand-written endpoints. The starter wires it for three uses — sign-in, email verification, and password reset — with the knobs stated rather than defaulted: six digits (the one value Better Auth already defaults to), a ten-minute expiry, and three allowed attempts before the code locks. Codes hash at rest (`storeOTP: 'hashed'`) in the `verification` table Better Auth already owns, so the code that opens a session never sits in D1 in plaintext and no new table is needed. `disableSignUp: true` is the consequential choice: a sign-in code only opens sessions for existing accounts, so registration — with its Turnstile gate (ADR 0031) and its `allowUserToCreateOrganization` logic — stays on `/sign-up`. Without it, proving mailbox control would silently mint accounts, and the enumeration defenses elsewhere in the starter would be guarding a door that no longer exists. Sending rides the same `AuthEmailSender` port the link flows use (a new `sendOneTimeCode` member carrying Better Auth's own callback signature), so the provider-light rule holds: with no `EMAIL` binding the code renders to the dev console's `email.dispatched` log line and the whole flow is demoable locally with zero provider configuration.

The plugin is the alternative path, not the default one. The emailed links stay primary: sign-up still sends a verification link (`sendVerificationOnSignUp` stays off — the plugin's after-hook would replace the link with a code), `/reset-password` and `/verify-email` remain link landing pages, and `overrideDefaultEmailVerification` stays off so the plugin does not silently take over the verification callback. The UI additions are one entry point on `/sign-in` (a footer link to `/sign-in/email-code`), a code card on `/verify-email`'s failure branch, and a second button on `/forgot-password` that leads to code entry plus the new-password fields. Every code surface shares the six-cell `OtpCodeInput` (one logical value, left-packed cells, paste-aware) and one visible resend cooldown (`useResendCooldown`, sixty seconds — the same window as the plugin's send rate limit). Non-disclosure carries over from the link flows: the send endpoint answers identically whether or not the address is registered, and the screens echo no address back.

The starter's own sensitive-surface policy (ADR 0030) covers the new endpoints. All five email-otp routes are credential material — sending a code is an email-sending primitive, verifying one is a guessable-credential check — so they land in the existing tight `auth_sign_in` bucket (5/min per IP) beside password sign-in, reusing the `RATE_LIMITER_AUTH_SIGN_IN` binding instead of provisioning a sixth one. The plugin's internal attempt counter is the finer lock: after three wrong verifies the code is consumed and even the correct code reads as invalid, so a fresh send is the only way back in.

Audit coverage reuses the existing exchange table in `apps/web/src/lib/server/auth-audit/`. The code-based sign-in and code-based verification get their own rows (`auth.sign_in` with `method: 'email-otp'`, and the `auth.email_verified` pair), while the code-based reset request and reset deliberately reuse the link-flow rows — their `/email-otp/…` pathnames end with the same suffixes, the events are the same, and two rows recording one decision is how the table drifts. The code _send_ records nothing: the sign-in, verification, or reset it enables is the audited outcome. No new taxonomy entries were needed.

What this cost. The email-otp plugin adds one more line to the plugin list that `tanstackStartCookies()` must stay behind, and one more callback Better Auth fires outside Effect. The sign-in code endpoint creates sessions, so it is now a second credential surface beside `/sign-in/email` — the tight rate-limit bucket and the attempt lockout are the compensating controls, and both live in code that already existed for the password path. The reset-by-code flow finishes on `/forgot-password` rather than redirecting through the auth handler, so its "one opaque failure state" is the form's error alert; the endpoint's answer (verify + set in one call, revoking prior sessions) is the same as the link's.
