# Require two-factor authentication for System Operators

Every System Operator must enroll and complete TOTP-based two-factor authentication before receiving an Operator Session. Password-only access is insufficient for the Operations App because its platform-wide permissions and impersonation capability justify the additional enrollment and sign-in friction. Recovery normally uses one-time backup codes; bypassing enrollment or downgrading an operator to password-only access is not supported. If both TOTP access and backup codes are lost, a focused Bun recovery script with explicit production targeting revokes the Operator Session and derived impersonation, disables existing 2FA material, requires fresh enrollment, and records a global system audit event. Starting impersonation additionally requires a fresh TOTP verification from the preceding five minutes, limiting the impact of an unattended or stolen Operator Session. Operator Sessions have an eight-hour absolute lifetime and a thirty-minute inactivity timeout, cannot slide beyond the absolute deadline, and are validated authoritatively against D1 on every request. Each operator may hold only one active Operator Session; a new sign-in revokes the previous session and every impersonation derived from it. The deterministic local seed includes one local-only System Operator password and TOTP secret for development and tests; those credentials are never created or accepted in production.
