# Social sign-in as an absent-until-configured provider

GitHub and Google sign-in ship as Optional Providers over Better Auth's `socialProviders`, and the inactive state of a provider is **absent**, never present-but-disabled. `activeSocialProviders` (`packages/env/src/server.ts`) resolves the worker env into the providers that have both halves of their credential — a `*_CLIENT_ID` without its `*_CLIENT_SECRET` means unconfigured, same as neither — and `AuthConfig.socialProviders` carries the resolved bag into `makeAuthOptions` unchanged (identity, not a re-built copy). When the resolution is empty the options key holds `{}`, which resolves to zero providers inside Better Auth — no provider exists at all, nothing exists-but-disabled — so the Local Auth Path's runtime shape is the same whether no provider is configured or none was ever wired. This replaces the earlier stated decision that the starter ships no `socialProviders` at all; what survived is the _shape_ of that decision — a fork adds a provider by extending the env schema and the resolver, not by wiring a provider that exists but is disabled.

Account linking runs on Better Auth's implicit linking with its defaults intact, and the defaults are the security posture the starter wants: a social identity links to an existing email/password account only when the provider confirms the email as verified **and** the local mailbox is verified (`requireLocalEmailVerified`, on by default). The unverified-local-mailbox case is refused with `account_not_linked` — the account-takeover shape that guard exists for — and that refusal is asserted in the live suite (`packages/auth/src/social-auth.test.ts`) rather than assumed. The suite drives the whole OAuth round-trip against a provisioned local D1 with GitHub's three HTTP endpoints stubbed at the `fetch` boundary: initiation, the state cookie, the code exchange, the profile read, the link decision, and the session the callback sets are all the real code paths, not a simulated flow.

The linking audit is a port on `AuthConfig`, not an exchange row. The OAuth callback answers with a redirect that names nobody, and a fresh social sign-in has no session to read before the handler runs, so the exchange-row machinery that audits credential sign-in cannot attribute a link event from the request/response pair. Better Auth's `databaseHooks.account.create.after` / `delete.after` fire with the account row itself — `userId` and `providerId` — which is exactly the attribution the event needs. `AuthConfig.accountHooks` carries the structural port (the same pattern as `AuthEmailSender`: Better Auth calls its hooks outside any Effect, so the port is a plain promise and the app supplies the adapter), and `apps/web/src/lib/server/social-account-audit.ts` records `auth.account_linked` / `auth.account_unlinked` through `AuditEventLog`, skipping `credential` rows because the credential sign-up lifecycle already has its own audit row over `/sign-up/email`. The write is best-effort by the same contract as the auth audit: a failed write is logged and never fails the sign-in exchange that triggered it. Two accepted trades come with the hook placement: the hook also fires on a first-time social sign-up (the event is accurate — a provider account was linked — but it is not exclusively an existing-account event), and a refused unlink (the last remaining account) records nothing, because the hook only sees successful deletes; the UI disables the control for that case and the endpoint refusal is the backstop. The callback still records `auth.sign_in` / `auth.sign_in_failed` exchange rows with the provider as the sign-in method — unattributed on a fresh sign-in, attributed when a session existed, which is the same shape as the session-ending rows.

The `lastLoginMethod` plugin ships in its core, cookie-backed form: `storeInDatabase` stays off, so there is no new user column and no migration, and losing the cookie is cosmetic — the hint on the sign-in page disappears, no data does. The cookie is client-readable by design (the client plugin reads it to render "Last signed in with GitHub"), which is the plugin's own trade and an acceptable one for a non-security signal.
