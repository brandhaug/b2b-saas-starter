# Magic link as the second Local Auth Path

Sign-in now has two Local Auth Paths (CONTEXT.md): email-and-password, and a single-use link emailed to the address. The link path runs on Better Auth's core `magicLink()` plugin rather than a hand-rolled token table, for the same reason membership runs on the `organization` plugin (ADR 0051): the plugin owns the token lifecycle — generation, storage, single-use atomic consumption, expiry — and reimplementing it would put a second credential authority beside Better Auth's `verification` table, which already backs the reset and verification tokens. The plugin slots into the existing seams with no new tables and no new env: the token lives in `verification`, the email goes out through the `AuthEmailSender` port (`sendMagicLink`, carrying the plugin's own callback signature so the app's adapter is the callback verbatim), and the drizzle adapter needs no `additionalFields` because no new column exists.

Three knobs are stated rather than defaulted. `expiresIn` is ten minutes (`MAGIC_LINK_EXPIRES_IN_SECONDS`, exported so the email template's copy and the app's expiry state name the same number): long enough for an email round trip, short enough that a link sitting in a shared inbox is not a standing credential. `storeToken: 'hashed'` means the emailed token is the credential and a read of the `verification` table is not enough to mint a session — the plaintext token never exists at rest. `disableSignUp: false` allows sign-up through a link, and consuming one proves control of the mailbox, so the plugin creates the account with `emailVerified: true`. That is the same proof the verification email asks for, which is why `requireEmailVerification` has nothing left to gate for a magic-link account and the production-only gate stays honest instead of locking link-signed-up users out of their workspaces.

The web flow reuses the token-exchange hop shape the reset and verification links already use, rather than consuming the token in a route loader. The emailed URL points at `GET /api/auth/magic-link/verify?token=…` with `callbackURL`, `newUserCallbackURL`, and `errorCallbackURL` all set to the app's `/magic-link/verify` page. The plugin consumes the token, opens the session, sets the cookie, and redirects: success arrives at the landing page already signed in and its `beforeLoad` continues straight to `/workspaces`; every failure — invalid, expired, or already used, which the plugin answers identically — arrives with `?error=INVALID_TOKEN` and renders one honest "cannot be used" state offering a fresh link. Consuming in a loader was rejected because the endpoint's contract is redirect-and-set-cookie, and calling it server-side to fish a JSON session out of it would fight the cookie bridge `tanstackStartCookies()` exists to provide.

Abuse surface. The send endpoint (`POST /sign-in/magic-link`) lands in the existing `auth_sign_in` rate-limit bucket (5 req/min, ADR 0030's sensitive-surface decision) — it mails an arbitrary address, which is the same exhaustion vector as credential stuffing — and joins sign-up behind the Turnstile gate (ADR 0031) when configured, with the widget's token riding `x-turnstile-token` as on sign-up. Unconfigured Turnstile stays inactive, so local development is unchanged. The endpoint itself is non-disclosing — it answers `{ status: true }` whether or not the address has an account, and the screen shows the same "if this email exists" message the forgot-password form does — so it records no audit event of its own. The sign-in is audited where it happens: `GET /magic-link/verify` is a row in the auth-catchall exchange table, writing the existing `auth.sign_in` / `auth.sign_in_failed` pair with `method: 'magic-link'` in the metadata, read from the redirect's `Location` header exactly like the email-verification row. No new taxonomy types — the method discriminator is metadata, as it already is for email versus username sign-in.
