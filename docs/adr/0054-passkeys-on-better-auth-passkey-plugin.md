# Passkeys on Better Auth's passkey plugin

Passkeys (WebAuthn) ship on `@better-auth/passkey` rather than a hand-rolled WebAuthn integration. The decision mirrors the organization plugin's (ADR 0051): the ceremony — challenge storage, response verification via `@simplewebauthn/server`, credential counters, the schema mapping — is protocol machinery the starter has no reason to reimplement, while the parts the starter owns (where sign-in is offered, what is audited, who gets emailed) live in the app as they do for every other auth surface. The plugin slots into the existing `packages/auth` factory between the two-factor plugin and the cookie bridge, and its `passkey` table is additive: one more Better Auth-owned table in `packages/db` with the plugin's shape (camelCase columns, epoch-integer dates), one migration, no changes to existing tables.

No new environment variable. `rpID` and `origin` derive from `BETTER_AUTH_URL`, which `AuthConfig` already carries as `baseURL`: the hostname is the rpID and `new URL(...).origin` is the ceremony origin (scheme, host, port; any path dropped). A hostname is a valid WebAuthn rpID by construction — `localhost` included, which is what keeps the feature provider-light: registering and signing in with a passkey works on the local dev server with zero configuration, the same rule that governs the Local Auth Path. The alternative, a `PASSKEY_RPID`/`PASSKEY_ORIGIN` pair, would drift from the auth URL the moment one of them was edited alone. A deployment serving the app on several origins widens `origin` to the array the plugin accepts.

**A passkey sign-in satisfies the two-factor requirement.** With TOTP enabled, credential sign-in opens no session: Better Auth's two-factor plugin is an after-hook that matches `/sign-in/email`, `/sign-in/username`, and `/sign-in/phone-number`, deletes the session the credential handler minted, and answers `twoFactorRedirect: true` so the app can route to `/two-factor`. The passkey plugin's `verify-authentication` endpoint is not on that list — it calls `internalAdapter.createSession` itself, and a session is what the client gets. That is correct rather than a bypass: a passkey ceremony is two factors in one gesture — possession of the credential (something you have) plus the user verification the authenticator performed, biometric or PIN (something you are or know). Requiring a TOTP code on top would demand a third factor from users who chose a phishing-resistant one. The honest caveat is recorded here too: user verification is requested as `preferred`, not `required`, so an authenticator that cannot verify may complete the ceremony on possession alone — the industry-standard passkey posture, and the same one every major relying party ships. The claim is pinned mechanically in `packages/auth/src/live-passkey.test.ts`: a TOTP-enabled user signs in with a passkey and receives a session with no code. Two-factor enrollment itself is untouched; the two features answer the same sign-in challenge by different means.

Governance rides the existing seams rather than new ones. Passkey add and remove are rows in the auth catchall's exchange table (`auth.passkey_added` / `auth.passkey_removed` and their `_failed` pairs, actor from the pre-handler session read, target the account), so they record exactly like the two-factor lifecycle events they sit beside. A passkey sign-in records the shared `auth.sign_in` pair with `method: "passkey"` in the metadata, like email and username sign-ins. Each successful add or remove emails the account holder through the same best-effort notification contract as `TwoFactorChangedEmail` (`PasskeyChangedEmail` via the provider-light dispatcher — to the log locally), because a sign-in credential changing silently is the same takeover signal a second factor changing silently is. Renaming a passkey is deliberately neither audited nor emailed: it changes a label, not a credential, and padding the audit trail with non-events makes the real ones harder to find.

What this does not ship. Passkey-first onboarding (`registration.requireSession: false` plus a `resolveUser` callback over a signed context) is out: pre-auth registration needs a context scheme worth its own decision, and the Local Auth Path stays email/password. There is no sessions list interaction, no account deletion coupling, and no last-used tracking — none of those change what a passkey is. Conditional UI is offered where the browser supports it (`webauthn` as the last autocomplete token on the email field, plus an on-mount preload behind `isConditionalMediationAvailable`) with the button as the universal fallback, so no browser is left without the flow and none of them gets a second one.
