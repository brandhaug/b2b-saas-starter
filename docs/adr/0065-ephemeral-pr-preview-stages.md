# Ephemeral per-pull-request preview stages

Production deploys stay as [0019 — CI with Alchemy deploy on merge](./0019-ci-with-manual-alchemy-deploy.md) decided: one `prod` stage, deployed from `master` or by hand from the `production` environment. This record adds a second kind of stage beside it. Every pull request from this repository gets an Alchemy stage named `pr-<number>` with its own D1 database, webhook queue and dead-letter queue, and three Workers (`b2b-saas-starter-pr-<number>-{web,api,background}`). The stage is deployed on `opened`, `synchronize`, and `reopened`, seeded with the Seed Workspace so reviewers see the reference app with data, linked from the PR timeline through a GitHub deployment status, and destroyed on `closed` ([.github/workflows/preview.yml](../../.github/workflows/preview.yml)).

The stage is the only axis that varies. `alchemy.run.ts` reads it from Alchemy's `Stage` service (the `--stage` flag; `pnpm run deploy:stage` passes `$ALCHEMY_STAGE` through) and asks `stageResourceNames` in `infra/bindings.ts` for the physical names: `prod` keeps the historical names, so the production stack is untouched and `pnpm run infra:wrangler` still renders the same `wrangler.jsonc` files; any other stage is prefixed `b2b-saas-starter-<stage>-`. Migrations run as part of the deploy (Alchemy's `D1.Database` `migrations` input), and the seed reuses `scripts/seed.ts` with `--remote --database=<name>` instead of a second seed path.

Previews are deliberately provider-light. A `pr-<number>` stage drops every env-gated provider value even when the deploying shell has one (Turnstile, Stripe, Sentry, PostHog, OTLP, OpenAI, Workers AI, email), keeps only `ENVIRONMENT=preview`, `SERVICE_VERSION`, and `GIT_COMMIT_SHA`, and takes `BETTER_AUTH_URL` from the account's `workers.dev` subdomain rather than from a per-PR secret. The workflow therefore needs three repository secrets (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `PREVIEW_BETTER_AUTH_SECRET`), and forks and Dependabot never run it because the secrets would be exposed to their code. A preview is public and carries the documented demo credentials; it must never hold real customer data, which the seeded fixture guarantees by construction.

Alternatives considered: Cloudflare's own Workers Builds previews (one Worker per branch, no D1 or queue isolation, and a second deploy path beside Alchemy), Worker version preview URLs (share the production database), and a single long-lived `staging` stage (serializes review and hides per-PR schema changes). A per-PR stage costs a few minutes of CI per push and a handful of free-tier resources that `alchemy destroy` reclaims on close.
