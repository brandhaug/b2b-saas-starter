# packages/db

Drizzle ORM (drizzle-orm `1.0.0-rc.4`) schema, migrations, and the shared `Database` Effect service for the Cloudflare D1 database.

## What lives here

- `src/schema.ts` — 18 tables in one file, in three ownership groups. **Better Auth core:** `user`, `session`, `account`, `verification`, plus the `twoFactor` plugin's `twoFactor` table (`two_factor`) and `user.twoFactorEnabled`, the `passkey` plugin's `passkey` table (ADR 0056 — plugin-owned shape, the export key stays the plugin's model name), the admin-plugin columns (`user.role`, typed with `systemRoles` and nullable because the plugin declares the field optional — `null` means `user`; `banned`), `account.issuer`, and `session.activeOrganizationId`. **Better Auth `organization` and `sso` plugins:** `workspaces`, `workspaceMembers`, `workspaceInvitations` (ADR 0051), and `workspaceSsoConnections` (ADR 0055 — workspace SSO) — see the next section, they are not starter-shaped. **Starter:** `apiTokens`, `webhookEndpoints`, `webhookDeliveries`, `notifications` (with a `kind` enum column), `notificationPreferences` (one row per explicit `(userId, kind)` channel choice, unique index; defaults live in code — ADR 0061), `auditEvents`, `workspaceExports` (ADR 0055 — export artifacts; `requested_by_user_id` is `ON DELETE SET NULL` so an export outlives the account that asked for it, and `download_secret` is the per-export HMAC key behind signed download links), and `workspaceSubscriptions` (per-seat billing's provider-linked state). Shared column helpers at the top (`id`, `authTimestamp`, `authCreatedAt`, `authTimestamps`, `isoCreatedAt`, `workspaceRef`, `workspaceRefNullable`, `workspaceIdIndex`) encode the dual timestamp dialect below — use them instead of hand-rolling the column chains, and note each returns _fresh_ builders because Drizzle column builders are single-use. There is no helper for a **nullable** ISO timestamp: that is plain `text('…')`, and a wrapper over it would be the identity function. `workspaceRef(column)` takes a column-name argument because the plugin-owned tables spell the foreign key `workspaceId` while everything else spells it `workspace_id`.
- **The three workspace tables belong to the `organization` plugin** ([ADR 0051](../../docs/adr/0051-workspace-membership-on-better-auth-organization-plugin.md)). Their names stay in the starter's vocabulary, but their _shape_ is the plugin's: camelCase column names, epoch-integer dates, surrogate `id` primary keys. Three consequences worth knowing before you edit them. (1) Adding a column here also means adding an `additionalFields` entry in [`packages/auth`](../auth/AGENTS.md) — a column the plugin does not know about is stripped from every endpoint response. The one deliberate exception is `workspaces.onboardingDismissedAt` (nullable epoch integer): only the `workspace-onboarding` capability reads or writes it and nothing that returns through a plugin endpoint needs it, so it stays plugin-invisible on purpose (ADR 0054). (2) `workspaces.metadata` is plain `text`, never `mode: 'json'`, because the plugin stringifies and parses it itself. (3) `workspace_members` has a **unique index** on `(workspaceId, userId)` rather than a composite primary key: the plugin's `removeMember` / `updateMemberRole` address a member by row id. The one-membership-per-user invariant is asserted in `live-d1.test.ts` — as an invariant (a second row for the pair is refused), not as an index shape. `invitationStatuses` carries the plugin's single-`l` `canceled` spelling because the plugin writes the value.
- `src/service.ts` — two services and one constructor: `class Database extends Context.Service<Database, EffectDatabase>()`, `class RawD1 extends Context.Service<RawD1, D1Binding>()`, and `layerFromD1(env.DB): Layer.Layer<Database | RawD1>`, which provides both from one binding (there is no `Database`-only constructor — one was removed because nothing could use it). `Database` holds drizzle's **Effect-native** database (`drizzle-orm/effect-d1` over an `@effect/sql-d1` `D1Client`): query builders are Effects, so capabilities `yield*` them directly. Capabilities map query failures to the typed `CapabilityUnavailable` error (see `packages/capabilities/src/internal/unavailable.ts`) — don't reintroduce `Effect.orDie`/`Effect.promise` around queries. Also exports `batch(statements): Effect<void, DbBatchError, RawD1>` + `BatchStatement` (`{ toSQL(): Query }`, drizzle's own `Query` type): compiles drizzle builders via `toSQL()` and runs them through the raw `D1Database` binding's `batch()` (an implicit transaction), since the effect-d1 driver has no batch/transaction support. The binding comes from the `RawD1` **service**, not an argument — resolve it once where the layer is built (`governance/audited-mutation.ts` does exactly that) rather than threading it through every call. `batch` fails with the typed `DbBatchError` (`Schema.TaggedError`, `{ reason: string }`) — callers get a tagged error, not a bare `Error`. Every mutating capability `Live*` layer requires `Database | RawD1`; tests use a shimmed Database layer.
- `src/client.ts` — `createDrizzleDb(d1)` and the `DrizzleDatabase` type, the **promise-based** `drizzle-orm/d1` client. Kept solely for Better Auth's `drizzleAdapter` (`packages/auth`), which needs promises. Don't reach for it in capabilities — use the `Database` service.
- `src/enums.ts` — **every** stored enum vocabulary (`workspaceRoles`, `systemRoles`, `invitationStatuses`, `apiTokenScopes`, `deliveryStatuses`, `workspaceExportStatuses`, `notificationKinds` + `securityNotificationKinds`, `notificationChannels`, `ssoProvisionedRoles` — `member | admin`, the roles an SSO Connection may provision — plus `adminSystemRole` and `isSsoProvisionedRole`, as a drizzle-free leaf module, re-exported by `schema.ts` and exported as the curated `./enums` subpath. A new stored enum goes here, not into `schema.ts` beside the table that stores it. The policy layer (`packages/authz`) and the auth server (`packages/auth`, for `adminRoles`) import it here rather than from `schema.ts` so neither depends on the table definitions. `systemRoles` (`admin | user`, stored in `user.role`) is the **system** axis and `workspaceRoles` (`owner | admin | member`, stored in `workspace_members.role`) is the **workspace** axis: they share the word `admin` and nothing else — a system admin gets `/admin` and no workspace access at all. `packages/capabilities` re-exports both as `SYSTEM_ROLES` / `WORKSPACE_ROLES` and derives its `SystemRole` / `WorkspaceRole` schemas from them.
- `migrations/` — `drizzle-kit` output, one folder per migration (`<timestamp_name>/migration.sql`). Generate with `pnpm run db:generate` after editing `schema.ts`; commit schema + migration together. Currently **one**: the squashed baseline `20260904091107_nosy_metal_master` (the webhook-operator branch rebased onto a migration DAG drizzle-kit could no longer generate against — `db:generate` failed even on master's forked chain — and nothing was live, so the nine prior migrations were deleted rather than migrated through; the baseline was regenerated from `schema.ts` as one full-schema folder; squashing again needs the same conditions).
- **Resetting a stale local D1.** After a squash an existing local database is wrong twice over: old table shapes, and a `d1_migrations` table naming migrations that no longer exist. Migrating on top of it does nothing. Drop the state and rebuild:

  ```bash
  rm -rf packages/db/.wrangler/state/v3/d1
  pnpm run db:migrate:local
  pnpm run db:seed
  ```

  Restart `pnpm run dev` afterwards so the shim re-attaches the binding (ADR 0049).

- `scripts/migrate.ts` — applies migrations via `wrangler d1 execute` with a `d1_migrations` tracking table (`pnpm run db:migrate:local` / `db:migrate:remote`). Don't switch back to `wrangler d1 migrations apply`: wrangler's runner only sees flat `migrations/*.sql` files and silently skips drizzle-kit's folder-style output.
- `src/testing.ts` — test-only `./testing` subpath: `provisionTestD1()` boots an isolated, non-persisted local D1 (workerd via wrangler's `getPlatformProxy`) with every committed migration applied. `src/live-d1.test.ts` uses it to validate migrations, column-mode round-trips, cascade deletes, and `batch` atomicity against real D1 semantics — its "every table exists" case derives the table list from the schema module (`is(value, Table)` + `getTableName`), so a new table is covered without editing the test; the per-capability `packages/capabilities/src/**/*.live.test.ts` suites use it (through `capabilities/src/testing/live-harness.ts`) for Live-adapter coverage. Never import the subpath from application code.

## D1 gotchas captured in the schema

- **No native boolean.** Booleans use `integer({ mode: 'boolean' })`. Don't switch to raw `integer` — capabilities read these as JS `boolean`.
- **Mixed timestamp shapes by design, and the line is ownership, not age.** Better Auth tables — core _and_ the three plugin-owned workspace tables — store epoch-seconds in `integer` columns (its plugin contract); starter tables store ISO strings in `text` columns. Don't normalize without updating both sides: the admin plugin queries by integer, and the organization plugin writes `Date` objects. `workspaces.createdAt` / `updatedAt` moved to integers with the plugin adoption, so anything reading them as ISO strings is reading a stale contract.
- **JSON columns are `text` with explicit `$type`.** `metadata`, `scopes`, etc. — Drizzle parses on read; never write the raw string. `auditEvents.metadata` is typed `JsonObject` (exported from `schema.ts` alongside `JsonValue`): audit detail is heterogeneous per event type, but it is JSON, so the column contract stays JSON rather than `Record<string, unknown>`.
- **All FKs cascade-delete from `workspaces.id`.** Removing a workspace removes its children. Audit log preserves removed-workspace rows via `workspaceId: null` system events — keep that asymmetry.
- **`workspace_invitations.inviterId` cascades from `user.id`, and is required.** The plugin declares it that way, so deleting a user now deletes their pending invitations instead of blocking the delete. The old `created_by_user_id` was nullable with no action.

## Seed lives outside this package

`scripts/seed.ts` (repo root, not `packages/db/src/`) is the canonical seed. It was moved out to break a workspace cycle — keep it there even if it feels like it belongs in `packages/db`. The Effect seed _fixture_ used by tests lives in `packages/capabilities/src/seed-fixture.ts`.

The seed script's `insert` helper takes the Drizzle table object (not a name string) and rows keyed by the table's **TS property names**: the SQL table/column names come from `getTableName`/`getTableColumns` and values map through each column's `mapToDriverValue` (JSON stringify, boolean → 0/1), so renaming a table or column — or typoing a key — breaks seed generation at compile time instead of drifting silently. Token hashes are produced with `hashApiToken` from `@b2b-saas-starter/capabilities` (the registry's own scheme), and the first fixture token is seeded from `SEED_API_TOKEN` so the documented credential verifies against both the Seed layer and a seeded local D1.
