# Domain and Capability Gap Map for Legacy Booking Parity

## Scope and evidence

This report answers which legacy Booking App journeys exceed the canonical language and current Effect application layer, and recommends an owning boundary for each responsibility. It is a planning artifact, not a proposal to preserve legacy package names or payloads. The checked-in legacy app is treated as behavioral evidence; the current repository's `CONTEXT.md`, `ARCHITECTURE.md`, intent nodes, schemas, and Effect services are the target-architecture authority.

The current implementation is deliberately a narrow vertical slice: one Merchant public page, Providers and Services, weekly Schedule Rules, an expiring Booking Session capability, one appointment's service selection, derived Availability, one Time Slot Hold and immutable Booking Quote, Customer Details, Pay In Person confirmation, Confirmation access, and an `appointment.created` outbox path. The database makes this boundary explicit: one public page per Merchant, only `pay_in_person`, only `active|consumed` Booking Sessions, and one `bookingSessionId` per Appointment (`packages/db/src/schema.ts:294-314`, `:316-365`, `:392-425`). The architecture explicitly defers Brands/Shops, Pay Now, rescheduling, reminders, analytics, customer accounts, and durable customer identity (`ARCHITECTURE.md`, “Explicitly deferred”).

The completed journey inventory is the route/state index for this analysis (`.scratch/legacy-booking-app-full-parity/research/legacy-booking-journey-state-inventory.md`). Direct citations below point to the underlying primary sources.

## Current capabilities that should be extended rather than replaced

- **Merchant Catalog** already owns Provider, Service, eligibility, status, and bookable reads (`packages/capabilities/src/merchant-catalog/merchant-catalog.ts:17-65`, `:90-109`). Extend this boundary for Brand/Shop topology and booking policies; do not reproduce catalog behavior in route loaders.
- **Booking Selection** already validates Provider preference plus primary/additional Services and exposes compatible additions (`packages/capabilities/src/booking/booking-selection.ts:17-77`). Keep one-request selection here, then compose multiple requests under a new group aggregate rather than turning one selection into an untyped cart.
- **Scheduling and Booking Scheduling** already separate merchant Schedule Rules from customer Availability/Holds (`packages/capabilities/src/scheduling/scheduling.ts:20-75`, `:100-134`; `packages/capabilities/src/booking/booking-scheduling.ts:29-105`). Add coordinated/reschedule/offer algorithms behind these seams; Availability remains derived rather than persisted.
- **Booking Checkout and Confirmation** already preserve accepted quote/customer facts and confirm atomically (`packages/capabilities/src/booking/booking-checkout.ts:10-56`; `packages/capabilities/src/booking/booking-confirmation.ts:48-101`; `ARCHITECTURE.md`, “Data and transaction boundary”). Expand the orchestration to Payments, Gift Cards, composite bookings, and new outbox events without reviving a generic Sale Order.
- **Confirmation access** is already a stronger least-privilege replacement for exposing a Sale Order ID (`packages/db/src/schema.ts:427-442`). Cancellation and rescheduling should authorize through a purpose-limited continuation of this model, not through Platform API tokens.

## Placement constraints

1. **`apps/booking` remains the customer boundary, not the business layer.** Route components compose typed capabilities and render legacy-observable states. They should not own pricing, eligibility, lifecycle transitions, or provider calls.
2. **`apps/api` is not the parity backend.** Its intent node restricts it to merchant-scoped Platform API contracts and explicitly says it is not a customer booking channel (`apps/api/AGENTS.md`). New customer commands belong behind the private Booking Worker binding; Platform API exposure is a separate later decision.
3. **D1 stores durable source-of-truth records, not view state.** Add tables for decided aggregates, immutable snapshots/ledgers, access metadata, and outbox work. Continue deriving Availability and Customer Directory. Do not persist popup phases, cart display modes, skeleton/null states, feature-provider objects, or calendar presentation.
4. **Background work starts from committed facts.** Payment reconciliation, reminders, waiting-list matching, offer expiry, gift-card delivery, and walk-in expiry need durable outbox/schedule records. Queue publication remains a wake-up, preserving the current transaction rule (`ARCHITECTURE.md`, “Data and transaction boundary”).
5. **Provider integrations remain replaceable and optional.** Payment processors, email/SMS, bot protection, ads, analytics, geolocation, and OAuth must sit behind typed adapters and expose disabled/needs-configuration states without breaking local booking, consistent with the map Notes and repository cross-cutting rules.

## Canonical language additions to decide before implementation planning

The existing glossary is sufficient for the first slice but not full parity. The following terms need explicit definitions and invariants before the final implementation plan: **Booking Party**, **Booking Request/Guest Booking**, **Merchant Checkout Policy**, **Policy Acceptance**, **Pricing Quote/Adjustment**, **Promotion**, **Payment Attempt**, **Payment Status**, **Gift Card Product**, **Gift Card Sale**, **Issued Gift Card**, **Gift Card Redemption**, **Waiting List Application**, **Availability Offer**, **Offer Attempt**, **Walk-in Queue**, **Walk-in Entry**, **Cancellation Policy**, **Reschedule Session**, **Customer Account**, **Operational Notification**, and **Reminder**.

Avoid making **Cart**, **Sale Order**, legacy **Reservation**, payment-provider objects, or UI checkout phases canonical aggregates. They conflate several responsibilities that the current architecture has already separated.

## Dependency implications for the parity plan

The architectural dependency order exposed by these gaps is:

1. Decide Brand/Shop topology, route ownership, policy inheritance, and glossary additions.
2. Decide the generalized pricing/quote contract and composite Booking aggregate; both Payments and receipts depend on them.
3. Extend Scheduling for group coordination, rescheduling, waiting-list candidate discovery, and queue-related rules.
4. Add Payments and Gift Cards as separate contexts with explicit atomic coordination points.
5. Add Waiting List and Walk-ins as distinct lifecycle capabilities unless a later domain-modeling session proves shared invariants.
6. Add Appointment cancellation/rescheduling commands and purpose-limited customer access.
7. Generalize domain outbox/Notifications and add scheduled Background Worker operations.
8. Layer localization, telemetry, experiments, ads, and optional customer identity around those stable contracts.

This ordering keeps the parity UI from hard-coding legacy Cart/Sale Order semantics while preserving the current Cloudflare-first transaction, privacy, and Worker boundaries.
