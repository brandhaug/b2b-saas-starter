# Legacy Booking App Journey and Observable-State Inventory

## Research status and evidence convention

This inventory treats `/Users/hassan/Desktop/ssqu/recreate/apps/booking-app` as the legacy primary source. Citations are relative to that directory unless stated otherwise. `Observed` means directly observable in static source (route/component/state wiring), not that a live production response was reproduced. `Runnable` means the state can be reached from the checked-out app without inventing backend data. `Inferred` means a real branch exists in source but reaching it requires particular API data, feature flags, persisted state, payment-provider state, or identifiers.

Runtime observation was not decision-complete: dependencies are installed, but almost every meaningful journey hydrates from live API/configuration, feature flags, cart storage, and valid brand/shop/order/wait-list identifiers. No fixture set or known-valid identifiers were supplied. The only universally runnable route is the deliberate error route; blank/loading shells can also be reached with invalid or unresolved identifiers, but they do not prove the successful journeys. Consequently the matrix below is source-observed and reachability-classified; the downstream visual-baseline ticket must capture runtime screenshots once fixtures are established.

## Executive conclusions

- The app exposes **12 public route patterns plus one deliberate error route**. There is no catch-all/404 UI; unmatched paths render the widget chrome with no page. Routes are ordered to keep the more-specific walk-in paths ahead of `/book/:shopIdOrRoute` (`sources/routeDefinitions.ts:1-14`, `sources/Routes.tsx:93-110`).
- The main booking journey is brand → shop/professional → services/add-ons or gift card → schedule → cart/checkout → reservation/gift-card receipt. It branches for single-shop/single-barber deep links, group appointments, any-professional selection, promotions, passcodes, waiting lists, walk-ins, assigned/unassigned gift cards, and multiple payment methods (`sources/Routes.tsx:57-63`, `sources/pages/shop/Shop.tsx:47-67`, `sources/pages/services/Services.tsx:46-119`, `sources/pages/schedule/Schedule.tsx:21-41`, `sources/contexts/CheckoutFlow/CheckoutFlowContext.tsx:31-97`).
- Many loading/error branches intentionally render **nothing** (`null` or Suspense `null`) rather than an error surface. Examples include route chunks, waiting-list loading, reservation loading, walk-in loading, and missing walk-in success data (`sources/Routes.tsx:93-95`, `sources/pages/waitingList/WaitingList.tsx:115-117`, `sources/pages/reservation/Reservation.tsx:173-175`, `sources/pages/walkinList/WalkinList.tsx:70-72`, `sources/pages/walkinList/WalkinListSuccess.tsx:36-38`). These blank states are parity requirements unless intentionally redesigned.
- Locale behavior is English/French by default, with Spanish enabled only under `clientBookingLocalization`; persisted locale wins, then browser detection when enabled, then English (`sources/contexts/Locale/LocaleContextProvider.tsx:28-53`, `:56-76`).
- Responsive behavior is primarily one mobile/widget layout rather than distinct page architectures. Global breakpoints are 375/1024/1440 px, document width behavior changes above 376 px, and most pointer differences are hover-capability media queries (`sources/styles/themes/default/index.ts:10-28`, `sources/styles/global/document.ts:28-31`). Query `viewMode=singleShop|singleBarber` changes navigation/edit affordances, not CSS (`sources/contexts/ViewModeContext/ViewModeContext.tsx:5-33`).
- Waiting-list status coverage is incomplete by construction: `removed`, `used`, and `rescheduled` render null; `selected` and `rescheduleSelected` have breakdown/CTA but no application component (`sources/pages/waitingList/WaitingList.tsx:31-50`, `:119-160`).

### Checkout phase/state machine

Checkout has explicit phases `initial`, user information, marketing consents, policies, payment information, processing booking, processing gift card, processing waiting list, waiting-list existence error, success, and error (files under `sources/contexts/CheckoutFlow/phases/`; dispatch is wired at `sources/contexts/CheckoutFlow/CheckoutFlowContext.tsx:35-37`, `:111-132`). Inputs can be blocked independently of loader state (`sources/contexts/CheckoutFlow/CheckoutFlowContext.tsx:22-35`). `webLogin && mobileCheckoutV2` chooses Checkout V2; otherwise legacy checkout opens (`sources/contexts/CheckoutFlow/CheckoutFlowContext.tsx:92-97`). Shop-scoped `payment-deposits-enabled` changes required-payment logic (`sources/contexts/CheckoutFlow/CheckoutFlowContext.tsx:52-61`, `sources/contexts/CheckoutFlow/phases/utils.ts:116`).

The baseline matrix must cover: no-payment booking, full card payment, deposit, gift-card redemption, promo/discount, assigned/unassigned gift-card purchase, waiting-list processing, payment processing, success, recoverable error returning to fallback phase, and blocked/loader presentation. Payment-method variants include saved/new card, Apple Pay, Cash App, and BNPL branches; feature gates appear at `sources/components/organisms/PaymentMethodForm/PaymentMethodForm.tsx:162-201` and `sources/components/molecules/Popup/popups/CheckoutFormPopup/usePaymentMethods.ts:44`.

## Edge cases and legacy quirks that must be decided explicitly

1. No 404 route or route-level error boundary is visible; invalid paths are blank.
2. Empty professionals resolve to perpetual seven-card skeleton; empty services resolve to blank page after skeleton.
3. Waiting-list `removed`, `used`, and `rescheduled` are explicitly unimplemented null states; selected states intentionally omit application content.
4. Gift-card info assumes a first gift card after loading and can fail on malformed data (`sources/pages/giftCardInfo/GiftCardInfo.tsx:19-38`).
5. Walk-in landing displays “Open now” independent of returned settings, then may display “walk-in list closed” below (`sources/pages/walkinList/components/WalkinListLanding/WalkinListLanding.tsx:81-88`, `:120-134`).
6. Walk-in landing drawer uses hard-coded mock service data; the next route independently loads repository services, so selections are not carried through (`sources/pages/walkinList/components/WalkinListLanding/WalkinListLanding.tsx:52-80`, `sources/pages/walkinList/WalkinListServices.tsx:59-75`).
7. Walk-in modal accepts optional email but source inspection is required to confirm whether its format is validated; screenshot baseline must test malformed optional email.
8. Reservation app-link popup is delayed five seconds and suppressed by cancel state, reschedule, or ads intent (`sources/pages/reservation/Reservation.tsx:50`, `:74-87`).
9. Route transitions intentionally delay exit mediation 100 ms and neighbor chunks preload after one second; visual automation must await stable state (`sources/Routes.tsx:78-91`).
10. Query `viewMode` is cast without runtime validation, so unknown values behave mostly like default while remaining non-null (`sources/contexts/ViewModeContext/ViewModeContext.tsx:18-31`).

## Runtime evidence gaps for the visual-baseline ticket

- valid identifiers for: multi-location brand, single location, rental shop, empty shop, named/any/passcode professional, assigned/unassigned gift-card-enabled shop, sale orders (single/group/cancelled/error/pending/gift-card), and every waiting-list status/attempt condition;

- provider sandboxes/mocks for Stripe card, Apple Pay, Cash App, BNPL, Rokt/Fluent ads, OAuth/OTP, geolocation and bot protection;
- API fault injection for initial load, empty success, 400-expired attempt, validation errors, checkout failures and mutation failures;
- screenshots at minimum widths 375, 376, 1024 and 1440, plus iframe and hover/non-hover modes;
- locale runs for en/fr/es with long strings, missing/partial translations, date/time and currency differences;
- stable-clock controls for cancellation windows, availability intervals, waiting-list expiry and the delayed app-link popup.

Until those fixtures exist, the correct classification is: **route shells and the deliberate error/unmatched paths are runnable; successful data-backed journeys and nearly all alternate states are source-inferred, though their rendering branches are directly observed in source.**

## Implications for downstream parity decisions

- Treat blank/null, perpetual-skeleton, and explicitly unimplemented states as named baseline cases, not accidental omissions.
- Split baseline capture by domain journey (booking, gift card, reservation management, waiting list, walk-in) and then cross-product only the relevant locale/view/flag/payment dimensions; a full Cartesian product would be wasteful.
- Lock whether parity means reproducing legacy quirks (hard-coded walk-in drawer, blank terminal statuses, no 404) or intentionally correcting them. Corrections belong in a separate decision/spec, because this inventory records what exists.
- Establish fixture IDs and flag snapshots before UI implementation tickets: without them, “runnable parity” cannot be verified even though the source contract is clear.
