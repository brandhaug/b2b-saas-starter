# Legacy dependency disposition inventory

## Scope and method

This inventory classifies the Booking App's declared direct dependencies, every imported `@water-web/*` surface, its local abstraction families, and the external providers visible in source. It uses only primary local sources: the legacy application and its workspace packages, plus the target repository's manifests, architecture, and implementation. “Recreate focused package” is reserved for a genuinely reusable technical seam; business behavior belongs in `@b2b-saas-starter/capabilities`, and browser-only composition belongs in `apps/booking`.

Primary entry points: [legacy manifest](/Users/hassan/Desktop/ssqu/recreate/apps/booking-app/package.json), [legacy app composition](/Users/hassan/Desktop/ssqu/recreate/apps/booking-app/sources/AppContextProvider.tsx), [target booking manifest](/Users/hassan/Desktop/beesolo%20HQ/b2b-saas-starter/apps/booking/package.json), [capability exports](/Users/hassan/Desktop/beesolo%20HQ/b2b-saas-starter/packages/capabilities/src/index.ts), and [target architecture](/Users/hassan/Desktop/beesolo%20HQ/b2b-saas-starter/ARCHITECTURE.md).

## Executive disposition

- Do **not** recreate any of the five `@water-web/*` packages wholesale. Their imports show UI, domain models, HTTP, persistence, analytics, feature flags, payment orchestration, and utilities crossing package boundaries.
- Reuse the target's existing `capabilities`, `db`, `auth`, `logger`, `email`, `env`, and `config` packages. Extend booking/catalog capability modules rather than importing legacy model classes.
- Recreate only one likely focused package: a provider-neutral **payments adapter** if Stripe and other tender orchestration must be shared by more than the public booking app. Keep Stripe Elements UI in `apps/booking`.
- Absorb the legacy view/component/context/hooks layer into `apps/booking`, rewritten against TanStack Router/Query, StyleX, Effect contracts, and target capability DTOs.
- Treat every analytics, advertising, social-login, maps, experimentation, and observability provider as optional configuration. Disabled integrations must not break local booking.

## Package plan

1. **Reuse unchanged:** `@b2b-saas-starter/db`, `auth`, `logger`, `env`, `config`, and the target React/Vite/TanStack/StyleX toolchain.
2. **Extend existing:** `@b2b-saas-starter/capabilities` for catalog, booking selection/session/scheduling/checkout/confirmation/appointment operations/notifications, plus explicit wait-list, gift-card/promo/tip behavior where parity requires it.
3. **Potentially create one package:** `@b2b-saas-starter/payments` only after a second consumer or server/browser adapter boundary is demonstrated. It exposes provider-neutral Effect services/schemas; Stripe implementation is isolated.
4. **Keep app-local:** booking UI, route/query adapters, localization, consent, theme/widget mode, provider script adapters, browser storage compatibility, Stripe Elements, and presentation utilities.
5. **Remove:** the `@water-web/view` facade, global types bucket, repository model graph, React Query v3/router v5/styled-components stack, proxy mutation observation, runtime locale backend, deep imports, and provider-coupled bridges.

## Decision

The new system should be organized around the target repository's existing domain capabilities, not around reconstructed legacy packages. Preserve behavior by porting invariants and provider-neutral contracts to their owners; preserve UI parity inside `apps/booking`; isolate optional providers behind adapters with disabled defaults. The only package need not already represented is a narrow payments seam, and even that should begin inside booking checkout until demonstrated reuse justifies extraction.
