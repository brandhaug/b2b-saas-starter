# Define Merchant Appointment Operations

Type: grilling
Status: resolved
Blocked by: 05

## Question

What command, authorization, validation, idempotency, revision, audit, and history contract should govern merchant-created Appointments and later edit, reassign, reschedule, cancel, complete, No Show, and External Collection actions, including newly entered versus existing Customer Details, Booking Party scope, stale tabs, races, and customer-visible consequences?

## Comments

### Resolution — 2026-07-30

BeeSolo exposes Appointment operations only to its authenticated Active Merchant Owner and to a System Operator acting through an explicitly audited Impersonated Merchant Session with that Owner's effective authority. Every lookup and command is Merchant-scoped; a missing or cross-Merchant Appointment has the same not-found result. A Merchant Access Hold, revoked authentication, or invalid impersonation blocks every command. Restricted Access blocks **Merchant-Created Appointment** and **Record Completed Appointment**, but continues to permit safe handling of existing commitments through edit, reschedule, cancellation, completion, No Show, outcome correction, External Collection, and explicit whole-party cancellation.

The command surface is explicit rather than a generic Appointment patch: create a Merchant-Created Appointment, Record Completed Appointment, Edit Appointment, Reschedule Appointment, Cancel Appointment, cancel a Booking Party's still-Scheduled Appointments, Complete Appointment, mark No Show, correct an Appointment outcome, and append an External Collection. BeeSolo exposes no reassign command because the Owner is its sole Provider. Every command derives Merchant and actor authority from the session, uses a server timestamp, carries a client-generated idempotency key, and—except initial creation—names the Appointment Revision the Owner viewed. Replaying the same key with identical input returns the recorded result; reusing it for different input is rejected. A stale revision changes nothing and returns the latest Appointment for deliberate review rather than silently merging or applying last-write-wins behavior. A command spanning multiple Appointments verifies every expected revision and commits all or none.

A Merchant-Created Appointment creates one Scheduled Appointment; recurrence belongs to the separate Appointment Series decision. The Owner selects one or more Active Services and either newly enters Customer Details or selects an existing Customer Directory result. Selecting an existing result copies its preferred details into the draft; editing that copy affects only the new Appointment. Both paths require a customer name, allow email and phone to be absent, and create the same immutable per-Appointment Customer Details snapshot. In the same transaction, creation conservatively matches or creates the durable Merchant-scoped Customer Record, links the Appointment, and contributes a new observation under [Define the Customer Directory and Privacy Contract](09-define-customer-directory-and-privacy.md). With no contact channel, the composer states that customer notifications cannot be sent. Merchant creation snapshots the current prices of the selected Services and does not permit arbitrary totals, discounts, or surcharges.

Merchant creation is not constrained by customer cancellation or reschedule cutoffs, Minimum Notice, or Booking Horizon. Placement outside current working time or across Blocked Time is permitted only after an explicit conflict warning; an optional override reason enters Appointment History. It atomically invalidates affected Time Slot Holds but can never overlap another non-terminal Appointment for the sole Owner-Provider. If customer confirmation and a Merchant create or reschedule command race for the same occupied interval, the first committed Appointment wins. Customer-first makes the Merchant command fail with the conflicting Appointment; Merchant-first invalidates the hold and makes customer confirmation return `slot_lost`. Neither path can create overlapping Scheduled Appointments, and neither channel has standing priority.

Normal New Appointment accepts a start at the current instant or in the future. **Record Completed Appointment** is the separate, explicit late-entry path for an already-finished visit such as an omitted walk-in. It requires past start and end instants, Customer Details, selected Services, a completion reason, and an External Collection choice, and it creates the Appointment directly as Completed with history recording when and by whom it was entered after service. A historical overlap receives a strong warning but does not block the record because terminal Appointments reserve no time. This path cannot manufacture past Cancelled or No Show lifecycles and is not a bulk-import surface.

**Edit Appointment** changes only Customer Details or the optional customer note. A successful edit increments the Appointment Revision and records before-and-after facts without rewriting earlier snapshots. Changing only name or note preserves existing Confirmation access. Changing email or phone atomically revokes every existing Confirmation access grant and offers a fresh secure Confirmation link to the new destination; suppressing that send leaves the old grants revoked and sends no replacement.

Changing start time, selected Services, duration, resolved Service Buffers, or customer-visible total is **Reschedule Appointment**, including a Service change whose start time stays fixed. The original Scheduled Appointment remains intact while replacement work is incomplete, invalid, expired, or loses a race. Commit atomically validates the complete replacement occupied interval, applies the replacement to the same Appointment identity, advances its revision, preserves before-and-after history, invalidates affected Time Slot Holds, supersedes stale reminders, and creates the customer consequence chosen for the new revision. Merchant rescheduling has the same public-window overrides and no-overlap invariant as Merchant creation. A time-only reschedule may retain an already snapshotted inactive Service and preserves the Appointment's agreed price despite catalog changes. Adding, removing, or replacing a Service requires an Active Service, recalculates the entire replacement total from current catalog prices, previews that total before commit, and retains the prior accepted total in history.

Confirmation or Merchant creation normally produces Scheduled. Only Scheduled may ordinarily become Completed, Cancelled, or No Show. Complete and No Show are unavailable before the Appointment starts. Rescheduling changes facts rather than introducing a Rescheduled status. Cancelled is irreversible: if the customer still needs service, the Owner creates a new Appointment. Completed and No Show cannot return to Scheduled, but may be corrected to one another through a dedicated **Appointment Outcome Correction** with a required reason, new revision, and preserved erroneous and corrected outcomes. No Show creates no automatic charge or outbound customer notification.

Cancellation defaults to one Appointment. When the Appointment came from a composite Booking Party, the Owner may explicitly choose all still-Scheduled Appointments from that party; the whole-party command checks every revision and commits atomically, while every other post-confirmation operation remains Appointment-scoped. Cancellation immediately releases occupied time and supersedes unsent reminders. It requires the Merchant-private category Customer Requested, Merchant Unavailable, Duplicate or Error, or Other; Other also requires a private note. Internal reasons never appear to customers automatically, while a separate optional customer message may appear in the notification and Confirmation. One reason and message govern an atomic whole-party cancellation.

**Complete Appointment** normally pairs service outcome with the Pay In Person workflow. Once the Appointment has started, the completion surface defaults to recording the full snapshotted total as an External Collection with the Owner's chosen method, but also permits Already Recorded or Collect Later. When the Owner enters a new collection, completion and the collection entry commit atomically. Completed describes the service outcome and never by itself means paid.

External Collection is an append-only Appointment ledger of value actually Collected or Returned outside BeeSolo. Each entry has a positive amount in the Appointment currency, method (`cash`, `card_terminal`, `bank_transfer`, or `other`), actual collection time, actor, and optional note or reference. Multiple and partial entries are allowed, but net collected value remains between zero and the Appointment Price Snapshot total; launch therefore records neither tips nor overpayment. A return cannot exceed previously collected value. Entries may follow any Appointment Status and are never edited or deleted; correction uses an offsetting entry with a required reason. External Collection never becomes a Payment, Payment Attempt, verified receipt, automatic charge, or platform refund.

External Collection never blocks cancellation. When net value exists, cancellation asks whether value was actually returned. If so, cancellation may atomically append a matching Returned entry; otherwise it commits without changing collection history. BeeSolo never assumes that cancelling an Appointment moved cash or reversed a separate-terminal transaction.

Merchant creation, rescheduling, and cancellation queue their ordinary customer notification by default when an eligible contact channel exists. The Owner may explicitly choose Don't Notify after confirming the customer already knows; the suppression reason is preserved in Appointment History. Editing Customer Details sends no general update, although a changed destination offers a fresh Confirmation as described above. Completion, No Show, outcome correction, and External Collection produce no automatic outbound message. Notification submission or delivery failure never rolls back the Appointment Command. The later Transactional Notification Workflows decision owns exact channel, timing, wording, retry, and delivery behavior.

The capability-protected Confirmation view always resolves current customer-visible facts and Appointment Status from the latest revision, independently of whether notification was sent or delivered. Ordinary reschedule, cancellation, completion, No Show, and outcome correction preserve existing Confirmation access so the same secure link shows the current result. Customers never see Merchant-private reasons, actors, complete Appointment History, or External Collection details.

Every successful command appends exactly one immutable Appointment History entry with command and operation identity, actor and any impersonating System Operator, server timestamp, prior and resulting revision, changed before-and-after facts, reason where supplied or required, and Appointment Notification Choice where relevant. Whole-party cancellation writes one entry per affected Appointment linked by one shared operation identity. Idempotent replay adds no duplicate Appointment, history, audit event, notification intent, Confirmation grant, or External Collection entry. Rejected stale or invalid commands add no Appointment History; appropriate security and operational telemetry may record those attempts separately.
