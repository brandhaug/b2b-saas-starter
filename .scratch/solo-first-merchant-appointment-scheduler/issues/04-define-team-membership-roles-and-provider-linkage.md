# Define Team Membership, Roles, and Provider Linkage

Type: grilling
Status: resolved
Blocked by: 02

## Question

What invitation, enrollment, revocation, role-change, account-recovery, and audit lifecycle should govern Team Plan employees; what exact permissions belong to Owner, Manager, and Employee; and how can each Merchant Member be optionally linked to a bookable Provider without Provider status granting Merchant App authority?

## Comments

### Resolution — 2026-07-29

Team authority is expressed only through an Active Merchant Membership and its fixed Merchant Role. Provider status and Merchant Member–Provider Linkage never grant Merchant App access. At launch, one authenticated person may have only one Pending or Active Merchant relationship across the platform, preserving the current server-resolved Merchant boundary without introducing a Merchant switcher. Every Merchant has exactly one Owner.

The role matrix is fixed as follows:

| Capability                                                                                                                                   | Owner                         | Manager                 | Employee             |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ----------------------- | -------------------- |
| View and operate all Shop appointments, Appointment Series, customers, Walk-in Queue entries, Waiting List entries, and External Collections | Yes                           | Yes                     | Yes                  |
| Create, assign, reassign, reschedule, cancel, complete, or mark no-show across the Shop                                                      | Yes                           | Yes                     | Yes                  |
| Manage Business Details, Public Page Status, Services, Providers, Schedule Rules, Booking Policies, and notification settings                | Yes                           | Yes                     | No                   |
| Edit the member's own linked Provider display profile and availability                                                                       | Yes                           | Yes                     | Yes                  |
| Change Provider Status, Service eligibility, or Member–Provider Linkage                                                                      | Yes                           | Yes                     | No                   |
| Invite, resend, revoke, or cancel Pending Employees                                                                                          | Yes                           | Yes                     | No                   |
| Invite Managers or manage Manager memberships                                                                                                | Yes                           | No                      | No                   |
| Promote, demote, or initiate Merchant Ownership Transfer                                                                                     | Yes                           | No                      | No                   |
| View operational reports                                                                                                                     | Yes                           | Yes                     | No                   |
| Export Merchant, customer, appointment, or audit data                                                                                        | Yes                           | No                      | No                   |
| View plan, renewal, billed quantity, SMS Balance, and SMS usage                                                                              | Yes                           | Yes                     | No                   |
| Change subscription, payment methods, SMS funding, or automatic top-up                                                                       | Yes                           | No                      | No                   |
| Manage API tokens, webhooks, integration credentials, or other long-lived secrets                                                            | Yes                           | No                      | No                   |
| Inspect Merchant Audit Events                                                                                                                | All permitted Merchant events | Operational subset only | No general audit log |
| Delete or irreversibly anonymize Merchant data or the Merchant                                                                               | Yes                           | No                      | No                   |
| Manage the person's own password, verified email, profile, and sessions                                                                      | Self only                     | Self only               | Self only            |

Employees may therefore operate the whole Shop ledger but cannot configure other Providers or the Merchant. A linked Employee may edit only their own Provider display profile and availability; Service eligibility, Provider Status, and linkage remain Owner-or-Manager decisions. Managers can run daily operations and bookable configuration, manage Employees, and view operational reports, but cannot exercise financial, ownership, Manager-governance, export, credential, or destructive authority. Owner-only financial, ownership, export, credential, and destructive actions require recent password reauthentication.

A Merchant Invitation is a normalized-email-bound, single-use, seven-day offer naming either Manager or Employee. An Owner may invite either role; a Manager may invite only an Employee; an Employee cannot invite. A Merchant may have only one live invitation per email. Resending the same offer rotates its token without creating another seat claim. Changing the intended role revokes the old offer and creates a new one. Invitations may be revoked before acceptance. Expired, revoked, accepted, and role-replaced invitations are terminal and retained for audit.

Inviting an existing Active or Pending member of the same Merchant is rejected. The inviter is never told whether the address belongs to another Merchant. An offer may be delivered to a person who already has a relationship with another Merchant, but acceptance is blocked by the one-Merchant rule and the invitation remains usable until expiry if the conflict is resolved. Acceptance is atomic and idempotent, so concurrent or repeated attempts create at most one membership episode.

The invitee must authenticate as a Better Auth identity whose verified email exactly matches the invitation. An existing identity signs in; a new identity sets a password and verifies the invited address. Acceptance consumes the invitation and creates a Pending Membership with no Merchant authority. During trial, or when an already-paid vacant Team slot exists, it activates immediately. Otherwise activation waits for confirmed prorated seat payment as defined by the Merchant Subscription lifecycle. A failed or abandoned charge leaves no authorized member; the Owner, or a Manager when the intended role is Employee, may cancel the Pending Membership without creating a billed seat.

Merchant Membership has exactly three states: Pending, Active, and Revoked. Active is the only state that grants role authority. Revocation is permanent historical state and immediately invalidates the membership's Merchant App sessions. Rehiring the same authenticated person requires a new invitation and creates a new membership episode tied to the same identity rather than restoring the old role or access.

Only the Owner may promote Employee to Manager or demote Manager to Employee. Managers cannot change roles. The Owner cannot change their own role through an ordinary role change. A role change is immediate, retains the membership episode and paid seat, leaves Provider linkage unchanged, and records actor, old role, new role, reason, and timestamp. Promotion requires recent Owner password reauthentication.

Ownership uses a separate Merchant Ownership Transfer. The current Owner may offer ownership only to an Active Manager after recent password reauthentication. The target must explicitly accept the single-use offer within 24 hours with their own recent password reauthentication; the current Owner may cancel it before acceptance. Acceptance atomically makes the Manager the sole Owner and the previous Owner a Manager, moving billing and all Owner-only authority immediately without changing either Provider linkage. Initiation, acceptance, cancellation, expiry, and both role transitions are audited.

An Owner may revoke any Manager or Employee; a Manager may revoke an Employee only. Managers and Employees may voluntarily leave after explicit confirmation. The Owner can neither leave nor be revoked until ownership is transferred. Pending Members may be cancelled by the Owner, or by a Manager when the intended role is Employee. Revocation or departure takes effect immediately even when only the Owner remains; the Merchant stays on Team and at its two-seat billing floor until it fills the vacancy or completes the already-defined Team-to-Solo downgrade. Every revocation, departure, or cancellation records actor, subject, role, administrative-versus-voluntary source, reason, and timestamp.

Merchant Member–Provider Linkage is an optional, merchant-consistent one-to-one relationship: an Active Member links to at most one Provider, and a Provider links to at most one Active Member. Either entity may exist without the other. The link supplies self-service context such as “my schedule” and “my availability” but grants no role or Merchant authority. Owner and Manager may create, replace, or remove it subject to Solo/Team readiness and scheduling invariants; Employee cannot manage linkage. Every change retains auditable before-and-after linkage facts.

When a linked Membership is revoked or the member leaves, one atomic operation revokes authority, invalidates sessions, removes the link, and marks the Provider Inactive. Historical and future Appointments remain assigned for an Owner or Manager to reassign, reschedule, or cancel, but the Provider receives no new work. Public Page Status intent is preserved; if the departure removes required Provider eligibility, Booking Readiness makes the page effectively unavailable. An Owner or Manager may later reactivate the unlinked Provider deliberately if the person remains bookable without Merchant App access. Ordinary unlinking, role changes, and temporary security holds do not themselves change Provider Status.

Suspected compromise uses a reversible Merchant Access Hold rather than another Membership state. Owner may place or clear a hold on Managers and Employees; Manager may do so for Employees; an authorized System Operator may hold any Membership, including the Owner, after a verified security report. A hold immediately invalidates sessions and blocks Merchant authority while leaving the Membership Active and billed with the same role, Provider linkage, and Provider Status. Clearance requires credential recovery, verified-email control, fresh authentication, a reason, and a security audit event.

Merchant authentication remains verified email and password only for this destination. Mandatory TOTP, backup codes, and MFA enrollment are out of scope. Ordinary password recovery uses an enumeration-safe email flow with a single-use 30-minute token. Completion against the same verified identity changes no Membership, role, or Provider linkage and revokes all identity sessions. No Owner or Manager can reset another person's credentials.

A self-service sign-in-email change requires recent password reauthentication, confirmation through both the current and new addresses, normalized-address uniqueness, notifications to both addresses, and revocation of existing sessions. It changes no Membership, role, or Provider linkage. Without access to the current mailbox, a Manager or Employee is recovered by revoking the old Membership and inviting a new verified identity.

An Owner who loses the current mailbox uses support-assisted Owner Account Recovery. It requires business and subscription-control evidence, two System Operator approvals, a 72-hour security hold, and notice to the old email and every Active Manager. When an Active Manager exists, recovery transfers ownership to that Manager after the hold. Otherwise, support replaces the identity attached to the existing Owner Membership only after verifying the claimant's new email. Completion invalidates old sessions and recovery artifacts. The audit record stores evidence categories, approvers, notices, timestamps, and the resulting ownership or identity transition, never raw identity documents.

Team-security Audit Events are append-only and retained for two years, matching the existing impersonation audit horizon. They cover every invitation transition, enrollment result, Pending activation or cancellation, Membership activation, revocation, or departure, role change, Ownership Transfer transition, Provider-link change, Access Hold transition, password-recovery security event, and Owner Account Recovery step. Each event preserves stable Merchant, actor, subject, Membership, Provider, and correlation identifiers; applicable before-and-after values; result, reason, timestamp, and System Operator provenance. Invitation or reset secrets, passwords, session tokens, raw identity documents, and full payment credentials never enter the audit record.

The Owner can inspect all permitted Merchant-scoped events except restricted recovery evidence. Managers can inspect operational Membership and Provider-link events but not billing, Owner-recovery, or credential-security details. Employees receive notifications for actions affecting themselves but have no general audit-log access. Authorized System Operators can inspect the global security record. Audit attribution survives Membership revocation and later identity redaction; ordinary reads and navigation do not emit individual Audit Events.

### Scope amendment — 2026-07-29

This resolved design is deferred in full beyond the BeeSolo launch destination. It remains future reference, but no invitation, multi-member Membership, Manager or Employee role, Member–Provider Linkage, ownership-transfer, team recovery, or team-audit implementation belongs in the current delivery program.
