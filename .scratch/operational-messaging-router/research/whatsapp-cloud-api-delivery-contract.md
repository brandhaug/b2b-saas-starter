# WhatsApp Cloud API Delivery Contract

Research date: 2026-07-27  
Scope: platform-owned WhatsApp Business Account (WABA) and shared sender for Romanian and English Booking Product Operational Notifications  
Source policy: current first-party Meta/WhatsApp material and official Cloudflare documentation. Meta's developer site returned HTTP 429 during this pass, so where possible its official Meta-owned Postman collection, SDK, and sample repository are used as accessible primary sources. Any fact not verifiable from those sources is marked as a gap rather than filled from third-party guidance.

## Decision summary

The proposed shared platform identity is technically viable, but it is not a transparent per-Merchant sender. The WhatsApp profile must truthfully identify the platform, must not impersonate a Merchant, and every controlled template should identify the relevant Merchant in its approved transactional content. The platform must possess the recipient's phone number and WhatsApp opt-in, honor opt-out, and send an approved Romanian or English Utility template whenever it initiates the notification.

Meta acknowledges an accepted submission with a `wamid`; that is not delivery. Delivery truth arrives asynchronously through signed webhooks (`sent`, `delivered`, `read`, or `failed`), and callbacks can arrive out of order. Meta documents no outbound idempotency key and no consent or reachability preflight. Consequently, the router must own semantic deduplication, consent evidence, ambiguous-submission handling, monotonic status projection, and terminal/transient error policy.

WhatsApp currently bills per delivered message, not per accepted submission. Romania Utility list price observed from WhatsApp's live calculator on 2026-07-27 was **EUR 0.0239** for the first 100,000 charged messages/month, with lower volume tiers after that. This is mutable configuration, not a code constant. Utility messages sent in response to a user inside the current 24-hour service window are presently uncharged; ordinary booking notifications must be budgeted as charged when no such window is known to be open. [WhatsApp Business Platform pricing](https://whatsappbusiness.com/products/platform-pricing/)

Cloudflare Workers can implement the integration directly with standards-based `fetch`, receive HTTPS webhooks, verify HMAC-SHA256 over the raw request body using Web Crypto, and keep tokens/app secrets in secret bindings. No Node-only Meta SDK is required.

## Proposed provider boundary

The provider adapter should expose evidence rather than pretend WhatsApp offers exactly-once delivery:

1. `checkEligibility` combines local opt-in/suppression, approved template version, provider/account/template health, and platform kill switch. It must not claim to query WhatsApp recipient reachability.
2. `submitTemplate` consumes an immutable semantic notification id, recipient E.164 number, provider template id/name/locale and typed variables. It returns either `rejected`, `accepted(wamid)`, or `submissionUnknown`; it never maps HTTP 200 to delivered.
3. `ingestWebhook` verifies the raw-body signature, durably records/deduplicates the event, then projects status monotonically using provider timestamps.
4. `classifyFailure` is an effective-dated operational table sourced from the current Meta error reference. Only explicitly transient failures retry. Explicit rejection or terminal `failed` can activate SMS fallback once; delayed/unknown cannot.
5. `quote` reads effective-dated rate configuration for recipient market/category/free-window/volume tier. `actualProviderCost` is reconciled from delivered/pricing evidence, never inferred from submission.

## Provisioning and pilot gates surfaced by this research

- Verify the platform's Meta business portfolio and establish the WABA, payment method and truthful platform display name.
- Acquire a dedicated platform-controlled number capable of SMS/voice ownership verification; register it with a separately stored six-digit 2FA PIN.
- Create a least-privilege System User token, App Secret and webhook verify token in Cloudflare secret bindings; pin a Graph version.
- Register the HTTPS callback, subscribe the app to the WABA, and prove raw-body HMAC verification, durable capture, duplicate handling and out-of-order handling.
- Submit eight controlled templates (four appointment events × Romanian/English), verify Utility category and approval, and test pause/disable/rejection handling. Only confirmation may contain the secure Confirmation link under the settled map decision.
- Confirm the platform profile plus Merchant-in-content design is understandable and not misleading; retain Merchant authorization and customer opt-in evidence.
- Fetch and approve current Romania rate cards immediately before the pilot; seed an effective-dated rate rather than copying the observed EUR 0.0239 indefinitely.
- Exercise synchronous rejection, accepted-then-failed, delivered, missing callback, callback replay, quality degradation, rate limiting, kill switch and SMS fallback in seed/pilot gates.

These should graduate to provisioning/verification tasks or remain runtime policy, not be guessed during implementation:

- Meta Business Verification evidence requirements and review duration for this actual legal entity.
- Approval of the proposed platform display name and each Romanian/English Utility template.
- Current account-specific messaging/throughput/pair limits and sandbox recipient cap shown after setup.
- Current canonical transient/terminal error-code table and exact webhook retry schedule at implementation time.
- Current Meta processing/retention terms applicable to this account and Cloud API region.
- Any pricing change whose effective date falls after this research date.
