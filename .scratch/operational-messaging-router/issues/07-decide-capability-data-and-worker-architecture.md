# Decide the Capability, Data, and Worker Architecture

Type: grilling
Status: resolved
Blocked by: 04, 06

## Question

How should the existing Notifications capability, transactional outbox, shared D1 boundary, booking-events Queue, Background Worker, Merchant App, Operations App, provider callbacks, cron recovery, and optional-provider local adapters be extended so the Operational Messaging Router remains a deep internal module without adding a seventh Worker or duplicating booking behavior?

## Comments

### Resolution — 2026-07-28

The existing **Notifications** bounded context becomes the sole owner of the Operational Messaging Router's application policy and lifecycle. It owns Notification Intents, route selection, Messaging Balance reservations and ledger effects, Provider Evidence projection, reconciliation, and terminal outcomes. Booking continues to own Appointment transitions and supplies only the triggering Appointment facts. The Background Worker, API Worker, Merchant App, and Operations App remain transport and actor adapters; none duplicates routing or delivery policy.

`notification_intents` becomes the authoritative durable mobile-messaging work record. It is extended through normalized owned records for Delivery Routes, Submission Attempts, Provider Evidence, Messaging Balance Reservations and Ledger Entries, Chargeable Deliveries, Provider Messaging Costs, suppression and channel controls, and reconciliation facts. D1 remains the shared transactional authority. No second messaging outbox or separate database is introduced, and queue payloads never become authoritative state.

Notifications exposes a typed intent-preparation boundary. Booking supplies the purpose, current source identity and version, recipient and permission snapshot, controlled content facts, semantic deduplication key, due time, and correlation facts; Notifications validates them and returns opaque D1 mutations that Booking composes into its existing atomic batch. Booking adapters no longer construct or update router tables directly. Fresh manual sends use the same preparation boundary inside a Notifications-owned command and never reopen an old intent.

The existing `booking_outbox` remains authoritative only for independent transactional email and signed Platform Webhook delivery. It is a sibling consequence of the same Booking transaction, correlated with mobile work by source identity and trace ID, but it no longer stores `notificationIntentId`, WhatsApp fields, or mobile outcome logic. Email/webhook progress can neither complete nor fail a mobile Notification Intent, and mobile routing can neither delay nor alter email/webhook work. The legacy console-WhatsApp outbox branch, columns, processing code, and linkage are removed rather than retained as historical delivery evidence because console capture never represented provider delivery.

A Reminder is represented only by a Scheduled Notification Intent with a due time and source version. Messaging reminders are not mirrored into `scheduled_work`. Domain changes atomically supersede obsolete intents; the Background Worker cron discovers due or recoverable intents from Notifications-owned data. A delayed queue message may reduce latency but is only a disposable wake-up.

The existing `booking-events` Queue and Background Worker are reused. A versioned, PII-free discriminated envelope identifies either `booking-outbox` work by outbox ID or `notification-intent` work by intent ID. The consumer temporarily accepts the legacy `{ outboxId }` shape during migration, dispatches each kind to its owning capability, and acknowledges or retries without interpreting business state. The five-minute cron independently scans both durable stores, so failed queue publication loses latency rather than work. No seventh Worker or second Queue is added.

Intent execution uses a short lease and write-ahead protocol. A D1 transaction claims due work, rechecks current source version, Merchant and notification-type enablement, global controls, suppression, content and destination eligibility, provider configuration, and available balance, then atomically acquires the one reservation. Before any external request it appends the immutable Submission Attempt with a stable idempotency key and commits. The provider call occurs outside D1. Its response is ingested as Provider Evidence in a new transaction that idempotently projects the route and performs any permitted retry, fallback, release, delivery charge, or terminal transition. A crash after write-ahead is conservatively recovered as Submission Unknown and enters reconciliation rather than blind resend or fallback.

Notifications defines provider-neutral Effect ports for submission, callback verification, provider querying, and provider-cost facts. Internal Meta and SMSO.ro adapter modules implement those ports and can be shared by the API and Background Workers without entering the public Notifications application interface. Development and test select deterministic console/fake adapters that redact destinations and secrets and record a distinct `captured` outcome, never provider acceptance or delivery. Non-local runtimes without required configuration select explicit `needs_configuration`; they never silently use fake delivery.

Provider callbacks enter through provider-specific, unversioned routes on the existing API Worker, outside the Merchant-scoped `/v1` Platform API contract and reference documentation. The edge verifies the raw request before decoding, normalizes it to Provider Evidence, calls Notifications for a durable idempotent commit, and best-effort publishes an intent wake-up. It returns success only after durable ingestion. Meta callbacks may contribute authoritative evidence under the provider contract; SMSO.ro callbacks remain untrusted hints until polling confirms them. The API Worker gains the shared queue binding but owns no lifecycle decisions.

The Merchant App uses a narrow Merchant-scoped Notifications facade for messaging settings, Messaging Balance and transaction views, Appointment delivery summaries, and fresh manual intents. The Merchant edge resolves session and role authority, while every query and command remains constrained by Merchant ID. The Operations App reaches an Operator facade through the Operations capability: Operations owns Operator Permission checks, reason capture, preview and confirmation, and audit orchestration; Notifications alone mutates kill switches, adjustments, reconciliation, and routing state. Both surfaces read purpose-built projections and never raw provider payloads or router tables.

Cutover is additive and forward-only without dual mobile processing: deploy schema and a consumer that accepts both wake-up envelopes; switch producers to independent email/webhook outbox work plus router-owned mobile intents; remove the legacy WhatsApp outbox branch; and migrate only genuinely pending future reminders for which no provider submission could have occurred. Historical confirmation, cancellation, or reschedule messages are never replayed because of the migration.

The exact migrations, Effect services and typed errors, queue schemas, callback paths and security controls, provider request contracts, read projections, reconciliation schedules, and deploy ordering remain with the downstream security and implementation-program tickets. Resolving this architecture makes those details constrainable but does not graduate them from the map's fog until the security decision also resolves; no new ticket is required now.
