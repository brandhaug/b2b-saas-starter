# Cal.com Canonical Booking Terms: Focused First Pass

Research date: 2026-07-09
Source repo: `/Users/hassan/Desktop/cal.shit/cal.diy`

## Executive Summary

Cal.com/Cal.diy appears to treat **User**, **Team**, **Organization**, **Membership**, **Event Type**, **Host**, **Attendee**, **Booking**, **Schedule**, **Availability**, **Profile**, `username`, and `slug` as canonical booking-product terms.

For our current question, the closest Cal.com equivalent to "provider/staff/professional" is **Host**. A `Host` is a user assigned to an event type, optionally with a host-specific schedule, membership, group, and location. Cal.com also uses **team member** in UI/API documentation for team scheduling, and older booking code frequently uses **organizer**, but the durable schema/API term for the bookable person on an event type is `Host`.

Recommendation for Beesolo: use **Provider** as our product/domain term if we want a solopreneur-service-market fit, with **Host** as a useful implementation precedent from Cal.com rather than the name we copy. "Provider" reads better for barbers, consultants, coaches, stylists, and solo operators; "Host" reads meeting-centric. Avoid **Staff Member** as canonical because it implies employment and team-first setup. In a Solo plan, the Merchant is the default Provider. In a Team plan, the Merchant can add more Providers.

## Mapping to Beesolo Planning

- **Merchant public slug**: Cal.com's public route model supports `/:user` and `/:user/:type`, where `user` is a username/profile identity and `type` is an event type slug. Our `www.<domain>/:merchantSlug` and `www.<domain>/:merchantSlug/booking` shape can borrow the public identity idea but should call it `merchantSlug`, not `username`, because our first-class public identity is a business/merchant, not necessarily an account user.
- **Solo plan**: In Cal.com, a solo booking page can be a User/Profile with Event Types and Schedules. For us, Solo should be Merchant -> default Provider -> Services -> Schedule/Availability -> Bookings. The default Provider can be hidden in UI until the merchant needs team features.
- **Team plan**: Cal.com adds Team, Membership, Host, team event types, and scheduling modes such as ROUND_ROBIN/COLLECTIVE/MANAGED. For us, Team plan should add Providers and Membership/Roles; team scheduling can come later as explicit routing/assignment behavior.
- **Provider vs Host**: Cal.com makes `Host` the canonical event-assigned bookable person. Beesolo should still use **Provider** because the product is service-business/solopreneur-first, not meeting-host-first. Internally, Provider should play the same role Cal.com's Host plays: a bookable person attached to services, availability, bookings, and optional team membership.
- **Avoid Staff Member**: Cal.com's durable schema does not need "Staff Member" as the core booking term. It uses User/Membership/Host/TeamMember. For Beesolo, "Staff" should be UI copy only if a merchant operates as an employer; it should not be the canonical model.
- **Attendee/Customer**: Cal.com uses Attendee for the person attending a booking. Beesolo can use **Customer** externally and possibly **Attendee** only in lower-level scheduling internals if needed. Since the product is appointment/service oriented, Customer is probably clearer.
- **Event Type vs Service**: Cal.com's Event Type is the bookable template. Beesolo should likely use **Service** as the merchant-facing term, with an internal Booking Type only if we later need non-service appointment templates.

## Open Ambiguities

- Cal.com uses **Host** in schema/API event-type assignment, but older booking tests and email code use **organizer** heavily. This looks like mixed historical language rather than a single canonical product term.
- **Team Member** appears in event-type docs and scheduling docs, while `Membership` is the durable role relation. Team Member is useful UI language, but it is not as precise as Host for "person who can receive this booking."
- Cal.com's `Team` model also represents organizations via `isOrganization` and parent/children relationships. That is powerful, but Beesolo should avoid copying that table shape too early if our planning language separates Merchant, Team, Brand, and Shop.
- Routing Forms are present in docs and booking input, but the repo also contains comments saying routing forms were removed in some Cal.diy surfaces. Treat Routing Form as a later assignment/routing feature, not first-slice terminology.
- `username`, `slug`, and `profile.username` overlap in Cal.com. Beesolo should deliberately keep `merchantSlug` for public pages and avoid making account usernames part of public booking URLs.
