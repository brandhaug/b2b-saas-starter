# Start a capability-protected Booking Session

Type: task
Category: enhancement
Status: ready-for-agent
Blocked by: 15
Parent: 10

## What to build

Turn the public booking CTA into a resumable, anonymous, server-owned Booking Session that is private to the browser that created it. A URL alone must never reveal or authorize private booking state.

## Acceptance criteria

- [ ] Entering a Published Merchant's Booking App creates or resumes a D1-backed Booking Session through a first-party server capability call rather than the Platform API.
- [ ] Session creation assigns the fixed `pay_in_person` Checkout Path on the server; browser commands cannot submit or replace it.
- [ ] Each Session has an opaque route ID and an independent 256-bit random browser capability; D1 stores only its hash.
- [ ] Each capability cookie is session-specific, host-only to the public origin, scoped to the exact Merchant booking path, `HttpOnly`, production-`Secure`, and `SameSite=Lax`.
- [ ] The secret never appears in a URL, browser JavaScript, local storage, logs, analytics, queue payloads, or persisted plaintext.
- [ ] Private access validates the Session ID, capability, Merchant slug, lifecycle, idle expiry, and absolute expiry without disclosing which check failed.
- [ ] Unfinished Sessions expire after thirty minutes without activity and two hours absolutely; expired Sessions cannot be resumed.
- [ ] Private mutations enforce same-origin evidence, Fetch Metadata when present, non-form content types, and per-session rate limits.
- [ ] Unpublishing blocks new Sessions immediately but does not by itself invalidate an existing short-lived Session whose selected facts remain valid.
- [ ] Capability, cookie, expiry, origin, cross-Merchant, rate-limit, generic `404`, safe `410`, and concurrent-session behavior are covered by tests.

## Agent Brief

**Category:** enhancement
**Summary:** Replace the fixture-backed booking flow with a resumable, anonymous Booking Session protected by a browser-held capability.

**Current behavior:** Public booking is a client-side prototype with scenario state. It has no durable Session, server authorization, Merchant-scoped cookie capability, or private-state protection.

**Desired behavior:** Entering a Published Merchant creates or resumes a D1-backed Booking Session through a first-party capability. A route ID alone never authorizes private state; the browser's random capability is stored only as a hash and is carried by a narrowly scoped secure cookie.

**Key interfaces:**

- Booking Session capability — creates, resumes, expires, and authorizes the anonymous session without using the Platform API.
- Session capability cookie — is host-only, `HttpOnly`, production-`Secure`, `SameSite=Lax`, and scoped to the exact Merchant booking path.
- Private Booking mutation guard — validates Session and Merchant lifecycle, same-origin evidence, Fetch Metadata when present, content type, and rate limits with non-disclosing errors.

**Acceptance criteria:**

- [ ] Published-page entry persists and resumes only the valid Merchant-scoped Session with server-assigned `pay_in_person` checkout behavior.
- [ ] Route ID and 256-bit capability are independent; only the capability hash is persisted and the secret never reaches URLs, JavaScript, storage, logs, analytics, queues, or persisted plaintext.
- [ ] Idle and absolute expiry, unpublishing behavior, origin controls, private mutation limits, and generic invalid-session behavior follow the settled contract.
- [ ] Capability, cookie, lifecycle, cross-Merchant, concurrent-session, and failure-path tests verify the boundary.

**Out of scope:**

- Provider or Service selection, availability, holds, quotations, checkout, and confirmation.
- Customer identity or Platform API authorization.
