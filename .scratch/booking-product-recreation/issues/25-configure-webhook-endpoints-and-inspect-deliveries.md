## Agent Brief

**Category:** enhancement
**Summary:** Replace the Workspace-era webhook configuration surface with the settled Merchant-scoped Platform API v1 endpoint lifecycle and safe Delivery Attempt history.

**Current behavior:**
The repository has a useful Starter-era baseline: Workspace-scoped webhook storage, list and create capability behavior, internal disable and signing-secret rotation operations, URL SSRF checks, delivery-attempt persistence, audit emission, and background dispatch support. The public API, however, exposes only a Workspace-slug create route guarded by the generic `write` scope. Its endpoint representation uses `enabled`, arbitrary `events`, and an aggregate `successRate`; creation does not disclose the generated signing secret; and the public contract has no patch, disable, rotation, or Delivery Attempt history routes. Storage and DTOs also lack several fields required by the settled Booking Product contract.

**Desired behavior:**
Platform API v1 should expose the settled Webhook Endpoint collection, creation, patch, idempotent disable, signing-secret rotation, and per-endpoint Delivery Attempt history operations. Bearer-token verification must derive the Merchant boundary and every route must require `webhooks:manage`, use the standard `data`/pagination envelopes and typed errors, and make unknown and cross-Merchant resources indistinguishable. Endpoint resources must use the `active`/`disabled` lifecycle, preserve disabled endpoints as terminal, validate the closed Appointment event vocabulary, and never expose inferred health or signing material on ordinary reads.

Creation and rotation must disclose a newly generated signing secret exactly once while ordinary DTOs, persistence-facing projections, logs, errors, audits, and delivery history exclude it. Webhook URLs must be absolute HTTPS URLs within the settled length and shape limits, contain no credentials or fragment, and pass the shared SSRF guard when configured and immediately before dispatch. Delivery history must be cursor-paginated and expose only the settled attempt metadata, status/failure vocabulary, filters, and ordering. Merchant App secret rotation must require recent password reauthentication; bearer-token-authorized Platform API operations follow the token scope boundary instead.

**Key interfaces:**

- `WebhookEndpoint` — Merchant-owned resource with opaque identity, URL, nullable description, `active | disabled` status, a non-empty unique Appointment event subscription, lifecycle timestamps, and no secret or health aggregate.
- `CreatedWebhookEndpoint` — creation result containing the complete endpoint resource plus a one-time `signingSecret`.
- `WebhookDeliveryAttempt` — safe attempt metadata containing delivery and event identity, event type, status, attempt number, response/failure metadata, duration, attempt time, and nullable next-attempt time, with no bodies, Customer Details, secrets, or free-form exceptions.
- `WebhookEndpoints` — capability operations for filtered endpoint listing, create, patch, idempotent disable, one-time secret rotation, and filtered cursor-paginated attempt history, all scoped through the resolved Merchant context.
- Platform API v1 webhook group — `GET`/`POST /v1/webhook-endpoints`, `PATCH`/`DELETE /v1/webhook-endpoints/:endpointId`, `POST /v1/webhook-endpoints/:endpointId/rotate-secret`, and `GET /v1/webhook-endpoints/:endpointId/deliveries` with the settled status codes, envelopes, errors, and `developer_config` rate-limit behavior.
- Shared webhook URL validation — one configuration-time and pre-dispatch contract enforcing HTTPS, maximum length, no credentials or fragment, and SSRF-safe destinations.
- Audit boundary — endpoint creation, update, disable, and secret rotation record sanitized events without signing material; no-op or cross-Merchant mutations do not emit misleading lifecycle events.

**Acceptance criteria:**

- [ ] All settled Platform API v1 Webhook Endpoint and Delivery Attempt routes exist, require `webhooks:manage`, derive exactly one Merchant from the verified bearer token, use the standard success/error envelopes and status codes, and apply the `developer_config` rate limit.
- [ ] Endpoint list includes active and disabled resources by default, supports repeatable status filters, orders by `(updatedAt ASC, id ASC)`, and uses the shared signed cursor contract without returning a total count.
- [ ] Creation and patch enforce an absolute HTTPS URL no longer than 2,048 characters with no credentials or fragment; nullable description is normalized and capped at 500 characters; and event subscriptions contain 1–5 unique values from the five settled Appointment event types.
- [ ] Creation returns `201` with the complete Endpoint and its signing secret exactly once; rotation returns `200` with only the newly persisted `signingSecret`; ordinary reads and all non-disclosure surfaces never expose plaintext signing material.
- [ ] Patch is last-write-wins, accepts at least one supported field, returns the complete updated Endpoint, and cannot reactivate a disabled Endpoint.
- [ ] Disable returns `204` for both first and repeated calls, disabled Endpoints cannot be re-enabled, and unknown or cross-Merchant endpoint access uses the same safe `404` behavior without mutation or secret creation.
- [ ] Delivery history supports the settled repeatable status and event filters, inclusive `attemptedAtFrom`, cursor and limit parameters, and `(attemptedAt DESC, id DESC)` ordering; an Endpoint with no attempts returns a successful empty page.
- [ ] Delivery Attempt resources use the settled IDs, statuses, failure codes, timestamps, duration, response status, and next-attempt metadata while omitting request/response bodies, Customer Details, secrets, and internal exception text.
- [ ] The shared URL guard runs at endpoint configuration and remains mandatory immediately before dispatch, including coverage for malformed, private, loopback, link-local, credential-bearing, fragment-bearing, and over-length destinations.
- [ ] Merchant App signing-secret rotation is gated by recent password reauthentication, while Platform API rotation relies on the authenticated token's `webhooks:manage` scope and Merchant boundary.
- [ ] Endpoint lifecycle and secret events are audited without secret values, and contract, handler, capability, real-D1, one-time disclosure, cursor, SSRF, cross-Merchant, disabled-state, audit, and empty-history tests pass.

**Out of scope:**

- Sending Webhook Events, retry orchestration, dead-letter recovery, and Appointment outbox fan-out; those belong to the downstream delivery slice.
- Webhook get-one, hard-delete, test-delivery, manual replay, automatic disabling, inferred health, and success-rate behavior.
- Wildcard subscriptions or Booking Session, Customer, Service, Provider, catalog, payment, and other non-Appointment event families.
- Re-enabling disabled Endpoints, idempotency keys, ETags, or conditional updates.
