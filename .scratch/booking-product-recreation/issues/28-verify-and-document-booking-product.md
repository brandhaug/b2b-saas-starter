## Agent Brief

**Category:** enhancement
**Summary:** Prove the complete five-Worker Booking Product and align its verification fixtures, checks, and documentation with the shipped product boundary.

**Current behavior:**
The repository has the settled Booking Product topology, domain decisions, and early Worker/prototype seams, but its verification contract still reflects the superseded Starter application. Browser coverage proves only public Starter pages and a seeded Workspace sign-in, the authored fixture is still Workspace-shaped, and the available tests do not yet prove the complete Merchant-to-customer booking journey, its credential boundaries, durable side-effect recovery, or both clean and upgrade migrations. Canonical documentation is mixed: the Booking Product glossary and ADRs describe the destination, while architecture, setup, API, operational, and intent-node guidance still describes Workspace-era behavior.

**Desired behavior:**
After the expand-contract implementation is complete, one typed, explicitly clock-anchored Seed Booking Scenario should drive local D1, test adapters, end-to-end setup, and product screenshots without parallel authored fixtures. Verification should enter through the Public Site and prove the complete supported flow for both Specific Provider and Any Provider choices, from verified Merchant Owner onboarding and publication through atomic Appointment confirmation, Merchant visibility, secure customer Confirmation, Platform API reads, and asynchronous notification delivery.

The suite should also prove the product's security and durability contracts: credentials remain confined to their intended Worker and Merchant boundary; cross-Merchant lookups do not disclose resource existence; persisted state, logs, queue messages, Webhooks, and delivery history do not retain forbidden secrets or PII; confirmation succeeds independently of queue, email, or Webhook availability; and committed outbox work can be recovered later. Both clean installation and upgrade from the final pre-contract schema must work, deterministic seeding must be safely repeatable against persisted local D1, and the complete Bun-only quality gate must cover all five Workers. Repository documentation should then describe only the shipped Booking Product boundary and explicitly identify deferred behavior.

**Key interfaces:**

- The canonical Seed Booking Scenario contract — a single connected Merchant graph with explicit clock input and deterministic identifiers, usable by D1 population, in-memory test adapters, end-to-end setup, and screenshot setup.
- Public Site booking ingress — the externally exercised entry point that delegates the customer journey to the Booking Worker while preserving origin, cookie, asset, and error boundaries.
- Booking confirmation contract — the atomic operation that consumes the hold, persists the Appointment snapshots and confirmation-access metadata, records the idempotent replay result, and appends durable outbox work before returning success.
- Durable outbox processing — queue wake-up, email delivery, Webhook delivery, retry/recovery, and delivery-history behavior whose failures cannot roll back or hide a committed Appointment.
- Platform API v1 authorization — independently scoped, single-Merchant bearer access to the supported read-only resources with non-disclosing tenant isolation.
- Database migration and seed entry points — reproducible clean, pre-contract upgrade, persisted-local, and repeat-seed paths using Bun-only commands.
- Canonical product documentation and intent nodes — the topology, domain, environment, local-development, API, operations, and deferred-scope contracts for the five shipped Workers.

**Acceptance criteria:**

- [x] Exactly one authored Seed Booking Scenario supplies local D1, capability-adapter tests, end-to-end tests, and screenshot workflows; its fixed-clock variants are deterministic and repeatable.
- [x] End-to-end coverage enters through the Public Site and proves verified Owner onboarding, catalog and schedule configuration, publication, Specific Provider and Any Provider booking, Time Slot Hold, Pay In Person review, idempotent confirmation, Merchant Appointment visibility, secure Confirmation, Platform API reads, and asynchronous delivery.
- [x] Automated security checks prove host-only Merchant cookies, public-origin isolation, non-disclosing cross-Merchant access, non-persistence of browser-held secrets, PII-free operational events and Webhook messages, and API scope isolation.
- [x] Failure-path checks prove queue publication, email delivery, and Webhook delivery failures do not change a successful confirmation response or hide the committed Appointment, and that later recovery processes the durable outbox without duplicating the Appointment.
- [x] Database verification passes from an empty database and from the latest pre-contract schema; repeated deterministic seeding replaces only the canonical seeded Merchant graph and persisted local-D1 startup uses the resulting data.
- [x] The repository's Bun-only build, typecheck, lint, format check, unit, real-D1, integration, and end-to-end commands pass across the Public Site, Merchant App, Booking App, Platform API, and Background Worker.
- [x] Architecture, domain, setup, environment, local-development, API, operations, and intent-node documentation consistently describes the five-Worker Booking Product, its security and data boundaries, and its explicitly deferred behavior.

**Out of scope:**

- Adding Pay Now, payment-provider state, refunds, rescheduling, reminders, analytics, customer accounts, Merchant roles, multi-location behavior, or other functionality deferred from the first Booking Vertical Slice.
- Turning the Platform API into a customer booking or first-party application data channel.
- Reintroducing superseded Workspace-era runtime behavior or preserving throwaway prototype fixtures as an additional supported data path.
- Requiring live third-party email or Webhook providers for deterministic local and CI verification.
