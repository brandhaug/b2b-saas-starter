# Confirm an Appointment atomically

Type: task
Category: enhancement
Status: ready-for-agent
Blocked by: 19
Parent: 10

## What to build

Make `Book` commit exactly one durable Appointment and make that success immediately visible even when queues, email, or webhooks are unavailable. Retried confirmation must never duplicate the Appointment.

## Acceptance criteria

- [ ] Confirmation atomically consumes the valid Time Slot Hold, creates one scheduled Appointment, creates Confirmation access metadata, reduces the Booking Session, and appends a durable outbox item.
- [ ] The Appointment retains current catalog references plus immutable snapshots of Services, roles, durations, prices, currency, Provider, start and end, Merchant timezone, Provider Preference, Customer Details, Checkout Path, and total.
- [ ] Confirmation generates deterministic HMAC-derived Confirmation access using route ID, token version, expiry, and signing-key ID; D1 stores metadata but never the plaintext token.
- [ ] Only the Booking App and Background Worker receive the Confirmation signing keyring, and new tokens use the current key while retained keys can verify still-valid tokens.
- [ ] The completed Session retains only the minimum twenty-four-hour idempotency record; Customer Details and Booking Quote no longer remain in its terminal payload.
- [ ] An identical confirmation retry during that window returns the existing Appointment and equivalent Confirmation access; every different Session operation returns `410`.
- [ ] The Booking App's `Book` action shows success only after the transaction commits, then establishes the confirmed customer's access and navigates to the canonical clean Confirmation URL; queue publication failure follows the same successful customer path.
- [ ] The Booking App publishes the committed outbox ID as a queue wake-up only after commit; publication failure cannot roll back, hide, or change the Appointment.
- [ ] The initiating trace ID is persisted with the outbox work, and no capability or Confirmation secret enters the outbox or queue message.
- [ ] The canonical seed scenario gains Confirmation access metadata but contains no active Booking Sessions, active holds, or pending outbox work.
- [ ] Real-D1 tests prove transaction rollback, conflict handling, immutable snapshots, replay idempotency, Session reduction, outbox durability, and success despite queue failure.

## Agent Brief

**Category:** enhancement
**Summary:** Make `Book` atomically create one durable Appointment and return customer-visible success independently of notification infrastructure.

**Current behavior:**
The Booking App can render a fixture-backed confirmation from selections held in React memory, but it does not commit an Appointment. The Booking capability and D1 model do not yet provide atomic confirmation, immutable Appointment snapshots, Confirmation access metadata, terminal Booking Session replay, or a booking outbox. The existing queue delivery machinery is for the generic Starter webhook surface and does not make booking confirmation durable.

**Desired behavior:**
An authorized `Book` command against an active Booking Session with a valid Time Slot Hold must perform one atomic state transition: consume the hold, create one Scheduled Appointment with immutable accepted facts, create revocable Confirmation access metadata, reduce the Session to its minimal twenty-four-hour replay record, and append one durable outbox item carrying the initiating trace ID. The transaction is the booking success boundary. After it commits, the Booking App establishes confirmation-specific access and navigates to the clean canonical Confirmation URL even if the subsequent queue wake-up cannot be published.

The Appointment must preserve current Merchant Catalog references while snapshotting the ordered Primary and Additional Services, roles, names, durations, positive prices and currency; the assigned Provider; the original Provider Preference; start and end; Merchant timezone; Customer Details; fixed Pay In Person Checkout Path; and exact total. Later catalog changes must not rewrite those accepted facts.

Confirmation access must use a deterministic HMAC-derived bearer secret based on the opaque route ID, token version, expiry, and signing-key ID. Persist only its metadata, never the bearer secret. New access uses the current signing key, retained keys can verify still-valid access, and only the Booking App and Background Worker receive the signing keyring.

For twenty-four hours after confirmation, retrying the identical confirmation through the consumed Session capability must return the existing Appointment and equivalent Confirmation access without creating another Appointment or outbox item. Every other operation against that terminal Session must return `410`. After the replay window, the terminal capability hash may be purged according to the settled cleanup policy.

**Key interfaces:**

- The Booking capability's confirmation command and result — accepts only authorization and command facts the server can validate; it must not accept Checkout Path, prices, snapshots, Provider assignment, or other accepted quote facts from the browser, and it returns the committed Appointment plus Confirmation access needed by the initiating customer.
- The Appointment aggregate and schemas — expose Scheduled status, current catalog references, and immutable snapshots of every fact accepted from the held Booking Quote and Customer Details.
- The Booking Session terminal representation — retains only the Session identity, Confirmed state, Appointment link, capability hash, and timestamps needed for the bounded idempotent replay; private Customer Details and the Booking Quote remain only in the Appointment snapshot.
- Confirmation access metadata and signing keyring — support deterministic derivation, current-key issuance, retained-key verification, targeted token-version revocation, key rotation, and expiry thirty days after the Appointment ends without storing plaintext tokens.
- The booking outbox record and queue wake-up contract — persist the committed work and initiating trace ID atomically with the Appointment, while the post-commit queue message contains only the outbox ID and no Booking Session capability or Confirmation secret.
- The Booking App `Book` action — reports success only after commit, establishes the customer's confirmation-specific access, and navigates to the canonical clean Confirmation URL; queue publication is a best-effort wake-up after that boundary.

**Acceptance criteria:**

- [ ] One atomic confirmation consumes a valid hold, creates exactly one Scheduled Appointment and its immutable snapshots, creates Confirmation access metadata, reduces the Booking Session, and appends exactly one durable outbox item; any failure before commit rolls all of it back.
- [ ] Appointment snapshots preserve the ordered Services and roles, durations, positive prices, currency, exact summed total, assigned Provider, Provider Preference, start and end, Merchant timezone, Customer Details, and `pay_in_person` Checkout Path while retaining current catalog references.
- [ ] The browser cannot override accepted quote, Provider, time, snapshot, total, currency, or Checkout Path facts in the confirmation command.
- [ ] Confirmation bearer access is deterministically HMAC-derived from persisted non-secret metadata, plaintext tokens are never stored, new access uses the current signing key, retained keys verify valid older access, and deployment configuration exposes the keyring only to the Booking App and Background Worker.
- [ ] During the twenty-four-hour replay window, an identical retry returns the existing Appointment and equivalent Confirmation access without duplicating the Appointment or outbox item; all other operations on the consumed Session return `410`.
- [ ] The terminal Booking Session retains only the minimal idempotency record and no Customer Details, Booking Quote, or other private working payload.
- [ ] After the transaction commits, the `Book` action follows the same successful customer path whether queue publication succeeds or fails, and it establishes Confirmation access before navigating to the clean canonical Confirmation URL.
- [ ] Queue publication occurs only after commit, carries only the outbox ID, and cannot roll back, hide, or alter the committed Appointment; the persisted outbox work retains the initiating trace ID and contains no capability or Confirmation secret.
- [ ] The canonical Seed Booking Scenario includes deterministic Confirmation access metadata but no active Booking Sessions, active holds, or pending outbox work.
- [ ] Real-D1 tests cover rollback, competing/conflicting confirmation, immutable snapshot retention, replay idempotency, Session reduction, outbox durability, signing-key behavior, and visible success when queue publication fails.

**Out of scope:**

- Rendering and authorizing the full cross-device Confirmation view beyond establishing access and navigating to its canonical URL.
- Delivering confirmation email or Appointment webhooks, retrying notification delivery, or maintaining delivery history; this issue creates durable outbox work only.
- Appointment mutation, cancellation, rescheduling, durable Customer identity, online payment, payment status, receipts, refunds, or reconciliation.
