# Configure Schedule Rules and publish a Public Booking Page

Type: task
Category: enhancement
Status: ready-for-agent

## What to build

Let a Merchant become publicly bookable by configuring recurring Provider hours, inspecting Booking Readiness, and publishing the current Public Booking Page. Customers should see the Merchant page and a working booking entry point only when publication rules allow it.

## Acceptance criteria

- [ ] Merchant Owners can create and edit recurring weekly Schedule Rules per Provider in the Merchant timezone; one-off exceptions and future schedules are absent.
- [ ] The Merchant App can inspect derived Availability for configured rules without persisting generated Time Slots.
- [ ] Booking Readiness is derived from public name and slug, an active Service, an eligible active Provider, and Schedule Rules; it does not require a Shop, Brand, checkout setting, payment provider, or currently open Time Slot.
- [ ] A Public Booking Page can be Published only when ready, can later be Unpublished without deleting configuration, and has no Draft, revision, or published-snapshot lifecycle.
- [ ] Published saves are visible immediately from current D1 data, with no HTML/catalog cache or cross-app invalidation mechanism.
- [ ] The Public Site renders the Merchant's current Published page and normal full-page booking CTA at the canonical public origin.
- [ ] An unknown slug returns a generic `404`; an Unpublished page returns the settled customer-facing unavailable response with `404` and `noindex`.
- [ ] The canonical seed graph becomes Published and schedule-complete, and fixed-clock tests produce deterministic readiness and future Availability.
- [ ] Merchant UI, capability, public-page, publication-transition, and ingress-path tests demonstrate ready, incomplete, Published, and Unpublished variants.

## Agent Brief

**Category:** enhancement
**Summary:** Make recurring Provider schedules, derived Booking Readiness, and Public Booking Page publication work end to end.

**Current behavior:**
The Merchant App has only a throwaway, in-memory prototype of recurring hours, readiness, and publication. Schedule Rules and Public Booking Pages are not persisted in D1 or exposed through Booking Product capabilities, and the Public Site does not resolve a Merchant's published page. The existing prototype establishes useful interaction vocabulary but performs no production persistence or cross-application behavior.

**Desired behavior:**
Merchant Owners can manage recurring weekly Schedule Rules for each Provider in the Merchant's IANA timezone and inspect deterministic, derived Availability without persisting generated Time Slots. Booking Readiness is derived from the Merchant's public name and slug, at least one active Service, an eligible active Provider, and Schedule Rules for that Provider. It must not depend on a Shop, Brand, checkout setting, payment provider, or the presence of a currently open Time Slot.

A Public Booking Page has only `Unpublished` and `Published` states. Publishing succeeds only while Booking Readiness is satisfied; unpublishing hides the page without deleting configuration. There is no Draft state, revision history, published snapshot, staged publication, or preview lifecycle. A Published page always renders current D1-backed content, so subsequent saves are visible immediately without an HTML/catalog cache or invalidation protocol.

At the canonical public origin, the Public Site resolves a Merchant slug and renders the current Published page with the normal full-page entry point into the Booking App. Unknown slugs return a generic `404`. Known but Unpublished pages return a customer-facing “Bookings are currently unavailable” response with `404` and `noindex`. Existing protected Booking Session and Confirmation routes remain governed by their own capabilities rather than current publication state.

**Key interfaces:**

- `ScheduleRule` — a Merchant-scoped recurring weekly interval owned by one Provider and interpreted in the Merchant's IANA timezone; first-slice rules exclude one-off exceptions and future-dated schedule versions.
- Scheduling capability — lists and mutates Provider Schedule Rules and derives Availability from current persisted booking inputs using an injectable clock; derived Time Slots are never stored.
- `BookingReadiness` — a derived projection that reports whether publication prerequisites are satisfied and which prerequisite checks are incomplete.
- Public-page publication transition — publishes only a ready page, supports unpublishing without configuration loss, and returns typed validation/application failures through the Effect capability boundary.
- Public Booking Page read model — exposes only current customer-visible Merchant and page data for Published pages and distinguishes unknown from known-but-Unpublished behavior without disclosing private Merchant configuration.
- Public booking path builder and ingress contract — the page CTA uses the canonical Merchant-scoped Booking App path at the Public Site origin; the Public Site remains the ingress owner.
- Seed Booking Scenario — expands the single authored Merchant graph with recurring Provider rules and Published page data while preserving derived incomplete and Unpublished test variants and fixed-clock determinism.

**Acceptance criteria:**

- [ ] Merchant Owners can create and edit recurring weekly Schedule Rules per Provider in the Merchant timezone; one-off exceptions, time off, extra hours, and future schedule versions are absent.
- [ ] Schedule Rule reads and mutations are Merchant-scoped, validated, D1-backed, and behaviorally equivalent in test adapters.
- [ ] Merchant Owners can inspect future Availability derived with an injected clock, and no generated Time Slot rows or seeded slot fixtures are introduced.
- [ ] Booking Readiness requires public name, slug, an active Service, an eligible active Provider, and Schedule Rules for that Provider, and reports incomplete prerequisites without requiring any deferred or runtime-availability condition.
- [ ] Publishing an incomplete page fails through a typed capability result; a ready page can become Published, and a Published page can become Unpublished without losing configuration.
- [ ] Public Page Status remains exactly `Published` or `Unpublished`, with no Draft, revision, staged publication, published snapshot, or draft-preview behavior.
- [ ] A Published page renders current D1-backed content at the Merchant slug and links to the canonical Merchant-scoped Booking App entry point; subsequent Merchant saves appear immediately.
- [ ] Unknown Merchant slugs return a generic `404`; Unpublished Merchant pages return “Bookings are currently unavailable” with `404` and `noindex`.
- [ ] The canonical Seed Booking Scenario is Published and schedule-complete, while fixed-clock variants deterministically cover incomplete readiness, Unpublished visibility, and future Availability.
- [ ] Capability, real-D1, Merchant App, Public Site, publication-transition, and public-ingress tests cover ready, incomplete, Published, and Unpublished behavior.

**Out of scope:**

- One-off schedule exceptions, holidays, time off, extra hours, or future-dated schedule versions.
- Persisted Time Slots, availability caches, generated HTML/catalog caches, or cross-application invalidation.
- Shop, Brand, checkout-policy, payment-provider, or currently-open-slot requirements for Booking Readiness.
- Drafts, revisions, staged publication, immutable published snapshots, or draft preview.
- Starting or protecting a Booking Session, selecting Providers or Services in that session, creating Time Slot Holds, confirming Appointments, or serving Confirmation access.
- Platform API mutations for Schedule Rules or Public Page Status.
