# Expose the read-only Platform API v1

Type: task
Category: enhancement
Status: ready-for-agent
Blocked by: 20, 23
Parent: 10

## What to build

Give server-to-server integrations a stable read-and-notify view of the Booking Product without turning the Platform API into a customer booking channel or first-party application backend.

## Acceptance criteria

- [ ] Scoped integrations can read the current Merchant, list and fetch Services, list and fetch Providers, and list and fetch Appointments through the settled `/v1` endpoints.
- [ ] Successful bodies use the `data` envelope, collections use the settled default and maximum limits, and no collection returns a total count.
- [ ] Resource IDs use the settled opaque prefixes, timestamps are UTC RFC 3339, durations are positive integer minutes, and money uses integer minor units plus uppercase currency.
- [ ] Merchant, Service, Provider, and Appointment representations contain exactly the settled current fields or immutable snapshots and omit internal identity, policy, payment, and confirmation data.
- [ ] Appointment reads expose authorized Customer Details, while errors, logs, cursor contents, and Webhook Events never contain those details.
- [ ] Collection filters, ordering, repeatable parameters, and inclusive/exclusive time semantics match the settled contract.
- [ ] Stateless signed cursors are PII-free, expire after twenty-four hours, bind to endpoint and filter hash, and return `invalid_cursor` when tampered, expired, cross-endpoint, or filter-mismatched.
- [ ] The API provides no Customers, Schedule Rules, Availability, Public Booking Page, Shop, Brand, Booking Session, checkout, confirmation, or Appointment mutation endpoints.
- [ ] The generated OpenAPI document and Scalar reference describe only the Booking Product contract, with health, OpenAPI, and reference remaining unversioned and unauthenticated.
- [ ] Generic Starter API groups are removed, and contract, handler, OpenAPI, authentication, filtering, cursor, PII, cross-Merchant, and rate-limit tests cover the published surface.

## Agent Brief

**Category:** enhancement
**Summary:** Replace the generic Starter API with the settled merchant-scoped, read-only Booking Product Platform API v1.

**Current behavior:**
The API Worker serves an unversioned generic Starter contract centered on Workspace, module, invitation, assistant, catalog, MCP, API-token, and webhook examples. Its authenticated routes use Workspace slugs and the old generic scope vocabulary, return resource bodies without the Booking Product's stable envelope and error contracts, and publish those Starter groups in generated OpenAPI. No Platform API endpoints currently expose Merchant, Service, Provider, or Appointment resources, and the capability and persistence layers do not yet contain those Booking Product read projections.

The completed Platform API contract decision fixes a different external boundary: independently scoped bearer tokens establish exactly one Merchant, `/v1` exposes read-only Merchant Catalog and Appointment data, and customer booking operations remain first-party Booking App behavior. Appointment confirmation and merchant-scoped token authentication are upstream dependencies because they establish the authoritative Appointment snapshots and authorization context this API must read.

**Desired behavior:**
The Platform API must serve the settled `/v1` Merchant, Services, Providers, and Appointments groups from the same Effect capabilities and D1-backed Booking Product state used by first-party applications. Every endpoint must require its one explicit read scope, derive Merchant context solely from the verified API Token, and make nonexistent and cross-Merchant resources indistinguishable. Successful responses use the `data` envelope; collections additionally return only `page.nextCursor`, default to 50 items, cap at 100, and never expose total counts.

Representations must use opaque prefixed IDs, UTC RFC 3339 timestamps, positive integer minute durations, and integer-minor-unit Money with uppercase currency. Merchant, Service, and Provider reads expose only their settled current fields. Appointment reads expose the accepted immutable Provider and ordered Service snapshots, Provider Preference, scheduling facts, Checkout Path, total, status, and authorized Customer Details while omitting payment, confirmation, internal identity, and policy data. Customer Details may appear only in authorized Appointment response bodies, never in logs, errors, cursor contents, OpenAPI examples, or Webhook Events.

Service and Provider collections must implement their settled repeatable filters and deterministic `(updatedAt, id)` ascending order. Appointment collections must implement the settled repeatable status and Provider filters, inclusive lower time bounds, exclusive `startsAtBefore`, and deterministic `(updatedAt, id)` ascending order for imports and reconciliation. Stateless signed cursors must be PII-free, expire after twenty-four hours, bind to endpoint and normalized filter hash but not limit, and produce the stable `invalid_cursor` error for tampering, expiry, endpoint reuse, or filter mismatch.

Generated OpenAPI and Scalar reference output must describe only the Booking Product contract. Health, OpenAPI, and reference stay unversioned and unauthenticated; all business-data routes live under `/v1`, use private/no-store authenticated responses and the settled typed error envelope, and apply the `data_read` rate-limit bucket. The old generic Starter public groups must leave the served contract rather than remain as compatibility routes.

**Key interfaces:**

- The Booking Product HTTP API contract — defines the unversioned health/documentation surface and the `/v1` Merchant, Service, Provider, and Appointment read groups, exact schemas, query parameters, response statuses, endpoint-specific typed errors, and OpenAPI metadata as one source of truth.
- Merchant-scoped bearer authentication — verifies only Platform API Tokens, establishes the token's Merchant context without a caller-supplied Merchant ID or slug, enforces `merchant:read`, `services:read`, `providers:read`, or `appointments:read` per route, and cannot accept Better Auth sessions or customer capabilities.
- Merchant Catalog read capabilities — provide current Merchant, Service, Provider, eligibility, Public Page Status, and booking URL projections without exposing internal ownership, Merchant Member, scheduling, or private Provider data.
- Appointment read capability — lists and fetches Merchant-owned Appointment records from immutable accepted snapshots, including authorized Customer Details while preserving the settled privacy boundary.
- Collection query and cursor contract — normalizes repeatable filters, applies deterministic keyset ordering and time-bound semantics, and signs/verifies endpoint- and filter-bound traversal cursors without PII.
- Platform API error and rate-limit contract — returns the stable safe error envelope with trace ID, maps missing and cross-Merchant resources to the same `resource_not_found` response, and applies the `data_read` bucket without promising remaining-count headers.

**Acceptance criteria:**

- [ ] Scoped tokens can read the current Merchant, list and fetch Services, list and fetch Providers, and list and fetch Appointments only within the token's Merchant through the settled `/v1` endpoints.
- [ ] Each route requires exactly its settled read scope; invalid credentials, insufficient scope, cross-Merchant access, and capability failures use the settled status, safe typed error envelope, authentication headers, trace ID, and cache policy.
- [ ] Every non-empty success uses `data`; collections add `page.nextCursor`, default to 50, reject or cap beyond the settled maximum of 100 as specified, and return no total count.
- [ ] Merchant, Service, Provider, and Appointment schemas expose exactly the settled fields, opaque ID prefixes, UTC RFC 3339 timestamps, positive integer durations, and integer-minor-unit Money with uppercase currency.
- [ ] Appointment reads use immutable Provider and ordered Service snapshots and expose authorized Customer Details, while responses omit payment status, processor and confirmation secrets, internal Merchant identity, customer accounts, and inferred Customer Directory data.
- [ ] Service, Provider, and Appointment collection filters, repeatable-parameter handling, inclusive/exclusive timestamp semantics, and deterministic ordering match the settled contract and are covered at both contract and handler boundaries.
- [ ] Signed cursors contain no Customer Details, expire after twenty-four hours, bind to endpoint and normalized filter hash, remain independent of limit, and return `invalid_cursor` for tampering, expiry, endpoint reuse, or changed filters.
- [ ] Logs, wide-event annotations, errors, validation details, cursor payloads, OpenAPI examples, and Webhook Events contain no Customer Details or other prohibited secrets.
- [ ] No customer Booking Session, Availability, checkout, confirmation, Appointment mutation, Customer, Schedule Rule, Public Booking Page, Brand, Shop, or generic Starter route is present in the served Platform API contract.
- [ ] Generated OpenAPI and Scalar reference output contain only the Booking Product surface; `/health`, `/openapi.json`, and `/reference` remain unversioned and public while `/v1` data routes remain authenticated and private/no-store.
- [ ] Contract, capability, handler, OpenAPI, authentication, filtering, cursor, PII-safety, cross-Merchant, rate-limit, and real-D1 tests prove the published behavior and the API Worker test suite remains green.

**Out of scope:**

- API Token and Webhook Endpoint lifecycle implementation beyond consuming the merchant-scoped authentication foundation supplied by their dedicated issues.
- Merchant catalog or Schedule Rule mutations, Appointment cancellation or rescheduling, customer booking operations, and any first-party application using the Platform API as its backend.
- Standalone Customer or Customer Directory endpoints, multi-Merchant partner credentials, Brands, Shops, online payments, payment state, confirmation access, MCP, and compatibility aliases for retired Starter routes.
- Durable synchronization checkpoints, collection totals, offset pagination, free-text catalog search, Customer Detail filters, idempotency keys, ETags, or conditional requests.
