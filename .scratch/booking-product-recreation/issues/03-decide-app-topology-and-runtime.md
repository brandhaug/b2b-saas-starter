# Decide App Topology and Runtime

Type: grilling
Status: done
Blocked by:

## Question

What exact target topology, route prefixes or domains, runtime choices, package names, ports, bindings, and ownership boundaries should `apps/web`, `apps/merchant`, `apps/booking`, `apps/api`, and `apps/background` use for the first Booking Vertical Slice?

The names are settled, but this ticket should decide whether Merchant App and Booking App are TanStack Start Workers, Vite SPAs, or another Cloudflare-compatible shape, and how they share configuration without coupling deployments.

## Resolved So Far

- `apps/merchant` and `apps/booking` will be first-party TanStack Start Cloudflare Workers, not Vite SPAs. They should call shared capabilities server-side through loaders and server functions. `apps/api` is the external HTTP **Platform API**, not the first-party app data layer or a customer booking channel.
- Target routing:
  - Public Site and merchant public pages: canonical `www.<domain>`, served by `apps/web`, local port `3071`; the apex permanently redirects to `www`.
  - Merchant App: `app.<domain>`, served by `apps/merchant`, local port `3072`.
  - Booking App: `www.<domain>/:merchantSlug/booking`, behavior served by `apps/booking` behind the `apps/web` ingress service binding, local port `3073`.
  - Platform API: `api.<domain>`, served by `apps/api`, local port `8787`.
  - Background: no public route; queue and cron triggers only.
- `apps/booking` owns `/:merchantSlug/booking` as an explicit router base path. The public route mapping should not strip the merchant slug or `/booking` prefix before requests reach the Booking App.
- `apps/web` is the production ingress Worker for the canonical `www.<domain>` custom domain. It handles Public Site and merchant public-page requests itself, then delegates `/:merchantSlug/booking*` and `/_booking/*` requests to `apps/booking` through a Cloudflare `BOOKING` service binding while preserving the original URL.
- Direct Cloudflare route patterns cannot express `/:merchantSlug/booking*` because Workers routes do not support infix wildcards. Do not configure the previously considered `www.<domain>/*/booking*` route. No sixth dispatcher app is needed; the narrow path dispatcher belongs at the `apps/web` ingress boundary.
- The `apps/web` dispatcher performs no D1 merchant lookup. It delegates only when the path has the merchant-scoped booking shape and its first segment is not in the shared reserved-public-slug set; reserved paths such as `/docs/booking` remain with the Public Site. `apps/booking` owns merchant lookup, Public Page Status checks, and Booking Session authorization after delegation.
- If the `BOOKING` service binding is unavailable or fails before returning a response, `apps/web` returns a minimal branded `503 Booking temporarily unavailable` response with `Retry-After` and the request trace ID. `apps/web` does not fall back to querying private booking state or implementing booking behavior.
- Better Auth and merchant browser sessions move to `apps/merchant`. `apps/web` becomes unauthenticated Public Site content only. `apps/booking` stays public for the first slice and uses an anonymous booking-session mechanism rather than Better Auth customer accounts. `apps/api` keeps API-token auth for external clients.
- The generic authenticated starter/reference app routes are retired from the target product topology. Reuse their implementation patterns in `apps/merchant` only when they serve Booking Product concepts such as public pages, services, providers, appointments, customers, settings, and reports.
- App package names stay short and unscoped: `web`, `merchant`, `booking`, `api`, and `background`. Scoped `@b2b-saas-starter/*` names remain for shared packages only.
- `apps/web`, `apps/merchant`, and `apps/booking` each get their own `wrangler.jsonc` and Alchemy `Cloudflare.Vite(...)` Worker declaration. Shared infra constants may live under `infra/*`, but each browser app remains an independent deploy unit.
- First-slice bindings:
  - `apps/web`: `DB` for public-read merchant pages at `/:merchantSlug` and a `BOOKING` service binding for delegated booking requests; no auth secrets or merchant session bindings.
  - `apps/merchant`: `DB`, `EMAIL` when configured, and auth rate limit bindings.
  - `apps/booking`: `DB`, a `BOOKING_EVENTS_QUEUE` producer binding, booking-specific rate limit bindings if needed, and no Better Auth or email secret.
  - `apps/api`: `DB`, `WEBHOOK_QUEUE` producer binding, API rate limits, and AI if retained; no `BOOKING_EVENTS_QUEUE` or direct booking-email binding.
  - `apps/background`: `DB`, `BOOKING_EVENTS_QUEUE` and `WEBHOOK_QUEUE` consumer bindings, cron recovery sweeps, and `EMAIL` when configured.
- `apps/merchant` and `apps/booking` both depend directly on `@b2b-saas-starter/capabilities` from server-side loaders and server functions. They do not call `api.<domain>` for first-party business behavior. `apps/api` exposes the same use cases externally through HTTP contracts.
- `apps/merchant` uses simple merchant-scoped routes for the first slice rather than `/workspaces/:workspaceSlug`: `/sign-in`, `/public-page`, `/services`, `/availability`, `/appointments`, `/customers`, and `/settings`, with team/provider routes gated by plan and need. Useful membership/role mechanics may be adapted around Merchant ownership, but Workspace is not retained as a Booking Product entity and the Merchant App speaks Merchant operations rather than Starter workspace language.
- `apps/booking` uses canonical Booking Product route vocabulary under `/:merchantSlug/booking` instead of legacy route names such as `/book`, `/barber`, or `/view-reservation`. Solo or single-provider routes can skip provider choice: `/:merchantSlug/booking`, `/:merchantSlug/booking/services`, `/:merchantSlug/booking/services/:serviceSelection/schedule`. Team or provider-choice routes use providers explicitly: `/:merchantSlug/booking/providers`, `/:merchantSlug/booking/providers/:providerPreference/services`, `/:merchantSlug/booking/providers/:providerPreference/services/:serviceSelection/schedule`. Checkout and confirmation routes are `/:merchantSlug/booking/session/:bookingSessionId/checkout` and `/:merchantSlug/booking/confirmations/:confirmationId`.
- `apps/api` exposes versioned Platform API contracts under `/v1` on `api.<domain>`. First-slice groups may cover merchant-owned catalog data, appointment records, API tokens, and webhook configuration; exact groups belong to the Platform API contract ticket. It must not expose customer Booking Session creation, availability search, checkout, or Appointment confirmation. Operational and documentation endpoints remain unversioned at `/health`, `/openapi.json`, and `/reference`.
- Because `apps/booking` is mounted at `www.<domain>/:merchantSlug/booking`, its customer-facing route paths, redirects, preload links, and generated booking URLs must preserve that merchant-scoped booking base. Compiled assets are the explicit exception and use the stable internal prefix `www.<domain>/_booking/*`. The `apps/web` ingress dispatcher delegates booking page requests and `/_booking/*` assets to the `BOOKING` service binding, while handling remaining `www.<domain>/*` traffic itself.
- Cross-app origins are explicit: `PUBLIC_SITE_ORIGIN`, `MERCHANT_APP_ORIGIN`, and `PLATFORM_API_ORIGIN`. `apps/booking` has no separate production origin because its public URLs share `PUBLIC_SITE_ORIGIN`; a typed booking-path builder generates `/:merchantSlug/booking` URLs. `BOOKING_DEV_ORIGIN=http://localhost:3073` exists only for the local ingress proxy. `BETTER_AUTH_URL` points to `MERCHANT_APP_ORIGIN` because `apps/merchant` owns sign-in.
- Local dev ports and scripts: root `bun run dev` continues to run Turbo dev tasks, with direct scripts `dev:web` on port `3071`, `dev:merchant` on `3072`, `dev:booking` on `3073`, `dev:api` on `8787`, and `dev:background` on `8788`.
- Local end-to-end public traffic enters through `http://localhost:3071`. During development, `apps/web` proxies `/:merchantSlug/booking*` and `/_booking/*` to `apps/booking` on `http://localhost:3073` while preserving the original request URL. Port `3073` remains directly available for isolated Booking App work, but end-to-end tests exercise the `:3071` ingress path.
- Do not create a shared UI package for the first Booking Vertical Slice. Each browser app owns its route shell and local components, reusing existing patterns from `apps/web` during scaffolding and extracting shared UI later only if real duplication appears.
- Keep one shared D1 database for the first Booking Vertical Slice: one `DB` binding, one Drizzle schema package, and one migration stream in `packages/db`. Split ownership at the capability/table/service level; exact table design belongs to the storage decision ticket.
- `apps/booking` may create and mutate booking sessions directly through server-side capability calls. The write boundary is the capability service, not the HTTP API worker. `apps/booking` should receive only public/anonymous booking capabilities, while merchant administration capabilities remain behind `apps/merchant` session gates.
- Confirming a Booking Session commits the Appointment and a durable outbox record together through the capability layer. `apps/booking` returns the Confirmation after that transaction commits; it does not send email or webhooks synchronously. `apps/background` owns processing the outbox, sending confirmation email, delivering webhooks, and retrying failures. Delivery failure never rolls back or hides a successfully committed Appointment.
- After the Appointment and outbox transaction commits, `apps/booking` publishes the outbox ID to `BOOKING_EVENTS_QUEUE` for prompt processing. `apps/background` consumes that signal, while a cron sweep recovers unprocessed outbox records when publication or delivery was missed. The durable outbox is the source of truth; the queue message is only a wake-up signal. `apps/api` cannot confirm an Appointment and does not produce booking events.
- Outbox processing is at-least-once and idempotent. Background workers atomically claim outbox items, reuse stable delivery IDs across retries, persist completion before acknowledging queue work, and treat an already completed item as a no-op. Email delivery uses a provider idempotency key when supported. Webhook retries reuse the same delivery ID so consumers can deduplicate; the system promises one logical delivery, not exactly one observable HTTP request.
- Preserve the repository's existing `x-trace-id` convention across the entire request path. `apps/web` accepts or creates the trace ID, forwards it through the `BOOKING` service binding, and booking capabilities persist it on outbox work so `apps/background` can continue the same trace in email and webhook logs.
- The external Platform API is server-to-server in the first slice. It does not enable wildcard or arbitrary-origin CORS, and API tokens are not intended for storage in third-party browser JavaScript. First-party browser apps continue to call capabilities through their own server runtimes; explicit allowlisted browser integrations can be designed later for a concrete partner use case.
- Remove auth secrets, auth route handling, and auth rate-limit bindings from `apps/web` in the target topology. `apps/merchant` owns `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, trusted origins, Better Auth routes, and auth rate limits; `packages/auth` remains shared implementation code.
- `:merchantSlug` represents the canonical public slug for a **Merchant**. The first slice optimizes for solopreneurs with one public booking presence, while leaving room for teams, brands, and shops underneath the merchant later.
- `apps/web` owns public merchant pages at `www.<domain>/:merchantSlug` and may use public-read merchant catalog capabilities through its `DB` binding. At the ingress boundary it delegates only `www.<domain>/:merchantSlug/booking*` and `www.<domain>/_booking/*` to `apps/booking`; `apps/booking` remains the behavioral owner of those delegated requests.
- Merchant public slugs must not collide with Public Site routes or infrastructure words. Reserve at least `docs`, `blog`, `faq`, `help`, `changelog`, `pricing`, `privacy`, `terms`, `booking`, `api`, `assets`, `_booking`, `admin`, `sign-in`, `app`, and `www`.
- Merchant App information architecture is plan-aware. A Solo plan hides staff/team setup and treats the merchant as the default bookable person. A Team plan exposes team/provider management and staff selection when there are multiple bookable people.
- Cal.com terminology research is captured in `../research/02-calcom-canonical-booking-terms.md`. Cal.com uses **Host**, but this product adopts **Provider** as the canonical service-booking term because Beesolo is solopreneur-service-first rather than meeting-host-first.
- Provider choice terms are **Provider Preference**, **Specific Provider**, and **Any Provider**. Solo plans hide provider choice when the merchant is the only provider; Team plans can expose provider choice when multiple eligible providers exist.
- Providers and Services belong to the Merchant by default in the first slice. Shops are optional growth structure for multi-location or multi-brand cases, not a prerequisite for a solopreneur to become bookable.
- Visible Shop management is deferred from the Solo first slice. Keep **Shop** in the domain model for legacy translation and later multi-location growth, but the first visible setup path should require only public page content, default provider, services, availability, appointments, and customer details. The fixed Pay In Person Checkout Path needs no Merchant setup.
- Visible Brand management is deferred from the Solo first slice. In the first slice, **Merchant** owns `merchantSlug`, display name, public page content, default provider, services, and availability directly. **Brand** remains future structure for multiple public identities, locations, or business lines.
- Merchant App primary navigation for the first slice is `Services`, `Availability`, `Appointments`, `Customers`, and `Settings`. Public page editing belongs under Settings or onboarding, with a persistent `View public page` action to `www.<domain>/:merchantSlug` rather than a primary nav item. Providers, Shops, Brands, and Reports are plan-gated, secondary, or later surfaces.
- `Customers` remains a primary Merchant App destination in the first slice, but it begins as a lightweight, appointment-derived directory. Customer records are created from booking and appointment activity; standalone CRM features such as imports, merchant notes, tags, marketing consent management, saved payment methods, and campaigns are deferred.
- The public booking CTA is a normal full-page navigation from `apps/web` at `www.<domain>/:merchantSlug` into `apps/booking` at `www.<domain>/:merchantSlug/booking`. `apps/web` may carry optional booking intent in the destination URL, but it remains read-only and never creates or mutates a booking session. `apps/booking` creates and owns the booking session from the first booking request onward.
- Anonymous Booking Session access uses two independent values: an opaque session ID in the route and a 256-bit random capability in a session-specific, host-only, `HttpOnly`, `Secure`, `SameSite=Lax` cookie. D1 stores only the capability hash; `apps/booking` validates the route ID, capability secret, Merchant slug, and active session before reading or mutating private state. A session URL alone is not authorization.
- An unfinished Booking Session is resumable only in the browser holding its session capability; its URL is not a cross-device resume link. After confirmation, `apps/booking` may issue a separate opaque **Confirmation Access Token** for an emailed cross-device link. That token grants only limited confirmation access and is distinct from the expired Booking Session capability. In the first slice this access is read-only because customer cancellation and rescheduling are explicitly deferred.
- Merchant browser sessions are host-only to `app.<domain>`. Merchant authentication cookies must not use a parent-domain scope and must never be sent to `www.<domain>` or `api.<domain>`. The Public Site and Booking App remain unauthenticated customer surfaces, while external Platform API requests use API-token authentication.
- Custom merchant domains are deferred from the first slice. Public pages and booking flows launch only at `www.<domain>/:merchantSlug` and `www.<domain>/:merchantSlug/booking`. Merchant resolution should not assume that the slug will always be the only routing input, leaving room for future hostname-based resolution without adding domain verification, certificate provisioning, custom-domain routing, or canonical URL behavior now.
- `www.<domain>` is the canonical Public Site origin. The apex domain permanently redirects to `www.<domain>` while preserving the complete path and query string; generated public-page, booking, confirmation, metadata, and sitemap URLs always use the `www` origin.
- Merchant public pages are rendered from current published data in D1 on each request in the first slice. Do not add HTML or catalog edge caching, revalidation hooks, or cross-app cache invalidation yet; cache only versioned static assets. Edge caching can be introduced later from measured traffic and freshness requirements.
- A Public Booking Page has only two **Public Page Status** values: **Unpublished** and **Published**. New merchants begin Unpublished and may publish after completing the minimum booking setup. Saves to a Published page become live immediately; there is no Draft state, revision workflow, staged publication, or draft preview. Unpublishing removes customer visibility without deleting merchant configuration.
- **Booking Readiness** gates publication. It requires a public name and slug, at least one active Service, at least one eligible Provider, and Schedule Rules for that provider. It does not require checkout configuration, a Shop, Brand, team member, payment provider, or currently available Time Slot.
- Unpublishing blocks creation of new Booking Sessions immediately, but an existing short-lived session may finish when its selected services, provider, price, and time slot remain valid. Unpublishing does not cancel appointments or revoke Confirmation Access Tokens, so existing customer confirmations remain available.
- An unknown merchant slug returns a generic `404`. An Unpublished page returns a simple customer-facing "Bookings are currently unavailable" response with `404` and `noindex`. Existing Booking Session and Confirmation routes are authorized by their own capabilities rather than by current public-page visibility.
- `apps/booking` reserves `www.<domain>/_booking/*` as its stable Vite asset base. This prefix is infrastructure-only and serves compiled JavaScript, CSS, and related build assets; it does not change customer-facing booking URLs under `/:merchantSlug/booking`.
- The production `apps/booking` Worker exposes neither a `workers.dev` route nor a direct preview URL. Customer traffic can reach it only through the `BOOKING` service binding from the `apps/web` ingress Worker, preventing alternate origins from bypassing canonical routing and ingress behavior. Direct port `3073` remains a local-development facility.
- Production `apps/web`, `apps/merchant`, and `apps/api` Workers also disable `workers.dev` and preview URLs. Their only public production origins are `www.<domain>`, `app.<domain>`, and `api.<domain>` respectively. Staging and local development use separate endpoints rather than alternate origins for production scripts.
- Staging is a fully isolated deployment environment with separate Workers, D1 database, queues, rate-limit namespaces, secrets, and email configuration. It preserves the same `apps/web` ingress-to-`apps/booking` service-binding topology and must not read production data or produce production appointments, email, queue messages, or webhook deliveries.
- Staging mirrors production host roles at `www.staging.<domain>` for the Public Site and booking flow, `app.staging.<domain>` for the Merchant App, and `api.staging.<domain>` for the Platform API. `staging.<domain>` permanently redirects to `www.staging.<domain>` with path and query preserved. Staging origin, cookie, and trusted-origin settings use only these staging hosts.
- The Platform API starts under `/v1`, superseding ADR 0048's decision to defer versioning for the retired generic Starter API. The new product-facing integration contract should not require a later breaking migration from unversioned URLs.
- ADR [0051 — Booking product application topology](../../../docs/adr/0051-booking-product-application-topology.md) records the final topology and supersedes the generic Starter decisions that no longer apply.
