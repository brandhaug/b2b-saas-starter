# Deliver booking notifications from the durable outbox

Type: task
Category: enhancement
Status: ready-for-agent
Blocked by: 20, 25
Parent: 10

## What to build

Turn a committed Appointment's outbox item into prompt, recoverable customer email and thin `appointment.created` Webhook delivery. Delivery must remain at-least-once and must never control whether the Appointment is considered confirmed.

## Acceptance criteria

- [ ] The Background Worker consumes booking-event wake-ups, atomically claims durable outbox items, treats completed work as a no-op, persists completion before acknowledgement, and safely handles redelivery.
- [ ] A scheduled recovery sweep finds eligible unprocessed outbox work when queue publication or prior processing was missed.
- [ ] When email is configured, the customer receives a confirmation message containing the immutable time, Services, total, Pay In Person wording, and a re-derivable Confirmation link; it is not called a receipt.
- [ ] When email is unconfigured or fails, the Appointment and customer Confirmation remain successful and visible, with the delivery state recorded safely for operations.
- [ ] `appointment.created` fan-out produces the settled thin, PII-free Webhook Event containing a stable Event ID and authoritative Appointment locator rather than Customer or snapshot data.
- [ ] Every HTTP attempt receives its own Delivery Attempt ID while retries retain the same Event ID and body so receivers can deduplicate the logical event.
- [ ] Delivery uses the settled headers and HMAC-SHA256 raw-body signature, a five-minute receiver tolerance, a ten-second timeout, and immediate pre-dispatch SSRF validation.
- [ ] Response classification, one initial attempt plus six scheduled retries, persisted attempt status, failure codes, next-attempt time, and dead-letter outcome match the settled Platform API contract.
- [ ] Delivery history never stores request or response bodies, secrets, Customer Details, or free-form exceptions, and failing Endpoints are not disabled automatically.
- [ ] The originating trace ID continues through email, Webhook, retry, and recovery logs; logs and queue payloads contain no capability, Confirmation, or signing secrets.
- [ ] Unit orchestration tests, real-D1 outbox and attempt tests, queue/dead-letter tests, recovery tests, signature vectors, and configuration-gated email tests prove idempotency and Appointment independence.

## Agent Brief

**Category:** enhancement
**Summary:** Process committed booking outbox work into recoverable confirmation email and thin, at-least-once `appointment.created` Webhook delivery without coupling either notification to Appointment success.

**Current behavior:**
The Booking Product topology already exposes a booking-events queue binding, but the Background Worker currently acknowledges those wake-ups without processing them. The repository also has reusable foundations for outbound email, generic Workspace-era webhook dispatch, retries, signatures, delivery history, dead letters, SSRF checks, and wide-event logging. It does not yet claim Booking outbox records, recover missed work, render Appointment confirmation email, or produce the settled Merchant-scoped Webhook Event and Delivery Attempt contract. Existing generic webhook identities, body shape, headers, statuses, and ownership boundary do not satisfy the Booking Product contract.

**Desired behavior:**
After Appointment confirmation commits its durable outbox item, the Background Worker should use queue messages only as wake-ups and D1 as the source of truth. It must atomically claim eligible work, make completed work a no-op, persist channel outcomes before acknowledging, safely reclaim interrupted work, and use a scheduled sweep to recover work missed because publication or processing failed. Duplicate or delayed wake-ups must not create a second logical Webhook Event or lose notification work.

When outbound email is configured, send the Customer a confirmation message derived from the immutable Appointment snapshot. It must show the scheduled time, ordered Services, exact total, Pay In Person wording, and a re-derivable Confirmation link, without calling the message a receipt. Missing configuration or delivery failure must be recorded for operations but must never roll back, hide, or change the Appointment or Confirmation.

For each subscribed active Webhook Endpoint, create a thin PII-free `appointment.created` event with a stable Event ID, schema version, occurrence time, Merchant identity, and authoritative Appointment locator/status/update facts. Retries preserve the Event ID and exact raw body, but every HTTP attempt receives a new Delivery Attempt ID, timestamp, and signature. Dispatch must revalidate the destination, use the settled headers and HMAC-SHA256 raw-body signature, enforce the ten-second timeout, classify outcomes according to the Platform API contract, persist every attempt and retry schedule, and finish in the settled dead-letter state after one initial attempt plus six retries. A failing Endpoint remains configured and active unless explicitly disabled elsewhere.

**Key interfaces:**

- Booking outbox processing capability — atomically claims eligible committed work, distinguishes completed and reclaimable work, records sanitized per-channel outcomes, and completes processing durably under queue redelivery and recovery sweeps.
- Booking event wake-up — carries only the outbox identity; it is not the durable event payload and contains no Booking Session capability, Confirmation secret, Customer Details, or signing secret.
- Appointment confirmation email — renders only immutable Appointment facts and derives valid Confirmation access from persisted non-secret metadata and the configured signing keyring.
- `WebhookEvent` — stable Merchant-scoped logical event using the `evt_` identity and the settled thin `appointment.created` schema, with no Customer Details or Appointment snapshot payload.
- `WebhookDeliveryAttempt` — one `dlv_`-identified HTTP attempt with the settled attempt number, status, response/failure metadata, duration, timestamps, and retry schedule, while excluding bodies, secrets, private customer data, and free-form exceptions.
- Background Worker queue and scheduled triggers — share the same idempotent outbox orchestration, preserve the originating trace ID, and acknowledge work only after the corresponding durable state is recorded.

**Acceptance criteria:**

- [ ] Queue wake-ups and scheduled recovery both drive the same durable processor; an eligible outbox item is claimed atomically, concurrent or duplicate processing is safe, completed work is a no-op, interrupted claims become recoverable, and completion is persisted before acknowledgement.
- [ ] Queue publication failure, worker failure, and redelivery cannot roll back, hide, duplicate, or otherwise change the committed Appointment or its customer Confirmation.
- [ ] Configured email delivery sends a confirmation containing the immutable scheduled time, ordered Services, exact total, Pay In Person wording, and a valid re-derivable Confirmation link, and never describes the message as a receipt or invents payment state.
- [ ] Missing email configuration and email send failure record safe operational outcomes without making Appointment confirmation or Confirmation access fail; logs and persisted state do not expose Customer Details beyond the email provider boundary.
- [ ] `appointment.created` fan-out targets only active Merchant-owned Endpoints subscribed to that event and uses one stable `evt_` Event ID and one byte-stable, PII-free body across all retries, containing only the settled thin event and authoritative Appointment locator/status/update facts.
- [ ] Every HTTP attempt receives a distinct `dlv_` Delivery Attempt ID and fresh timestamp/signature, sends the settled headers, signs `<timestamp>.<raw-body>` with HMAC-SHA256, re-runs the destination SSRF guard immediately before dispatch, and times out after ten seconds.
- [ ] `2xx`, network error, timeout, `408`, `429`, `5xx`, redirects, other `4xx`, invalid destination, and exhausted retry paths map to the settled attempt statuses and failure codes; one initial attempt plus retries at 30, 60, 90, 120, 150, and 180 seconds produce persisted attempt numbers and matching `nextAttemptAt` values before terminal dead-letter handling.
- [ ] Delivery history and operational logging retain no request or response bodies, signing or Confirmation secrets, Customer Details, capability values, or free-form exception text; repeated failure never automatically disables a Webhook Endpoint.
- [ ] The initiating trace ID is propagated through outbox processing, email, webhook dispatch, retries, recovery, and dead-letter handling, while queue messages and logs remain secret-free.
- [ ] Unit orchestration tests, real-D1 claim/completion and Delivery Attempt tests, queue/redelivery/dead-letter tests, recovery tests, fixed signature vectors, and configuration-gated email tests prove idempotency, retry fidelity, privacy, and Appointment independence.

**Out of scope:**

- Appointment confirmation, outbox creation, Confirmation-page authorization/rendering, or changing the atomic commit boundary owned by the upstream booking slice.
- Webhook Endpoint configuration or history APIs, API Token behavior, manual replay, test delivery, wildcard or non-Appointment events, automatic Endpoint disabling, and delivery-health inference.
- Appointment updates, completion, cancellation, no-show emission, reminders, marketing email, receipts, payment collection or status, online payment, rescheduling, and Customer accounts.
