# Bootstrap merchant-scoped Platform API Tokens

Type: task
Category: enhancement
Status: ready-for-agent
Blocked by: 13

## What to build

Let a Merchant Owner create the first server-to-server credential and let authorized integrations safely delegate narrower credentials. Establish the authentication, scope, response, error, and rate-limit foundation used by every Platform API v1 group.

## Acceptance criteria

- [ ] A freshly password-reauthenticated Merchant Owner can bootstrap the first API Token from Merchant settings and sees its plaintext value exactly once.
- [ ] Each Token belongs to exactly one Merchant, stores only a hash plus display prefix and metadata, and supports the exact six settled scopes.
- [ ] Token list, create, and idempotent revoke operations follow the settled `/v1/api-tokens` contract, pagination, status vocabulary, status precedence, validation, and response codes.
- [ ] A token-created credential can receive only scopes already held by the caller; no wildcard, generic admin, customer-booking, or cross-Merchant scope exists.
- [ ] Expired, revoked, malformed, and unknown credentials receive the same `401` and `WWW-Authenticate` response; a valid token lacking the route scope receives the scoped `403` response.
- [ ] Platform API authentication accepts only `Authorization: Bearer`, enables no browser CORS, and never accepts Better Auth sessions, Booking Session capabilities, Confirmation tokens, or query/body credentials.
- [ ] The `data_read`, `developer_config`, and `auth_failure` rate-limit buckets use the settled limits and safe `429` response without promising remaining-count headers.
- [ ] All errors use the stable typed envelope and trace ID, all authenticated responses are private/no-store, and validation never echoes submitted values.
- [ ] Token lifecycle audit events contain no bearer secret, and capability, Merchant settings, API handler, rate-limit, delegation, and real-D1 tests cover the complete lifecycle.

## Agent Brief

**Category:** enhancement
**Summary:** Replace the superseded Workspace token flow with the Merchant-scoped credential foundation for Platform API v1

**Current behavior:**
The repository has a working Starter-era API Token registry, D1 persistence, settings form, bearer guard, API routes, rate limiting, and audit integration. That implementation belongs to a Workspace, exposes only `read`, `write`, and `admin` scopes, uses Workspace-slug routes and generic Starter responses, and has no expiration or complete status model. Merchant settings cannot require fresh password proof, Platform API token delegation is not privilege-bounded by the caller's scopes, and the settled v1 authentication, error-envelope, cache, and rate-limit contracts are not implemented.

**Desired behavior:**
A Merchant Owner whose password was reauthenticated within the preceding 15 minutes can create the Merchant's first API Token from the Merchant App without sending the Better Auth session to the Platform API. The capability receives only proof of fresh authentication, never the password. The plaintext token is returned exactly once; persistence retains only its hash, display prefix, Merchant ownership, name, exact scopes, timestamps, creator metadata, and expiration/revocation state.

Platform API clients manage later tokens through the settled `/v1/api-tokens` collection using a Merchant-scoped bearer credential with `api_tokens:manage`. Creation may grant only scopes already held by the caller. Missing, malformed, unknown, expired, and revoked credentials are indistinguishable `401` failures, while a valid credential missing the required route scope receives the settled scope-specific `403`. Authentication accepts only `Authorization: Bearer`, establishes Merchant context from the token, enables no browser CORS, and never treats browser sessions or customer capabilities as Platform API credentials.

**Key interfaces:**

- `ApiTokenRegistry` — list, create, idempotently revoke, and verify Merchant-scoped credentials while enforcing expiration, status precedence, delegation, one-time secret exposure, and audit behavior.
- `ApiToken` and `ApiTokenStatus` — expose metadata for `active`, `expired`, and `revoked` credentials; explicit revocation takes precedence over expiration and expired credentials do not acquire a revocation timestamp.
- `ApiTokenScope` — the closed set `merchant:read`, `services:read`, `providers:read`, `appointments:read`, `api_tokens:manage`, and `webhooks:manage`; free-form, wildcard, generic administrator, and customer-booking scopes are invalid.
- Merchant settings token bootstrap — requires current Merchant Owner authorization plus password reauthentication no more than 15 minutes old, returns the plaintext once, and leaves revocation available without fresh authentication because it reduces access.
- Platform API token contract — `GET /v1/api-tokens`, `POST /v1/api-tokens`, and idempotent `DELETE /v1/api-tokens/:tokenId`, with token-derived Merchant context, settled cursor pagination, response envelopes, status filters, validation, and HTTP status codes.
- Platform API bearer guard and typed error contract — uniform `401` authentication failures with `WWW-Authenticate: Bearer`, scope-specific `403`, safe validation details, stable trace-bearing error envelopes, and private/no-store authenticated responses.
- Platform API rate limiter — `data_read` at 60 requests per minute per verified token, `developer_config` at 20 requests per minute per verified token, and `auth_failure` at 30 failed authentications per minute per source IP; denial returns the settled safe `429` response with `Retry-After: 60` and no promised remaining-count headers.
- API Token audit events — record lifecycle actors and metadata without plaintext tokens, hashes, submitted credential values, or other bearer material.

**Acceptance criteria:**

- [ ] A verified Merchant Owner can bootstrap the first token only after Better Auth has verified the password within the preceding 15 minutes; the capability receives fresh-auth proof rather than the password, and the plaintext token is displayed exactly once.
- [ ] Every Token belongs to exactly one Merchant and stores only a hash, display prefix, name, the exact six-scope set, nullable `lastUsedAt`, nullable future `expiresAt`, nullable `revokedAt`, creation metadata, and no recoverable plaintext credential.
- [ ] `GET /v1/api-tokens` requires `api_tokens:manage`, returns `{ data, page: { nextCursor } }`, includes all statuses by default, accepts repeatable `active`, `expired`, and `revoked` filters plus `cursor` and a default-50/max-100 `limit`, and orders by creation time then ID descending.
- [ ] `POST /v1/api-tokens` requires JSON no larger than 16 KiB, rejects unknown properties, accepts a trimmed 1–100-character name, 1–6 unique known scopes, and a nullable future RFC 3339 expiration, returns `201` with metadata plus the one-time plaintext token, and creates a new Token on every successful call.
- [ ] Token creation through the Platform API grants only scopes held by the calling token; escalation fails with the settled `scope_escalation_denied` response and neither creates nor exposes a credential.
- [ ] `DELETE /v1/api-tokens/:tokenId` requires `api_tokens:manage`, returns `204` for both first and repeated same-Merchant revocation, and uses the same non-disclosing not-found behavior for nonexistent and cross-Merchant targets.
- [ ] Status is derived as `revoked` before `expired` before `active`; expiration is automatic, does not set `revokedAt`, and does not emit a revocation audit event.
- [ ] Missing, malformed, unknown, expired, and revoked credentials return the same `401 unauthorized` envelope with `WWW-Authenticate: Bearer`; a valid token missing the route scope returns `403 insufficient_scope` naming only the required scope.
- [ ] The Platform API accepts credentials only from `Authorization: Bearer`, derives Merchant context only from the verified Token, has no browser CORS, and rejects Better Auth sessions, Booking Session capabilities, Confirmation Access Tokens, cookies, query credentials, and body credentials.
- [ ] `data_read`, `developer_config`, and `auth_failure` enforce the settled keys and limits in Cloudflare and local fallback modes; `429 rate_limited` names the bucket, includes `Retry-After: 60`, and does not promise remaining-count headers.
- [ ] Every API error uses `{ error: { code, message, traceId, details } }`; validation details identify paths and rules without echoing values, authenticated responses use `Cache-Control: private, no-store`, and secret or customer data never enters errors or request telemetry.
- [ ] Creation and effective revocation emit Merchant-scoped durable audit events with safe actor and token metadata; failed, repeated no-op, and automatic-expiration paths do not emit misleading lifecycle events, and no event contains bearer material.
- [ ] Capability tests, Merchant settings tests, API handler tests, delegation and cross-Merchant tests, rate-limit tests, and real-D1 lifecycle tests cover bootstrap, one-time display, pagination, expiration, revocation, authentication equivalence, insufficient scope, escalation denial, audit safety, and concurrent or repeated operations.

**Out of scope:**

- Platform API reads for Merchant, Services, Providers, or Appointments, which are delivered by the downstream read-only API issue.
- Webhook Endpoint configuration, signing-secret lifecycle, delivery, or retry behavior.
- Customer Booking Sessions, Availability, checkout, Appointment confirmation, or any customer-booking API scope.
- Multi-Merchant partner credentials, token update/get-one/rotate operations, wildcard scopes, generic administrator scopes, hard deletion, idempotency keys, ETags, or conditional updates.
- Additional Merchant roles, OAuth-based Merchant authentication, System Admin access to Merchant credentials, or using the Platform API as a first-party browser data layer.
