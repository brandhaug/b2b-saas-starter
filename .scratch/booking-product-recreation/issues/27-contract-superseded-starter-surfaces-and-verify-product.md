## Agent Brief

**Category:** enhancement
**Summary:** Contract the completed Booking Product onto its settled Merchant-owned surfaces by removing every superseded Starter and prototype runtime path.

**Current behavior:**
The repository is still in the expansion half of the migration. The Public Site owns generic authenticated Workspace routes and Starter reference behavior; the Merchant App and Booking App still expose throwaway, fixture-backed prototype flows; the shared application and storage layers remain centered on Workspace, Starter Module, readiness, report, integration, and catalog-refresh concepts; and the API and Background Workers still ship generic Starter contracts and operations. The upstream implementation graph supplies the production Booking Product replacements before this contraction begins, including secure Confirmation, Merchant Appointment and Customer Directory reads, the `/v1` Platform API, and durable booking notifications.

**Desired behavior:**
After all blocking replacement slices are green, the shipped product must contain only the settled Booking Product runtime boundaries. The Merchant App is the sole first-party authenticated product application, the Public Site remains unauthenticated public content and booking ingress, and the Booking App owns the anonymous customer journey. Throwaway routes, variant controls, explanatory stubs, fixture-only runtime behavior, generic Workspace application flows, and obsolete Starter capability call sites must be absent.

The final mutable model must be Merchant-owned and D1-backed, with the Seed Booking Scenario used only through the settled seed and test contracts. Contracted persistence must not retain a Workspace-to-Merchant bridge or deferred and legacy-shaped records such as Brand, Shop, durable Customer, persisted Availability, Sale Order, a generic payment ledger, Merchant Checkout Policy, or prototype state. The Platform API and Background Worker must expose only their settled Booking Product contracts; removal of generic API groups promised by the upstream API slice is a required invariant, not a second compatibility surface.

**Key interfaces:**

- First-party surface ownership — the Merchant App owns authenticated Merchant operations, the Public Site owns unauthenticated editorial content and booking ingress, and the Booking App owns capability-protected customer booking and Confirmation access.
- Booking Product capability composition — application callers resolve Merchant Catalog, Scheduling, Booking, developer-platform, governance, and notification behavior without Workspace-era reference capabilities or runtime fixture fallbacks.
- Booking Product persistence contract — mutable state is Merchant-owned, derived concepts remain unpersisted, obsolete Starter and legacy-shaped storage is removable only after all callers have moved, and authentication records required by the Merchant App remain intact.
- Platform API contract — only the settled unversioned health/documentation endpoints and merchant-scoped `/v1` read-and-notify surface ship; generic Starter groups and compatibility aliases are absent.
- Background operation contract — durable booking-event recovery, email, and Webhook work remain, while catalog-refresh and other obsolete Starter jobs, bindings, and call sites do not.
- Seed Booking Scenario — one typed deterministic graph supports local D1, tests, and product fixtures without any production application falling back to authored in-memory demo data.
