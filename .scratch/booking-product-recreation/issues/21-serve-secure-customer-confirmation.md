## Agent Brief

**Category:** enhancement
**Summary:** Serve a narrowly disclosed, read-only Appointment Confirmation through revocable cross-device token access and a clean cookie-authorized URL.

**Current behavior:** The Booking App has a fixture-backed migration-spike screen that demonstrates the Legacy Source's detailed post-booking information hierarchy, but it is driven by browser memory and a demo Confirmation identifier. There is no production Confirmation route, server-side Appointment read model, Confirmation token exchange, scoped access cookie, expiry or revocation enforcement, uniform not-found behavior, or response-level privacy policy. Appointment commitment and issuance of Confirmation access metadata are owned by the blocking confirmation slice and are not yet available to this view.

**Desired behavior:** A customer can open a valid Confirmation link on any device without creating an account. The first request validates the Confirmation ID and bearer token, exchanges the token for a confirmation-specific host-only `HttpOnly` cookie lasting twenty-four hours and scoped to the exact Confirmation path, then redirects to the canonical URL with no bearer secret. Reopening a still-valid link recreates the cookie. Every authorized read revalidates the Appointment's Confirmation access metadata so thirty-day expiry, targeted token-version revocation, signing-key rotation, and emergency removal of a previous key take effect without exposing whether unrelated records exist.

The clean Confirmation view remains available if the Public Booking Page becomes Unpublished. It derives immutable customer-visible booking facts from the Appointment snapshot while reflecting the Appointment's current operational status. It discloses only that Appointment's status, time, Provider and Service snapshots, Pay In Person summary, Merchant contact or location facts, and captured Customer Details. It contains no mutation controls, payment-status inference, other Appointment data, Customer Directory data, merchant internals, or third-party analytics. The presentation retains the settled detailed Legacy Source hierarchy but uses Confirmation and Appointment language rather than receipt or Sale Order language.

**Key interfaces:**

- Confirmation access verifier — derives and validates a token from the Confirmation ID, token version, expiry, and signing-key ID; accepts retained verification keys, uses the current key for newly issued access, and rejects revoked, expired, or emergency-invalidated access without persisting plaintext bearer secrets.
- Confirmation token exchange — accepts the first valid bearer request, creates the path-scoped host-only `HttpOnly` access cookie, and redirects to the canonical clean Confirmation URL without retaining the token in navigation or downstream requests.
- Confirmation cookie authorization — binds one cookie to one exact Confirmation path and validates current access metadata on every read so version revocation, expiry, and key removal also invalidate previously exchanged access.
- Confirmation read model — derives one customer-safe view from the Appointment snapshot and current Appointment Status without joining live catalog facts that could rewrite history or exposing adjacent Merchant or Customer data.
- Confirmation HTTP boundary — returns the same generic `404` for unknown IDs and invalid credentials, returns the settled explanatory `410` only for a valid but expired credential, and applies `Cache-Control: private, no-store` plus `Referrer-Policy: no-referrer` to token exchange, error, redirect, and clean-view responses as applicable.
- Confirmation presentation — renders the source-faithful detailed booking hierarchy with Pay In Person wording and canonical Booking Product terminology, with no receipt, Sale Order, payment-status, cancellation, rescheduling, or other mutation behavior.

**Acceptance criteria:**

- [x] A first request with a valid Confirmation ID and token sets a confirmation-specific host-only `HttpOnly` cookie with a twenty-four-hour lifetime and exact Confirmation-path scope, then redirects to the clean canonical URL without the bearer token.
- [x] The clean URL is authorized only for the matching Confirmation, and reopening a still-valid emailed link on the same or another device recreates access without a customer account.
- [x] Confirmation access expires thirty days after the Appointment ends; each read honors current token version and signing-key metadata, retained keys verify eligible older access, targeted version increments revoke one Confirmation, and emergency previous-key removal invalidates access signed by that key.
- [x] Unknown Confirmation IDs, malformed tokens, invalid tokens, wrong-path cookies, and credentials for unrelated Confirmations are indistinguishable generic `404` responses; a valid but expired credential receives the settled explanatory `410`.
- [x] An authorized Confirmation remains readable after its Public Booking Page is Unpublished, preserves immutable Service, Provider, money, time, timezone, Checkout Path, and Customer snapshots, and reflects the Appointment's current Scheduled, Completed, Cancelled, or No Show status.
- [x] The response exposes only the allowed facts for that Appointment and never exposes other Appointments, Customer Directory data, live private catalog data, merchant administration data, mutation controls, bearer secrets, or a payment status.
- [x] Token exchange, redirects, clean views, and applicable error responses prevent caching and referrer leakage with the required headers, and the Confirmation surface initializes no third-party analytics.
- [x] The UI preserves the detailed post-booking information hierarchy across the settled mobile and desktop Booking App presentation while consistently using Confirmation, Appointment, and Pay In Person language.
- [x] Automated coverage exercises token exchange, redirect cleanliness, cookie lifetime and exact path scope, cross-device link reuse, expiry, targeted revocation, retained-key rotation, emergency key removal, Unpublished access, status changes, response headers, uniform errors, and cross-Appointment non-disclosure.

**Out of scope:**

- Atomically creating the Appointment, immutable snapshots, Confirmation access metadata, terminal Booking Session record, and durable outbox item; those are prerequisites owned by the blocking confirmation slice.
- Confirmation email composition, delivery, retries, queue recovery, or webhook fan-out; this slice only serves links and cookies generated from already-issued access.
- Customer accounts, OTP or social sign-in, durable Customer profiles, Customer Directory behavior, or access to multiple Appointments through one credential.
- Appointment cancellation or rescheduling, other customer mutation controls, online payment, payment collection, payment status, receipts, Sale Orders, refunds, or card details.
