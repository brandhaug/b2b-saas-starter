Every request, cron tick, and queue message runs inside one scope from `packages/logger`. That scope emits a single structured wide event, opens an OpenTelemetry span, and records RED metrics — three views of the same thing, so they can never disagree. Without configuration the event goes to the console and Cloudflare Workers Logs. Set one env var and the same data is exported over OTLP.

## Wide events

One canonical line per request per service, rather than log lines scattered through the handler.

`withHttpRequestScope({ service, event, request, env })` owns the whole envelope for an HTTP handler — trace continuation, environment enrichment, `pathname`/`method` — and `withTriggerScope` does the same for cron and queue triggers. Handlers add business context with `annotateWide` (an alias of `Effect.annotateLogsScoped`), and it lands on the same event:

```ts
const refresh = Effect.gen(function* () {
  const moduleCount = yield* runCatalogRefresh
  yield* annotateWide({ workspaceId: ctx.workspace.id, plan: 'pro', moduleCount })
})
```

Every event carries the request's identity (`service`, `traceId`, `otelTraceId`, `otelSpanId`), the deployment's identity (`commitHash`, `serviceVersion`, `region`, `environment`), the outcome (`status`, `durationMs`, and on failure `errorKind`/`errorTag`), and whatever business context the handler added. There are two levels and no more: `info` when the scope succeeded, `error` when it did not — with the failure `Cause` attached.

The event is emitted from `Effect.onExit`, not a scope finalizer. Finalizers run after `annotateLogsScoped` restores the previous annotations, which would drop every field a handler added.

## Traces

Trace context crosses every hop:

| Hop                         | Carrier                                                           |
| --------------------------- | ----------------------------------------------------------------- |
| Client → worker             | W3C `traceparent` (or B3), decoded into the request span's parent |
| Worker → any HTTP call      | Injected by Effect's `HttpClient`, including webhook deliveries   |
| Worker → D1 (query builder) | Automatic child spans (`sql.execute`)\*                           |
| API → queue → background    | `traceparent` stamped on the queue message by `WebhookPublisher`  |

\* Only for reads and writes that go through the `@effect/sql-d1` client. `batch()` (`packages/db/src/service.ts`) compiles its statements and runs them through the raw `D1Database` binding's own `prepare`/`batch` calls, bypassing the client, so a batched write emits no span. The provider-light default Seed layer has no SQL client at all, so there is nothing to span there either.

A page load against the Live D1 layer therefore reads as one trace: `web.request` → `capability.workspace` → `sql.execute`. In the web worker a global TanStack Start request middleware (`src/start.ts`) opens that single scope; loaders and server functions join it with `withWebRequestScope` instead of starting traces of their own.

`x-trace-id` is still there as the value a support ticket can quote, and it now defaults to the OTel trace id, so one string resolves in both the log stream and the trace backend.

## Metrics

Two series come off the same scope, attributed by `service`, `event`, and `status`:

- `starter.requests` — a counter of completed scopes.
- `starter.request.duration` — a histogram of wall-clock duration.

Attributes stay deliberately low cardinality. Workspace, token, and endpoint ids belong on the wide event and on span attributes, not on a metric series.

## Exporting

Set `OTEL_EXPORTER_OTLP_ENDPOINT` to a collector's OTLP/HTTP port and traces, metrics, and the same canonical log records are exported. Nothing else changes: the console JSON event keeps flowing to Workers Logs.

```bash
# .env — any OTLP/HTTP collector, local or vendor-hosted
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
OTEL_EXPORTER_OTLP_HEADERS=x-vendor-key=...   # comma-separated key=value
SERVICE_VERSION=1.4.0
GIT_COMMIT_SHA=$(git rev-parse HEAD)
ENVIRONMENT=production
```

The last three also fill the `commitHash`/`serviceVersion`/`environment` fields on every wide event and the `service.version`, `vcs.ref.head.revision`, and `deployment.environment.name` OTel resource attributes — which is what lets you correlate an incident with a deploy.

### One caveat worth knowing

The exporter layer is built **per invocation**, never per isolate — see ADR 0050 for why. Each entry point provides it with `Effect.provide(layer, { local: true })`; follow the same shape for any new entry point — `makeOtlpLayer` documents it.

## Sentry and PostHog

Both remain Optional Provider Modules with reserved env gates (`SENTRY_DSN`, `POSTHOG_KEY`). No SDK is wired, and missing configuration never throws. Pointing the OTLP endpoint at a collector that forwards to your vendor is the supported path today.

## Audit events vs. wide events

Wide events are operational and ephemeral. Audit Events are persisted in the `audit_events` D1 table and exposed via `AuditEventLog.list` (with `WorkspaceContext`) and `AuditEventLog.listGlobal`. The two streams coexist: a request that emits a wide event may also create an Audit Event when the action is governance-sensitive — a plan change, a member role change, a token revocation, a webhook endpoint update.
