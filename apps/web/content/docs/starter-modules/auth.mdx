The auth module is a Starter Module wired through Better Auth. The Local Auth Path (email and password) works without any external configuration; OAuth providers are activated only when their secrets are present.

## What ships ready

- Email/password authentication with sessions in D1
- Public sign-up (`/sign-up`) — registration with auto sign-in
- Password reset: forgot-password form (`/forgot-password`), single-use one-hour token, reset page (`/reset-password`), and session revocation on success (`revokeSessionsOnPasswordReset`)
- Email verification: sent on sign-up (`sendOnSignUp`), verified through the `/api/auth/verify-email` token hop, landing on `/verify-email`; the unverified state surfaces as a banner on `/workspaces` with a resend action. Verification is encouraged, not enforced — `requireEmailVerification` stays off so provider-light local dev (log-mode email) never locks the sign-in it cannot unblock
- Username plugin (for friendlier display names)
- Admin plugin (System Admin role) — registered with `adminRoles: ['admin']`
- Organization plugin, remapped onto the starter's Workspace vocabulary — it backs Members, Invitations, and Workspace Roles (ADR 0051). Teams and runtime-defined roles are switched off
- TanStack Start cookie bridge via the `tanstackStartCookies()` plugin, registered last so other plugins' cookies reach the framework
- Better Auth React client (`authClient`) for current user and current session; workspace membership loads from the `WorkspaceMembership` capability in route loaders
- Skip-to-content and accessible form patterns on the sign-in page

## Lifecycle emails

Password-reset and verification emails flow through the same React Email dispatcher as invitations. `packages/auth` declares an `AuthEmailSender` port (it cannot import the sibling `email` package); `apps/web/src/lib/server/auth-emails.ts` supplies the adapter, so the flows work in log mode with zero providers. The emailed links point at the auth handler's own token-exchange routes, which validate and redirect to the app pages — see the [Email module](/docs/starter-modules/email) for the template inventory.

## What activates when configured

- GitHub OAuth (the Example OAuth Provider) — registered only when `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are both set
- Additional Example OAuth Providers can be wired the same way

Each provider is an Optional Provider Module. Missing config does not block local development.

## Sessions

Sessions are handled by Better Auth with the `tanstackStartCookies()` plugin: signed HTTP-only cookies, signed with `BETTER_AUTH_SECRET`, scoped per Better Auth's defaults. Trusted origins come from `BETTER_AUTH_TRUSTED_ORIGINS` (or fall back to `BETTER_AUTH_URL`). The session deliberately does not carry an active workspace: the organization plugin writes `session.activeOrganizationId` and nothing reads it, because the workspace is resolved from the slug in the URL. Two sources of truth for "which workspace" is how a user ends up looking at one workspace's URL and another's data.

## System Admin

The Better Auth admin plugin is enabled and exposes a System Admin UI behind `/admin`. System Admin is distinct from a Workspace Role: it controls user-level governance, not workspace-level membership.
