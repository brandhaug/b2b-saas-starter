Workspace owners configure OIDC or SAML connections in settings. Admins can read sanitized connection details but cannot change them. Secrets are write-only.

## Set up a connection

1. Add a disabled connection with one exact email domain and your IdP configuration. OIDC requires an issuer, client ID, and secret. SAML requires metadata.
2. Request the DNS verification record and publish the displayed TXT value at the displayed record name. Verify it in settings.
3. Check metadata, then complete **Test sign-in** with the IdP. Metadata validation alone does not make a connection ready.
4. Enable the tested connection. Before requiring SSO, enroll an independent owner recovery factor: a passkey, or a password with MFA.
5. Confirm the impact of requiring SSO. Every human member must then authenticate through this connection to access the workspace.

Configuration changes require recent authentication. If requested, sign in again before continuing. A session refresh does not count as a new authentication.

Operators can set `SSO_PROOF_TTL_SECONDS` and `SSO_CONFIGURATION_AUTH_MAX_AGE_SECONDS`. Defaults are 43200 and 300 seconds. Supported ranges are 1–604800 and 1–3600 seconds respectively; unset or invalid values retain the defaults. Changes apply to newly issued proofs and subsequent configuration requests.

## Domains and membership

A verified domain belongs to one workspace per deployment. A subdomain is a separate claim. Creating an unverified connection never reserves a domain or routes another workspace's users.

Existing members and people with pending invitations can use the IdP. This includes invited contractors with a different email domain. Optional auto-join admits verified IdP identities from the claimed domain as members only. Password, magic-link, social, and other non-SSO sign-ins never gain membership from the domain claim.

## Required SSO

The requirement applies to workspace access, including requests from sessions that existed before activation. It does not disable the user's other account sign-in methods or lock unrelated workspaces.

An SSO proof belongs to one session and one connection generation. Its default lifetime is 12 hours. Session refresh cannot extend it. Impersonation and System Admin status cannot bypass the requirement.

API tokens remain machine credentials. Creating or managing those tokens is human workspace access and must satisfy SSO. Interactive MCP clients retain the session proof from consent and need renewed authentication when it expires.

## Replace or retire a connection

Configure and test a replacement while the existing connection remains active. Activate it as a replacement to switch the requirement and invalidate authentication through the retired connection together.

Testing a disabled replacement creates an account session without granting access through that replacement. If the workspace already requires SSO, sign in through the current IdP again before returning to settings and choosing **Activate replacement**. After activation, sign in through the replacement to regain workspace access.

A required connection cannot be deleted or disabled by itself. Explicitly disable the requirement first, or activate a tested replacement. Deleting the user who originally registered a connection does not delete the connection.

## DNS failures and recovery

The background worker checks domain verification daily. A missing TXT record or DNS failure starts a fixed seven-day grace period and notifies owners. Repeated failures do not restart the deadline.

After the deadline, new SSO authentication stops. Required SSO stays enforced, and existing proofs expire normally. Restoring the expected TXT record allows a subsequent successful check to restore new authentication.

An operator can grant an existing owner a one-hour SSO repair exception. The owner must authenticate with an independent factor enrolled before the grant. The exception does not open workspace data or developer controls. Creation, use, and expiry are audited and notify owners.

See the operator SSO runbook in `docs/operations.md` for recovery and explicit domain transfers.

## Audit and limits

Connection changes, verification status changes, SSO sign-ins, and recovery activity have audit records. SAML single logout is disabled, so signing out of the app ends only its app session.

Protocol integration lives in `packages/auth`. Workspace policy and connection lifecycle live in `packages/capabilities`. ADRs 0069 and 0077 record the ownership and enforcement decisions.
