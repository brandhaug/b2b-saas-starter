The starter is Cloudflare-first. Production resources are declared once in the root `alchemy.run.ts` using Alchemy v2 and provisioned with a single command.

## What gets provisioned

- One D1 database shared by the six application Workers
- Public Site, Merchant App, Operations App, Booking App, Platform API, and Background Worker
- A booking-events Queue consumed by the Background Worker for durable recovery
- A restricted Cloudflare `SendEmail` binding; production Operations readiness requires it
- Dedicated rate-limit bindings for Merchant, Booking, Platform API, and Operations categories

## Deploy

```bash
bun run deploy
```

`bun run deploy` is `bun alchemy.run.ts` — it executes the Alchemy Stack programmatically rather than going through a separate CLI. Each Worker also has a hand-maintained `wrangler.jsonc` that mirrors the Alchemy declaration so `wrangler dev` and `wrangler d1 migrations apply` keep working locally; Alchemy is the source of truth for production.

## Environment configuration

Sensitive values are wrapped in `effect/Redacted` inside `alchemy.run.ts` so they never appear in logs or stack traces. Merchant and Operations secrets must be distinct, and each realm has its own origin and trusted-origin list. Optional product providers remain module-aware; missing Operations email configuration fails production readiness closed. See `ARCHITECTURE.md`, `.env.example`, and `docs/operations.md` for the complete split.

Cloudflare Access is deferred and is not part of application correctness. Add it later only as defense in depth; do not use it to replace Operations Auth, current-state authorization, rate limiting, or audit evidence.

## Rolling back

`bun run destroy` (which is `bun alchemy.run.ts --destroy`) tears the entire stack down. Targeted rollbacks today go through redeploying a previous commit from CI — there is no versioned rollback flag in the starter's scripts.
