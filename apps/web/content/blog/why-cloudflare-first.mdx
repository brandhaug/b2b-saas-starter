The starter commits to Cloudflare for compute, persistence, and background work.
Workers run the three applications, D1 stores their shared data, Queues deliver
background jobs, and R2 stores optional workspace exports.

That choice avoids maintaining interchangeable database and deployment adapters.
The cost is platform dependence: moving to another host would require replacing
the Cloudflare bindings and infrastructure definitions.

Alchemy declares production resources in `alchemy.run.ts`. Queue and rate-limit
settings come from `infra/bindings.ts`, which also supplies the generated local
Wrangler configurations. Local development uses the same binding shapes with
persisted local D1.

Stripe, Sentry, PostHog, and other optional providers work alongside those
Cloudflare resources. Unset provider configuration keeps their integrations
inactive. See [optional providers](/docs/getting-started/optional-providers) for
configuration and [deployment](/docs/getting-started/cloudflare-deployment) for
the production workflow.
