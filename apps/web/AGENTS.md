# apps/web

TanStack Start web app served by a Cloudflare Worker (`vite.config.ts` uses the `cloudflare:workers` shim). Dev server runs on `:3071`. Owns the public showcase, knowledge content, auth screens, the seed-backed workspace reference app, admin dashboard, Storybook, Vitest (unit), and Playwright (e2e).

## Routes

- `/` — interactive architecture showcase, capability-backed against the `starter-lab` seed workspace. The loader's actorless read (`src/lib/server/demo-showcase.ts`) feeds the live-numbers strip (members, tokens, endpoint success, notifications) and the REST snippet, which embeds the exact `workspaceOverview` JSON the endpoint serves — page and API cannot drift. A missing showcase workspace hides the strip instead of failing the page.
- `/demo` — the live demo: the signed-in dashboard's page component rendered from the same actorless read for a member-view payload (owner segments are `null` because the loader never reads them). The page's ports keep it read-only — the list port answers from loader data, and mark-as-read rejects with a reason pointing at the seeded demo credentials. No session, no mutation path; an unseeded deployment 404s through the shared failure mapping. The slug is fixed (`DEMO_WORKSPACE_SLUG`, `lib/demo-workspace.ts`) — the actorless read is sanctioned for the showcase workspace only, so the route must never accept a workspace param.
- `/docs`, `/blog`, `/faq`, `/changelog` — checked-in MDX/JSON knowledge content inside one pathless knowledge layout (`src/routes/_knowledge.tsx`): one collapsible left nav, one article column, per-article table of contents with its below-xl disclosure. URLs are unchanged; `/help` and `/pricing` are pure redirects into the docs that replaced them.
- `/sign-in` — email/password via Better Auth, plus "Sign in with a passkey": conditional UI (passkey autofill) where the browser supports it — the `webauthn` autocomplete token on the email field plus an on-mount preload behind `isConditionalMediationAvailable` — with the button as the universal fallback. A passkey success opens the session in the ceremony itself (ADR 0056); there is no two-factor hop. The loader also reads the active social provider ids server-side (`lib/server/social-providers.ts`, env-gated): one "Continue with …" button per active provider above the email form, none when unconfigured, plus the `lastLoginMethod` hint ("Last signed in with GitHub") when the plugin's cookie remembers a method. Carries the forgot-password link and the sign-up link.
- `/sign-up` — public registration (auto sign-in, verification email follows). Turnstile-protected when configured: the page's loader fetches the site key server-side, the widget token rides `x-turnstile-token`, and the auth route verifies it via `TurnstileVerifier` (see `lib/server/turnstile.ts`). Unset env = no widget, no gate. The same loader also carries the active social provider ids, rendered exactly as on `/sign-in`.
- `/forgot-password` — request form; the response message is constant whether or not the email exists (non-disclosure rule, same as the endpoint).
- `/reset-password` — the landing page for the emailed reset link. The link points at `/api/auth/reset-password/:token` (the auth handler), which validates the token and redirects here with `?token=` or `?error=`; one opaque "cannot be used" state for every failure. Success redirects to `/sign-in` — the reset revokes every session.
- `/verify-email` — the landing page for the verification link. Same hop shape: `/api/auth/verify-email` redirects here (success plain, failure with `?error=`); `autoSignInAfterVerification` means the success arrival carries a session cookie. The unverified state itself surfaces as the `EmailVerificationBanner` on `/workspaces`, with a resend action.
  Members owns the roster plus the invitation flow (its loader composes the invitation segment through `whenPermitted({ invitation: ['create'] })`); settings carries workspace identity — rename (`organization:update`) and delete (`organization:delete`) through `src/lib/server/workspace-lifecycle.ts` — plus the owner-only data-export panel: the loader composes the exports segment through `whenPermitted({ workspaceExport: ['request'] })` (`src/lib/server/workspace-exports.ts` mints signed download links at load time against `API_PUBLIC_URL`, default `http://localhost:8787`), the segment is `null` for admins and members so the panel is absent, and without a configured export bucket it explains why instead of offering a button that would fail (ADR 0055). The API tokens page is the create/list/revoke surface (`apiToken:create/list/revoke`, loader hard-gated on `apiToken:list` so a plain member meets a denial at the URL) backed by `src/lib/server/api-tokens.ts`; the webhooks page is the operator surface (`webhook:list` hard-gates the loader) backed by `src/lib/server/webhooks.ts` — create with the one-time secret reveal, disable, update, delete, rotate (one-time reveal plus the 24h dual-signing grace note), a per-endpoint deliveries drawer (`webhook-deliveries-drawer.tsx`) with the attempt timeline and recorded evidence, replay on failed rows (`webhook:replay`), and a test send (`webhook:test`); the assistant page hard-gates on `{ assistant: ['read'] }` and asks through `AssistantService` (`src/lib/server/assistant.ts`) — its loader carries `configured`, and with no provider configured the form is replaced by honest copy instead of an error; nav and palette thread the current slug (`src/routes/workspaces.tsx` is the subtree's auth-gate layout route).
- `/workspaces/$workspaceSlug/billing` — plan catalog + the Stripe handoffs (`src/lib/server/billing.ts`). The Manage-billing button renders only when the Billing capability itself reports Stripe configured, and both server fns (`startCheckoutServerFn`, `startPortalSessionServerFn`) compose their success/cancel/return URLs server-side — the client names only its slug (and plan), so neither handoff is an open redirect. Invoices, payment method, and cancellation live in the Stripe Billing Portal, not here (ADR 0060).
- `/workspaces/$workspaceSlug/members` — the roster plus the seat prompt: the loader also computes `seatUsage` (`plan-catalog.ts`) from the resolved workspace's plan, and a flat plan past its included seats renders an upgrade prompt linking to billing. Members are never blocked at a seat ceiling — seats prompt, resource ceilings refuse. The membership and invitation server functions trigger seat sync below the capability seam; the web worker's `BILLING_QUEUE` binding carries the message to the background worker (unwired locally, where the provider webhook reconciles instead).
- `/admin` — Better Auth admin plugin dashboard, gated by `requireAdmin` (admin role required; non-admins 404). System-level: users via `PlatformUserAdmin.listUsers` (`src/lib/server/admin.ts`), audit events via `runCapabilities` + `AuditEventLog.listGlobal` — it never borrows a workspace, so the shell renders with `workspaceSlug={null}` and no unread badge. Row actions: `BanUserAction` and `ImpersonateUserAction` (ADR 0054). Impersonation runs through server functions (`impersonateUserServerFn` / `stopImpersonatingServerFn`) → `PlatformUserAdmin.startImpersonation` / `.stopImpersonation` → `webUserAdminBinding` → the plugin's `impersonateUser` / `stopImpersonating`; `tanstackStartCookies()` forwards the plugin's cookie swap onto the server-function response, and the action then `router.invalidate()`s so the gates re-read the session. `impersonateUserServerFn` refuses to start from a session that is already an impersonation (no nesting); `stopImpersonatingServerFn` takes the admin from `session.impersonatedBy`, never a body.
- `/invitations/accept?invitation=<id>` — the destination of the emailed invite link. Deliberately **outside** the `/workspaces` subtree: those routes resolve a workspace the visitor must already be a member of, and an invitee is not one until they accept. It keeps its own `requireSession` gate (an invitation is addressed to an email, so there is nothing to match until we know who is asking) and shows one opaque "cannot be used" state for every failure — expired, cancelled, already accepted, or addressed to somebody else.
- `/account` — account-level security settings (linked sign-in providers with unlinking via `LinkedAccountsPanel` — a provider can be removed only while another method remains, matching Better Auth's last-account refusal; two-factor enable/verify/disable via `TwoFactorPanel`; passkey register/rename/remove via `PasskeysPanel` — names are labels; the WebAuthn ceremony is browser-mediated; active-session list with per-session revoke and "sign out everywhere else" via `SessionsPanel`). Like `/invitations/accept`, it keeps its own `requireSession` gate: it is user-level, not workspace-level. On an impersonation session (`session.impersonatedBy`) the linked-accounts, two-factor, and passkey panels are each replaced by a one-line reason — an impersonating admin must not change the user's sign-in surface, and the catchall refuses those endpoints anyway.
- `/account/notifications?kind=<kind>` — where every notification email's unsubscribe link lands (ADR 0061): the same preferences panel with that kind's row highlighted. A signed-in page, not a one-click endpoint — the link carries no token, so a forwarded email changes nobody's preference. The route file is `account_.notifications.tsx` (flat, trailing underscore) because `/account` has a component and no `<Outlet />`.
- `/two-factor` — the sign-in challenge page. When two-factor is enabled, credential sign-in opens no session; it sets Better Auth's short-lived two-factor cookie and `SignInPage` routes here (preserving `?redirect=`). Verifying a TOTP code (`authClient.twoFactor.verifyTotp`) exchanges the cookie for a session.
- `/api/auth/$` — Better Auth catchall handler.

## Data fetching

- Route loaders use `runWorkspaceCapabilities(slug, effect, actor)` (`src/lib/capabilities.ts`) to call `@b2b-saas-starter/capabilities` directly. Reads that are not scoped to one workspace (the `/workspaces` index projection, `/admin`'s global audit log) use `runCapabilities(effect)` from the same file — it provides the capability services without `WorkspaceContext`. **There are no REST round-trips from this app to `apps/api`** — `apps/api` is the _external_ surface.
- Prefer the named read projections from the capabilities package over hand-composed `Effect.gen` loaders: the dashboard loads `workspaceDashboard`, which ships pre-computed aggregates (unread count). Components render those values — don't re-derive them in `useMemo`.
- **Permission-shaped payloads.** The workspace loaders live in `src/lib/server/workspace-dashboard.ts` and `workspace-settings.ts`, not inline in the route. Each is assembled by `workspacePage(gate, segment)` (`src/lib/server/page-frame.ts`), the shared frame: it hard-gates the page's own read permission with `requireWorkspacePermission`, resolves the `WorkspaceContext` once, and closes by attaching the single `viewer` every payload carries — the page supplies only its own segment, and a page that badges unread notifications composes the shared `unreadCount` read into its `Effect.all`. Segments carrying a second permission stay soft: wrap them in `whenPermitted(permission, effect)` (`src/lib/server/authorize.ts`), which yields `null` instead of failing. A `null` segment means the read never ran, so a member's serialized loader data carries no API-token count, no webhook count and no invitation list — hiding those in the component alone would still ship them in the SSR payload. The payload types are declared in the app, not in `capabilities`: which segments exist is an authorization decision, and capabilities do not make those.
- `src/lib/capabilities.ts` reads bindings from `cloudflare:workers` (same as `auth-runtime.ts`): with a real `DB` binding the Live D1 layer activates; without one the in-memory Seed layer keeps the app provider-light. Never hardcode an empty env. `vite dev` aliases to `cloudflare-workers-shim-dev.ts`, which attaches the persisted local D1 (`packages/db/.wrangler`, from `db:migrate:local` + `db:seed`) via wrangler's `getPlatformProxy` when it exists — so credential sign-in and Live layers work locally (ADR 0049). Test and build keep the inert `cloudflare-workers-shim.ts` (`DB: undefined`); the dev shim's Node imports stay behind `import.meta.env.SSR` because dev serves it to the browser too. Client-side navigations run loaders in the browser against the Seed layer regardless, so Seed/Live fixture equivalence (demo user membership included) is load-bearing.
- Mutations use TanStack Start server functions (e.g. `createApiTokenServerFn`) that wrap a capability call. Server-fn inputs are validated by `effect/Schema` **with all constraints in the schema** (no imperative re-validation).
- **A server function holds the session gate; the behaviour sits below it as an exported effect.** `src/lib/server/invitations.ts` (declarations) + `invitations.effects.ts` (behaviour) is the reference split: `sendInvitation`, `cancelInvitation`, `invitationPreview` and `acceptInvitation` are effects taking the actor's address, the request origin and the `EmailDispatcher` as arguments, and each `…ServerFn` adds only `requireRequestSession()`, `requestOrigin()` and the binding. The two-file layout is load-bearing for the bundle: the route tree ships statically to the browser, so `invitations.ts` holds only the `createServerFn` declarations, input schemas and payload types, and its handlers reach the effects module through dynamic `import()` — handler bodies are stripped from the client build, so react-email, the auth session gate and the plugin binding never ship (asserted after every build by `scripts/assert-client-boundary.mjs`). That split is also what makes the permission gates and the invitation non-disclosure rule testable — `requireRequestSession` reaches the auth runtime, which no Vitest harness stands up; the tests import `invitations.effects.ts` directly.
- Mutations that go through Better Auth's `organization` plugin pass a **binding** as the last argument to `runWorkspaceCapabilities` / `runCapabilities` (`CapabilityBindings`). The adapter lives in a server-only module (`src/lib/server/invitation-binding.ts`) and reaches the plugin through `sessionCall` / `serverCall` (`src/lib/server/plugin-call.ts`) — `sessionCall` for the `requireHeaders: true` endpoints (the great majority), `serverCall` for the two trusted headerless routes (`addMember`, `createOrganization`) that take the acting user from the body. It is passed per call rather than sitting on the module-level `starterEnv`: `src/lib/capabilities.ts` is bundled for the browser too, so a module-level adapter would drag the whole Better Auth server instance into the client bundle. Every invitation endpoint the plugin exposes is `requireHeaders: true`, which is the whole reason the adapter has to live in the app.
- Effect Atom for client server-state is **not wired** today; loaders + server functions are sufficient. Revisit once a route needs subscribe/optimistic semantics.

## Observability

- **One wide event per HTTP request, opened in exactly one place.** `src/start.ts` registers a global TanStack Start request middleware (`createStart({ requestMiddleware })`) that wraps every server request — SSR document renders and server-function calls — in `runWebRequestScope` (`src/lib/observability.ts`). It continues any inbound `traceparent`, provides `makeOtlpLayer` per invocation (never per isolate — see ADR 0050), and emits the canonical line with `statusCode` and a `nested` array when the response is ready. `WideEventLoggerLive` is provided isolate-level from a module-scope `ManagedRuntime`, not rebuilt per request.
- **Nested work joins that scope; it never opens its own.** `runWorkspaceCapabilities` / `runCapabilities`, the `/api/auth/$` handler, and the auth gates in `src/lib/server/auth.ts` / `src/lib/server/admin.ts` all call `withWebRequestScope({ event, metadata }, effect)`, which becomes a child span under the request span, reuses the request's loggers and exporters, and folds its own `Effect.annotateLogsScoped` fields into the request's event. Without it a page load emits one wide event and one root trace _per loader_. Don't call `withTriggerScope` directly from a loader.
- Outside a request — a client-side navigation re-running loaders against the Seed layer, or a standalone test — `withWebRequestScope` falls back to its own scope and tags the event `scope: 'standalone'`, so a missed join is visible in the log stream instead of silently producing an extra root trace.
- The registry is a `WeakMap` keyed by the request object (an isolate interleaves concurrent requests, so a module-level "current" would race). `src/lib/request-context.ts` exposes the lookup as `currentRequest()`, wrapping `createIsomorphicFn`/`getRequest` in one place: it keeps `getRequest` out of the browser bundle, returns `undefined` rather than throwing with no ambient request, and is the seam tests mock.
- **One server runtime: `webRuntime`** (`src/lib/observability.ts`). Every server-side Effect run in this app goes through it — the request middleware, `runWorkspaceCapabilities` / `runCapabilities`, the env gate, the lifecycle-email dispatch — instead of a bare `Effect.runPromise*` per call site. It holds the isolate-level loggers (`WideEventLoggerLive`) and nothing else; the OTLP exporters stay per invocation.
- `authRuntime` holds only the `Auth` service, and is the one runtime that stays separate: loggers, tracer, and exporters belong to one request and must not live on a per-isolate runtime — the auth gates reach them by joining the request scope (above), not by reading `authRuntime` — and merging `AuthLive` into `webRuntime` would drag the Better Auth server into the browser bundle, since `capabilities.ts` runs loaders on `webRuntime` and is bundled for the client. That is why `withWebRequestScope`'s standalone branch still provides `WideEventLoggerLive` itself: `readSession` runs on `authRuntime`, which has none. `Logger.layer` replaces the logger set, so the doubled provide emits one line, not two (tested).
- `OTEL_EXPORTER_OTLP_ENDPOINT` (plus `SERVICE_VERSION` / `GIT_COMMIT_SHA` / `ENVIRONMENT`) reaches local dev through `src/lib/cloudflare-workers-shim.ts`. Unset, the console JSON event is the whole story and nothing fails.
- **The required-env gate runs before the request scope.** `src/start.ts` registers `configGateMiddleware` ahead of the observability middleware; it calls `enforceRequiredEnvOnce` (`src/lib/server/env-gate.ts`) once per isolate. With `ENVIRONMENT=production` and an insecure `BETTER_AUTH_SECRET`/`BETTER_AUTH_URL` (missing, placeholder, or too-short — see `auditRequiredEnv` in `@b2b-saas-starter/env`) every request throws `InsecureProductionEnvError`; with another `ENVIRONMENT` value it emits one standalone `config.insecure` wide event and continues. Unset `ENVIRONMENT` is local dev and stays silent.

## Auth

- The auth stack runs on `effectful-better-auth` (the sibling repo's Effect v4 wrapper): `packages/auth` mints the `Auth` service (`Auth.Tag` provides `{ api, instance }`; `api` endpoints are Effects failing `BetterAuthApiError`) and the `AuthConfig` key; `src/lib/auth-runtime.ts` provides `AuthConfig` from worker env and exposes the per-isolate `authRuntime`. `/api/auth/$` mounts the handler via `toHttpEffect` (rate limiting, wide events, and auth audit wrap it as ordinary Effect middleware).
- Server gates live in `src/lib/server/auth.ts`:
  - `requireSession(redirectTo)` — redirects anonymous visitors to `/sign-in` (preserving `?redirect=`) and returns the session. It runs ONCE in the `/workspaces` layout route's `beforeLoad` (`src/routes/workspaces.tsx`); child routes read `context.session` instead of re-gating. Don't copy the gate into new `/workspaces/*` routes.
  - `requireAdmin(redirectTo)` for `/admin` — additionally checks the Better Auth admin role (`user.role === 'admin'`); non-admins get a 404 (non-disclosing). `/admin` keeps its own `beforeLoad` gate.
  - `RouteSession` (what the gates put on route context) carries `user.{id,name,email,emailVerified,role,twoFactorEnabled}` and `impersonatedBy: string | null` — nothing else. `toRouteSession` is the projection and `auth.test.ts` pins its keys.
  - `requireRequestSession()` inside **every** workspace-data server-function handler. On session expiry it fails with the typed `UnauthorizedError` (message displayed by the calling form) — never a redirect; redirects belong to navigation gates only.
- Workspace loaders and server functions must pass the actor (`{ userId: session.user.id }`) to `runWorkspaceCapabilities`; the capabilities layer enforces workspace membership and non-members get `WorkspaceNotFound`. Only trusted public-showcase reads (`/` homepage) omit the actor.
- Membership is not permission. Every workspace **mutation** additionally composes `requireWorkspacePermission(permission)` (`src/lib/server/authorize.ts`) inside the effect it guards — it reads the actor the `WorkspaceContext` layer resolved and asks the shared `authorize()` path in `@b2b-saas-starter/authz`. Name the permission (`{ apiToken: ['create'] }`), never the role: `if (actor.role === 'owner')` puts the role table in two places. `createApiTokenServerFn` is the reference. A denial leaves the boundary as `ForbiddenError`, whose `message` the calling form displays.
- **The UI gates too, and never by role name.** The loader payload carries `viewer: { role }`; components ask `viewerCan(viewer, permission)` (`src/lib/permissions.ts`), which runs the same pure `authorize()` through `@b2b-saas-starter/authz/client` — the package's client-safe entry point, which omits the Effect guard so the browser bundle stays out of `effect` and the logger. Two rules: a section whose data the actor cannot read is **absent** (the loader already withheld it), and an action inside a section they can see renders with a **reason** instead of the control ("Your role cannot mint tokens"). This is presentation, not enforcement — every mutation still passes `requireWorkspacePermission` on the server.
- A system admin (`user.role === 'admin'`) gets nothing inside a workspace. `/admin` keeps its own `requireAdmin` gate; never add a bypass to the workspace guard, because an invisible one leaves no trace in the audit log.
- **Impersonation (ADR 0054).** `WorkspaceShell` renders `ImpersonationBanner` above the header whenever the route context's `session.impersonatedBy` is set; it reads that through `useImpersonation()` (`src/lib/impersonation.ts`, a Schema decode over `useRouteContext({ strict: false })`) rather than a prop, because every gated route already carries `session` and the banner must show on all of them. Stop calls `stopImpersonatingServerFn`, invalidates the router, and navigates to `/admin`. The forbidden-actions guard is `src/lib/server/impersonation-guard.ts`: a path→action table over the capability's `IMPERSONATION_FORBIDDEN_ACTIONS`, applied in `api.auth.$.ts` before Better Auth runs (403 `forbidden_while_impersonating`). The catchall's one pre-handler session read now serves both the audit context and this guard (`readPreHandlerContext`). The `/admin/impersonate-user` and `/admin/stop-impersonating` audit rows stay for direct client calls; the UI's own flow is audited once, by the capability.
- `auth-client.ts` composes Better Auth `adminClient()` + `usernameClient()` + `twoFactorClient()` + `passkeyClient()` + `lastLoginMethodClient()` plugins. Client components that need a session call `authClient.useSession()`; `WorkspaceShell` renders a sign-out button via `authClient.signOut()`.
- Search-param validation: the auth-flow routes (`sign-in`, `sign-up`, `two-factor`, `verify-email`, `reset-password`, `invitations.accept`) use the plain `pickOptionalStrings` validator from `lib/utils.ts` — their route files ship statically to the browser, so an `effect/Schema` import there would pin the Effect runtime onto pages that never run a capability. Routes inside `/workspaces` (e.g. the audit trail's multi-field filters) keep `effect/Schema`, where the capability runtime is loaded anyway.
- Seeded demo credentials for a local D1 live in `src/lib/demo-workspace.ts` and docs/setup.md (`demo@starter.local`).
- Auth rate limiting — `src/lib/rate-limit.ts` is a thin config shim over `@b2b-saas-starter/rate-limit`; the fallback store is module-scope in the package, so `api.auth.$.ts` rebuilding the layer per request is safe; `clientKey` trusts only `cf-connecting-ip` (no `x-forwarded-for`, even in dev).
- Account lifecycle emails (password reset, verification) — `src/lib/server/auth-emails.ts` implements the `AuthEmailSender` port from `packages/auth` on the provider-light `EmailDispatcher`; unlike `sendInvitation`, a send failure is not downgraded (the auth endpoint has no honest "sent but not really" response). `src/lib/server/auth-audit/` records both the lifecycle and the system-admin exchanges (`auth.sign_in` over email, username, passkey, or a social provider callback, `auth.sign_up`, `auth.password_reset_requested`, `auth.password_reset`, `auth.email_verified`, session end via `auth.sign_out` / `auth.session_revoked`, the two-factor exchanges (`auth.two_factor_enabled`/`_disabled` with pre-handler actors, `auth.two_factor_verified` from the response body), the passkey exchanges (`auth.passkey_added`/`_removed` with pre-handler actors — sign-in rides the shared `auth.sign_in` pair with `method: "passkey"`), plus their failures) through one `ExchangeRow` table in `auth-audit/exchanges.ts` — one row per endpoint, carrying where the actor comes from (`session` | `response` | `none`), the target, and whether success is signalled by a redirect. `auth-audit/record.ts` holds the single mapper and recorder; `api.auth.$.ts` parses the request URL once into an `AuthExchange` and threads it through the rate-limit bucket, the Turnstile gate, the recorder and the one credential-change notifier (`credential-change-notification.ts` — emails the account holder on every two-factor or passkey change the rows mark `notifyOnSuccess`, best-effort). The session-ending rows take their actor from a pre-handler session read (`needsPreHandlerActor`).
- Social sign-in and linking — providers are env-gated and absent until configured (ADR 0057): `activeSocialProviders` (`@b2b-saas-starter/env`) resolves the worker env, `auth-runtime.ts` carries the result onto `AuthConfig.socialProviders`, and `lib/server/social-providers.ts` exposes the active ids to the auth screens as a server fn (ids only — secrets never cross). Link/unlink audit events come from the auth instance's account hooks (`lib/server/social-account-audit.ts`), best-effort like every audit write; the OAuth callback exchange rows (`/callback/{github,google}`) record the sign-in itself with the provider as the method. The docs page is `content/docs/integrations/social-sign-in.mdx`.

## Error handling

- `runWorkspaceCapabilities`/`runCapabilities` map typed capability failures: `WorkspaceNotFound` → TanStack `notFound()` (404 page), `CapabilityUnavailable` → `CapabilityUnavailableError`, rendered by `router.tsx`'s `defaultErrorComponent` as a friendly degraded-state notice (CLAUDE.md rule 3), and `AuthorizationDenied` → `ForbiddenError`. Loaders don't catch anything themselves.
- The degraded-state discriminant is `CAPABILITY_UNAVAILABLE_ERROR_NAME` in `src/lib/capability-error.ts` — a client-safe module (no `cloudflare:workers` import) single-sourcing the error's `name` and the router's check. `FORBIDDEN_ERROR_NAME` sits beside it on the same rules. Loader errors cross the SSR boundary through `defaultSerializeError`, which keeps only `name`/`message` — never sniff message text or use `instanceof`.
- Capability-backed routes set `pendingComponent: RoutePending` (`src/components/route-pending.tsx`).
- The demo-workspace slug constant lives in `src/lib/demo-workspace.ts`; workspace UI (shell nav, command palette) threads the current `$workspaceSlug` — there is no demo-slug fallback anywhere: `WorkspaceShell` requires `workspaceSlug` (`null` on system surfaces like `/admin`), and the palette falls back to the `/workspaces` list.

## Patterns

- **One page anatomy.** Every workspace page renders `WorkspaceShell > PageHeader + Panel(s)` (`src/components/page/`). `PageHeader` owns the `h1`, description, breadcrumb slot, and action row; `pageTitle` (`src/components/page/page-title.ts`) derives every document title, so a route's `head()` builds its string there instead of hand-writing it. `Panel` is the single sharp workspace wrapper (title, description, action row, footer); `CreateSection` is its create-or-reason half and `ListSection` its list half (rows or the empty state in their place, plus an optional denied-reason footer) — a resource panel is the two of them inside a `Panel`, never a hand-rolled heading-and-empty section. `ActionFeedback` renders a `useServerAction` result's error (and ok notices) — no panel hand-rolls a destructive `Alert` or a raw `<p role="alert">`. `Identifier` is the one mono, break-all-safe rendering for tokens, URLs, secrets, and ids. The shell centers every page at one `max-w-4xl` column; pages do not pick their own widths.
- **One table.** `DataTable` renders the admin users table and the audit trail alike; `formatDateTime` (`src/lib/format-date.ts`) is the one table timestamp, so the two tables cannot disagree.
- Use shadcn/ui primitives from `src/components/ui` — don't ship one-off primitives.
- Use semantic Tailwind tokens, not raw one-off colors.
- Use TanStack Form for meaningful mutation forms (`sign-in.tsx`, `api-token-form.tsx` are the canonical references).
- The command palette generates its workspace entries from `WORKSPACE_NAV` (same `viewerCan` filter as the sidebar) and indexes doc + blog titles/descriptions through the cached meta promises when its lazy dialog opens. The sidebar nav carries a `group` per row; the palette keeps matching the section name via item keywords (`General` answers "settings").
- Keep full workspace-data search out of the first search index; search public content + command actions first.

## Testing

- Vitest for unit tests co-located with components (`*.test.tsx`).
- **Loaders are testable without a worker.** `vite.config.ts` aliases `cloudflare:workers` to the inert shim in test mode, so `DB` is undefined and `runWorkspaceCapabilities` answers from the Seed layer: a Vitest test calls `loadWorkspaceSettings({ workspaceSlug: 'starter-lab', userId: 'usr_dev' })` directly and asserts on the payload (`src/lib/server/workspace-settings.test.ts`). `usr_demo` owns the seed workspace and `usr_dev` is a plain member of it, which is what makes an owner/member payload comparison possible. Route-level page tests take the payload from the real loader rather than a hand-written fixture, so a payload shape change cannot pass in a test and fail in the app.
- `renderWithRouter` (`src/test/router-harness.tsx`) takes an optional `routeContext` — what the route under test's `beforeLoad` returns — for components that read the route context instead of taking it as a prop; `workspace-shell.test.tsx` renders the impersonation banner that way.
- **A parent route with a `component` and no `<Outlet />` swallows its children** (`Match.js`: `Comp ? jsx(Comp) : jsx(Outlet)`). That is why the dashboard is `workspaces.$workspaceSlug.index.tsx` and there is no `workspaces.$workspaceSlug.tsx`: as a route file with a component it silently replaced `/settings` with the dashboard. Nothing but an e2e test catches this class of bug — component tests render the page directly and never exercise the match chain.
- **Server-function behaviour is tested as the effect, not through the server fn.** A `createServerFn` handler cannot run under Vitest — it opens with `requireRequestSession()`, which reaches `authRuntime` and a real request context. So the effect below the gate is exported and driven directly against purpose-built fixture layers: `src/lib/server/invitations.test.ts` seeds `SeedWorkspaceInvitations` per case (the app's own layer starts empty), supplies `testWorkspaceContext(workspace, actor)` for the role under test, and stubs `EmailDispatcher` to assert the send-failed fallback. Use plain `it` + `Effect.runPromise` there, not `@effect/vitest`'s `it.effect`: its `TestClock` starts at epoch 0, so an expiry fixture dated after 1970 would sit in that clock's future.
- **A page's one server call is a prop, not an import.** `invitations.accept.tsx` exports `AcceptInvitationPage` taking `accept: AcceptInvitation`; the route wraps it in `AcceptInvitationRoute`, which reads the loader and passes the real server fn. The test then asserts the two outcomes the user sees — navigated to the workspace, or a reason in an `alert` — with no session. Same shape as `WorkspaceSettingsPage`'s `ports`.
- **A server-only adapter can still be tested for its no-request branch.** `invitation-binding.test.ts` calls `webInvitationBinding` with no ambient request, which is the branch that never reaches Better Auth, and runs the capability's own `readPluginBindingFailure` over the rejection to prove it classifies as unavailable rather than refused.
- Playwright e2e in `e2e/` driven by `playwright.config.ts`. Use the same dev server, not a built artefact. `e2e/passkeys.spec.ts` drives Chromium's CDP virtual authenticator (`WebAuthn.addVirtualAuthenticator`, options nested under `options` in the current protocol) — the whole register/sign-in/remove flow runs without hardware; the spec skips itself when no seeded local D1 exists.
- Storybook config at `.storybook/`, stories co-located (`*.stories.tsx`). Follow the storybook skill for new stories.
