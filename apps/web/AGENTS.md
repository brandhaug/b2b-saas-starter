# apps/web

TanStack Start web app served by a Cloudflare Worker (`vite.config.ts` uses the `cloudflare:workers` shim). Dev server runs on `:3071`. Owns the public showcase, knowledge content, auth screens, the seed-backed workspace reference app, admin dashboard, Storybook, Vitest (unit), and Playwright (e2e).

## Routes

- `/` — interactive architecture showcase, capability-backed against the `starter-lab` seed workspace.
- `/docs`, `/blog`, `/faq`, `/help`, `/changelog` — checked-in MDX/JSON knowledge content.
- `/pricing`, `/privacy`, `/terms` — standard B2B SaaS surfaces adapted for the starter.
- `/sign-in` — email/password via Better Auth. Carries the forgot-password link and the sign-up link.
- `/sign-up` — public registration (auto sign-in, verification email follows). Turnstile-protected when configured: the page's loader fetches the site key server-side, the widget token rides `x-turnstile-token`, and the auth route verifies it via `TurnstileVerifier` (see `lib/server/turnstile.ts`). Unset env = no widget, no gate.
- `/forgot-password` — request form; the response message is constant whether or not the email exists (non-disclosure rule, same as the endpoint).
- `/reset-password` — the landing page for the emailed reset link. The link points at `/api/auth/reset-password/:token` (the auth handler), which validates the token and redirects here with `?token=` or `?error=`; one opaque "cannot be used" state for every failure. Success redirects to `/sign-in` — the reset revokes every session.
- `/verify-email` — the landing page for the verification link. Same hop shape: `/api/auth/verify-email` redirects here (success plain, failure with `?error=`); `autoSignInAfterVerification` means the success arrival carries a session cookie. The unverified state itself surfaces as the `EmailVerificationBanner` on `/workspaces`, with a resend action.
- `/workspaces`, `/workspaces/$workspaceSlug` (the dashboard, in `workspaces.$workspaceSlug.index.tsx`), `/workspaces/$workspaceSlug/assistant`, `/workspaces/$workspaceSlug/settings`, `/workspaces/$workspaceSlug/api-tokens` — reference app; the index lists the user's memberships via the `listWorkspacesForUser` projection (possibly empty — empty state with a create-workspace form, never a 404; creating makes the signed-in user its first owner). Settings carries rename (`organization:update`) and delete (`organization:delete`) through `src/lib/server/workspace-lifecycle.ts` plus invitation/webhook segments; the API tokens page is the create/list/revoke surface (`apiToken:create/list/revoke`, loader hard-gated on `apiToken:list` so a plain member meets a denial at the URL) backed by `src/lib/server/api-tokens.ts`; the assistant page hard-gates on `{ assistant: ['read'] }` and asks through `AssistantService` (`src/lib/server/assistant.ts`) — its loader carries `configured`, and with no provider configured the form is replaced by honest copy instead of an error; nav and palette thread the current slug (`src/routes/workspaces.tsx` is the subtree's auth-gate layout route).
- `/admin` — Better Auth admin plugin dashboard, gated by `requireAdmin` (admin role required; non-admins 404). System-level reads only: users via the admin plugin's `listUsers` (`src/lib/server/admin.ts`), audit events via `runCapabilities` + `AuditEventLog.listGlobal` — it never borrows a workspace, so the shell renders with `workspaceSlug={null}` and no unread badge. **No impersonation UI on purpose** — out of scope for the starter.
- `/invitations/accept?invitation=<id>` — the destination of the emailed invite link. Deliberately **outside** the `/workspaces` subtree: those routes resolve a workspace the visitor must already be a member of, and an invitee is not one until they accept. It keeps its own `requireSession` gate (an invitation is addressed to an email, so there is nothing to match until we know who is asking) and shows one opaque "cannot be used" state for every failure — expired, cancelled, already accepted, or addressed to somebody else.
- `/account` — account-level security settings (two-factor enable/verify/disable via `TwoFactorPanel`, active-session list with per-session revoke and "sign out everywhere else" via `SessionsPanel`). Like `/invitations/accept`, it keeps its own `requireSession` gate: it is user-level, not workspace-level.
- `/two-factor` — the sign-in challenge page. When two-factor is enabled, credential sign-in opens no session; it sets Better Auth's short-lived two-factor cookie and `SignInPage` routes here (preserving `?redirect=`). Verifying a TOTP code (`authClient.twoFactor.verifyTotp`) exchanges the cookie for a session.
- `/api/auth/$` — Better Auth catchall handler.

## Data fetching

- Route loaders use `runWorkspaceCapabilities(slug, effect, actor)` (`src/lib/capabilities.ts`) to call `@b2b-saas-starter/capabilities` directly. Reads that are not scoped to one workspace (the `/workspaces` index projection, `/admin`'s global audit log) use `runCapabilities(effect)` from the same file — it provides the capability services without `WorkspaceContext`. **There are no REST round-trips from this app to `apps/api`** — `apps/api` is the _external_ surface.
- Prefer the named read projections from the capabilities package over hand-composed `Effect.gen` loaders: the dashboard loads `workspaceDashboard`, which ships pre-computed aggregates (unread count). Components render those values — don't re-derive them in `useMemo`.
- **Permission-shaped payloads.** The workspace loaders live in `src/lib/server/workspace-dashboard.ts` and `workspace-settings.ts`, not inline in the route. Each hard-gates the page's own read permission (`{ notification: ['read'] }`) with `requireWorkspacePermission`, then wraps every further segment in `whenPermitted(permission, effect)` (`src/lib/server/authorize.ts`), which yields `null` instead of failing. A `null` segment means the read never ran, so a member's serialized loader data carries no API-token count, no webhook count and no invitation list — hiding those in the component alone would still ship them in the SSR payload. The payload types are declared in the app, not in `capabilities`: which segments exist is an authorization decision, and capabilities do not make those.
- `src/lib/capabilities.ts` reads bindings from `cloudflare:workers` (same as `auth-runtime.ts`): with a real `DB` binding the Live D1 layer activates; without one the in-memory Seed layer keeps the app provider-light. Never hardcode an empty env. `vite dev` aliases to `cloudflare-workers-shim-dev.ts`, which attaches the persisted local D1 (`packages/db/.wrangler`, from `db:migrate:local` + `db:seed`) via wrangler's `getPlatformProxy` when it exists — so credential sign-in and Live layers work locally (ADR 0049). Test and build keep the inert `cloudflare-workers-shim.ts` (`DB: undefined`); the dev shim's Node imports stay behind `import.meta.env.SSR` because dev serves it to the browser too. Client-side navigations run loaders in the browser against the Seed layer regardless, so Seed/Live fixture equivalence (demo user membership included) is load-bearing.
- Mutations use TanStack Start server functions (e.g. `createApiTokenServerFn`) that wrap a capability call. Server-fn inputs are validated by `effect/Schema` **with all constraints in the schema** (no imperative re-validation).
- **A server function holds the session gate; the behaviour sits below it as an exported effect.** `src/lib/server/invitations.ts` is the reference: `sendInvitation`, `cancelInvitation`, `invitationPreview` and `acceptInvitation` are effects taking the actor's address, the request origin and the `EmailDispatcher` as arguments, and each `…ServerFn` adds only `requireRequestSession()`, `requestOrigin()` and the binding. That split is what makes the permission gates and the invitation non-disclosure rule testable — `requireRequestSession` reaches the auth runtime, which no Vitest harness stands up.
- Mutations that go through Better Auth's `organization` plugin pass a **binding** as the last argument to `runWorkspaceCapabilities` / `runCapabilities` (`CapabilityBindings`). The adapter lives in a server-only module (`src/lib/server/invitation-binding.ts`) and is passed per call rather than sitting on the module-level `starterEnv`: `src/lib/capabilities.ts` is bundled for the browser too, so a module-level adapter would drag the whole Better Auth server instance into the client bundle. Every invitation endpoint the plugin exposes is `requireHeaders: true`, which is the whole reason the adapter has to live in the app.
- Effect Atom for client server-state is **not wired** today; loaders + server functions are sufficient. Revisit once a route needs subscribe/optimistic semantics.

## Observability

- **One wide event per HTTP request, opened in exactly one place.** `src/start.ts` registers a global TanStack Start request middleware (`createStart({ requestMiddleware })`) that wraps every server request — SSR document renders and server-function calls — in `runWebRequestScope` (`src/lib/observability.ts`). It continues any inbound `traceparent`, provides `makeOtlpLayer` per invocation (never per isolate — see ADR 0050), and emits the canonical line with `statusCode` and a `nested` array when the response is ready. `WideEventLoggerLive` is provided isolate-level from a module-scope `ManagedRuntime`, not rebuilt per request.
- **Nested work joins that scope; it never opens its own.** `runWorkspaceCapabilities` / `runCapabilities`, the `/api/auth/$` handler, and the auth gates in `src/lib/server/auth.ts` / `src/lib/server/admin.ts` all call `withWebRequestScope({ event, metadata }, effect)`, which becomes a child span under the request span, reuses the request's loggers and exporters, and folds its own `Effect.annotateLogsScoped` fields into the request's event. Without it a page load emits one wide event and one root trace _per loader_. Don't call `withTriggerScope` directly from a loader.
- Outside a request — a client-side navigation re-running loaders against the Seed layer, or a standalone test — `withWebRequestScope` falls back to its own scope and tags the event `scope: 'standalone'`, so a missed join is visible in the log stream instead of silently producing an extra root trace.
- The registry is a `WeakMap` keyed by the request object (an isolate interleaves concurrent requests, so a module-level "current" would race). `src/lib/request-context.ts` exposes the lookup as `currentRequest()`, wrapping `createIsomorphicFn`/`getRequest` in one place: it keeps `getRequest` out of the browser bundle, returns `undefined` rather than throwing with no ambient request, and is the seam tests mock.
- `authRuntime` holds only the `Auth` service. Loggers, tracer, and exporters belong to one request and must not live on a per-isolate runtime — the auth gates reach them by joining the request scope (above), not by reading `authRuntime`.
- `OTEL_EXPORTER_OTLP_ENDPOINT` (plus `SERVICE_VERSION` / `GIT_COMMIT_SHA` / `ENVIRONMENT`) reaches local dev through `src/lib/cloudflare-workers-shim.ts`. Unset, the console JSON event is the whole story and nothing fails.
- **The required-env gate runs before the request scope.** `src/start.ts` registers `configGateMiddleware` ahead of the observability middleware; it calls `enforceRequiredEnvOnce` (`src/lib/server/env-gate.ts`) once per isolate. With `ENVIRONMENT=production` and an insecure `BETTER_AUTH_SECRET`/`BETTER_AUTH_URL` (missing, placeholder, or too-short — see `auditRequiredEnv` in `@b2b-saas-starter/env`) every request throws `InsecureProductionEnvError`; with another `ENVIRONMENT` value it emits one standalone `config.insecure` wide event and continues. Unset `ENVIRONMENT` is local dev and stays silent.

## Auth

- The auth stack runs on `effectful-better-auth` (the sibling repo's Effect v4 wrapper): `packages/auth` mints the `Auth` service (`Auth.Tag` provides `{ api, instance }`; `api` endpoints are Effects failing `BetterAuthApiError`) and the `AuthConfig` key; `src/lib/auth-runtime.ts` provides `AuthConfig` from worker env and exposes the per-isolate `authRuntime`. `/api/auth/$` mounts the handler via `toHttpEffect` (rate limiting, wide events, and auth audit wrap it as ordinary Effect middleware).
- Server gates live in `src/lib/server/auth.ts`:
  - `requireSession(redirectTo)` — redirects anonymous visitors to `/sign-in` (preserving `?redirect=`) and returns the session. It runs ONCE in the `/workspaces` layout route's `beforeLoad` (`src/routes/workspaces.tsx`); child routes read `context.session` instead of re-gating. Don't copy the gate into new `/workspaces/*` routes.
  - `requireAdmin(redirectTo)` for `/admin` — additionally checks the Better Auth admin role (`user.role === 'admin'`); non-admins get a 404 (non-disclosing). `/admin` keeps its own `beforeLoad` gate.
  - `requireRequestSession()` inside **every** workspace-data server-function handler. On session expiry it fails with the typed `UnauthorizedError` (message displayed by the calling form) — never a redirect; redirects belong to navigation gates only.
- Workspace loaders and server functions must pass the actor (`{ userId: session.user.id }`) to `runWorkspaceCapabilities`; the capabilities layer enforces workspace membership and non-members get `WorkspaceNotFound`. Only trusted public-showcase reads (`/` homepage) omit the actor.
- Membership is not permission. Every workspace **mutation** additionally composes `requireWorkspacePermission(permission)` (`src/lib/server/authorize.ts`) inside the effect it guards — it reads the actor the `WorkspaceContext` layer resolved and asks the shared `authorize()` path in `@b2b-saas-starter/authz`. Name the permission (`{ apiToken: ['create'] }`), never the role: `if (actor.role === 'owner')` puts the role table in two places. `createApiTokenServerFn` is the reference. A denial leaves the boundary as `ForbiddenError`, whose `message` the calling form displays.
- **The UI gates too, and never by role name.** The loader payload carries `viewer: { role }`; components ask `viewerCan(viewer, permission)` (`src/lib/permissions.ts`), which runs the same pure `authorize()` through `@b2b-saas-starter/authz/client` — the package's client-safe entry point, which omits the Effect guard so the browser bundle stays out of `effect` and the logger. Two rules: a section whose data the actor cannot read is **absent** (the loader already withheld it), and an action inside a section they can see renders with a **reason** instead of the control ("Your role cannot mint tokens"). This is presentation, not enforcement — every mutation still passes `requireWorkspacePermission` on the server.
- A system admin (`user.role === 'admin'`) gets nothing inside a workspace. `/admin` keeps its own `requireAdmin` gate; never add a bypass to the workspace guard, because an invisible one leaves no trace in the audit log.
- `auth-client.ts` composes Better Auth `adminClient()` + `usernameClient()` + `twoFactorClient()` plugins. Client components that need a session call `authClient.useSession()`; `WorkspaceShell` renders a sign-out button via `authClient.signOut()`.
- Search-param schemas validate inputs with `effect/Schema` (see `sign-in.tsx`).
- Seeded demo credentials for a local D1 live in `src/lib/demo-workspace.ts` and docs/setup.md (`demo@starter.local`).
- Auth rate limiting — `src/lib/rate-limit.ts` is a thin config shim over `@b2b-saas-starter/rate-limit`; the fallback store is module-scope in the package, so `api.auth.$.ts` rebuilding the layer per request is safe; `clientKey` trusts only `cf-connecting-ip` (no `x-forwarded-for`, even in dev).
- Account lifecycle emails (password reset, verification) — `src/lib/server/auth-emails.ts` implements the `AuthEmailSender` port from `packages/auth` on the provider-light `EmailDispatcher`; unlike `sendInvitation`, a send failure is not downgraded (the auth endpoint has no honest "sent but not really" response). `src/lib/server/auth-audit.ts` records the lifecycle exchanges (`auth.sign_in` over email or username, `auth.sign_up`, `auth.password_reset_requested`, `auth.password_reset`, `auth.email_verified`, session end via `auth.sign_out` / `auth.session_revoked`, the two-factor exchanges (`auth.two_factor_enabled`/`_disabled` with pre-handler actors, `auth.two_factor_verified` from the response body), plus their failures) through one path→event table; the session-ending rows take their actor from a pre-handler session read (`needsPreHandlerActor`), shared with the admin-endpoint producer.

## Error handling

- `runWorkspaceCapabilities`/`runCapabilities` map typed capability failures: `WorkspaceNotFound` → TanStack `notFound()` (404 page), `CapabilityUnavailable` → `CapabilityUnavailableError`, rendered by `router.tsx`'s `defaultErrorComponent` as a friendly degraded-state notice (CLAUDE.md rule 3), and `AuthorizationDenied` → `ForbiddenError`. Loaders don't catch anything themselves.
- The degraded-state discriminant is `CAPABILITY_UNAVAILABLE_ERROR_NAME` in `src/lib/capability-error.ts` — a client-safe module (no `cloudflare:workers` import) single-sourcing the error's `name` and the router's check. `FORBIDDEN_ERROR_NAME` sits beside it on the same rules. Loader errors cross the SSR boundary through `defaultSerializeError`, which keeps only `name`/`message` — never sniff message text or use `instanceof`.
- Capability-backed routes set `pendingComponent: RoutePending` (`src/components/route-pending.tsx`).
- The demo-workspace slug constant lives in `src/lib/demo-workspace.ts`; workspace UI (shell nav, command palette) threads the current `$workspaceSlug` — there is no demo-slug fallback anywhere: `WorkspaceShell` requires `workspaceSlug` (`null` on system surfaces like `/admin`), and the palette falls back to the `/workspaces` list.

## Patterns

- Use shadcn/ui primitives from `src/components/ui` — don't ship one-off primitives.
- Use semantic Tailwind tokens, not raw one-off colors.
- Use TanStack Form for meaningful mutation forms (`sign-in.tsx`, `api-token-form.tsx` are the canonical references).
- Keep full workspace-data search out of the first search index; search public content + command actions first.

## Testing

- Vitest for unit tests co-located with components (`*.test.tsx`).
- **Loaders are testable without a worker.** `vite.config.ts` aliases `cloudflare:workers` to the inert shim in test mode, so `DB` is undefined and `runWorkspaceCapabilities` answers from the Seed layer: a Vitest test calls `loadWorkspaceSettings({ workspaceSlug: 'starter-lab', userId: 'usr_dev' })` directly and asserts on the payload (`src/lib/server/workspace-settings.test.ts`). `usr_demo` owns the seed workspace and `usr_dev` is a plain member of it, which is what makes an owner/member payload comparison possible. Route-level page tests take the payload from the real loader rather than a hand-written fixture, so a payload shape change cannot pass in a test and fail in the app.
- **A parent route with a `component` and no `<Outlet />` swallows its children** (`Match.js`: `Comp ? jsx(Comp) : jsx(Outlet)`). That is why the dashboard is `workspaces.$workspaceSlug.index.tsx` and there is no `workspaces.$workspaceSlug.tsx`: as a route file with a component it silently replaced `/settings` with the dashboard. Nothing but an e2e test catches this class of bug — component tests render the page directly and never exercise the match chain.
- **Server-function behaviour is tested as the effect, not through the server fn.** A `createServerFn` handler cannot run under Vitest — it opens with `requireRequestSession()`, which reaches `authRuntime` and a real request context. So the effect below the gate is exported and driven directly against purpose-built fixture layers: `src/lib/server/invitations.test.ts` seeds `SeedWorkspaceInvitations` per case (the app's own layer starts empty), supplies `testWorkspaceContext(workspace, actor)` for the role under test, and stubs `EmailDispatcher` to assert the send-failed fallback. Use plain `it` + `Effect.runPromise` there, not `@effect/vitest`'s `it.effect`: its `TestClock` starts at epoch 0, so an expiry fixture dated after 1970 would sit in that clock's future.
- **A page's one server call is a prop, not an import.** `invitations.accept.tsx` exports `AcceptInvitationPage` taking `accept: AcceptInvitation`; the route wraps it in `AcceptInvitationRoute`, which reads the loader and passes the real server fn. The test then asserts the two outcomes the user sees — navigated to the workspace, or a reason in an `alert` — with no session. Same shape as `WorkspaceSettingsPage`'s `ports`.
- **A server-only adapter can still be tested for its no-request branch.** `invitation-binding.test.ts` calls `webInvitationBinding` with no ambient request, which is the branch that never reaches Better Auth, and runs the capability's own `readPluginBindingFailure` over the rejection to prove it classifies as unavailable rather than refused.
- Playwright e2e in `e2e/` driven by `playwright.config.ts`. Use the same dev server, not a built artefact.
- Storybook config at `.storybook/`, stories co-located (`*.stories.tsx`). Follow the storybook skill for new stories.
